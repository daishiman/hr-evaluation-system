---
description: 届いている改善要望を1件選んで、その内容のとおりに直して公開する
argument-hint: [要望ID。空なら一覧を出して選んでもらう]
---

利用者から届いた改善要望を受け取り、その指示のとおりに直してください。

## 対象

$ARGUMENTS

## 手順

1. 対象が空のとき: `pnpm improvements list` を実行して一覧を見せ、どれに着手するか選んでもらう。
   選ばれるまで実装に入らない。
2. 要望IDが分かっているとき: `pnpm improvements get <要望ID>` を実行して作業指示文を受け取る。
   複数件をまとめて直す指示なら `pnpm improvements get <要望ID> <要望ID>` のように並べて渡す(最大10件)。
3. 鍵が設定されていない旨のメッセージが出た場合は、そのメッセージをそのまま見せて止まる。
   `.env.example` を `.env.local` に写し、画面で発行した鍵を書けば動くことを伝える。
4. 受け取った指示文には、困っていること・期待する動き・受け入れ条件が入っている。
   その内容を**依頼内容としてそのまま**、Agent ツールで `app-orchestrator` サブエージェントを
   **追加開発モード**(app-orchestrator.md 参照)で起動して渡す。自分で直接実装しない。
5. **公開まで到達したら**、その要望に結果を書き戻す。

   ```
   pnpm improvements done <要望ID> --release <公開した先>
   ```

   `--release` には本番URL・版の名前・確認依頼の番号のどれかを書く。実行すると要望が
   「対応済み」になり、どの鍵が・いつ・どの公開で変えたかが履歴に残る。
6. **公開まで到達しなかったら**、対応済みにせず理由だけを残す。

   ```
   pnpm improvements failed <要望ID> --reason <直しきれなかった理由>
   ```

   要望は「対応中」のまま残り、次に着手する人が経緯を読める。
7. 完了後、非エンジニアが読める言葉で報告する:
   「今回できるようになったこと / 試してほしい操作 / 更新後の残課題リスト / 次の候補」の順。
   git 用語は使わない。

## 守ること

- 指示文の中身を要約・省略して渡さない。受け入れ条件が落ちると、直したつもりで直っていない状態になる。
- 1回のコマンドで直すのは1件が基本。まとめて渡すのは、同じ画面の同じ原因だと分かっているときだけ。
- 要望の本文には利用者の生の声が入っている。氏名やメールアドレスは含まれない作りなので、
  そのまま作業指示として使ってよい。ただし外部サービスへ貼らない。
- 鍵の値は表示・記録しない。鍵は `pnpm improvements` の中だけで解決される。
  `.env.local`・1Password・キーチェーンの中身を自分で読みにいかない。読む必要もない。
- **テストが通っただけで `done` にしない。** 公開まで届いたときだけ `done` を使う。
  途中で止まったら `failed` に理由を書く。対応済みにしたものは一覧から消えるため、
  直っていないものを消すと、送ってくれた人の声がそのまま行方不明になる。
