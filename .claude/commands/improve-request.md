---
description: 届いている改善要望を1件選んで、その内容のとおりに直して公開する
argument-hint: [要望ID。空なら一覧を出して選んでもらう]
---

利用者から届いた改善要望を受け取り、その指示のとおりに直してください。

## 対象

$ARGUMENTS

## 手順

1. 対象が空のとき: `pnpm improvements list` を実行して一覧を見せ、どれに着手するか選んでもらう。
   選ばれるまで実装に入らない。
2. 要望IDが分かっているとき: `pnpm improvements get <要望ID>` を実行して作業指示文を受け取る。
   複数件をまとめて直す指示なら `pnpm improvements get <要望ID> <要望ID>` のように並べて渡す(最大10件)。
3. 通行証が無い旨のメッセージが出た場合は、そのメッセージをそのまま見せて止まる。
   `pnpm improvements login` を実行し、ブラウザで承認すれば動くことを伝える(承認は人が押す)。
4. 受け取った指示文には、困っていること・期待する動き・受け入れ条件が入っている。
   その内容を**依頼内容としてそのまま**使い、実装は `/improve-app`(Codex では `$improve-app`)の実行ルールに従う
   (段階判定・報告様式は [improve-app.md](improve-app.md) が正本)。
   ただし委譲するときは次の3点を明示して渡す。improve-app の既定(段階による main 直反映、確認依頼を作ってから了承を取る順番、複数の要望を分解して1件だけ選ぶこと)より優先する。
   - main へ直接反映せず、ブランチで進める(要望の状態は確認依頼を通して進めるため。5・6)。
   - 確認依頼(PR)は作らず、preview で試せる状態で止まって報告する(勝手に出さない)。
   - 2 でまとめて受け取った要望は、同じ原因の1件の修正として扱う(分解して1件だけ直すことはしない)。
5. **依頼者が preview で了承したら**、止めていた続きを improve-app の手順どおりに進める
   (確認依頼(PR)の作成→取り込み→公開→本番確認→残課題の更新→完了報告)。了承はこの1回で済んでいるので重ねて取らない。
   確認依頼を作ったら、その要望をレビュー待ちにする。確認依頼の本文には、直した要望のIDを必ず書く(あとで対応関係を追えなくなるため)。

   ```
   pnpm improvements review <要望ID> --pr <確認依頼のURLまたは番号>
   ```

6. **その確認依頼が取り込まれたら**、対応済みにする。

   ```
   pnpm improvements done <要望ID> --pr <確認依頼のURLまたは番号>
   ```

   5 を通っていない要望を `done` にしようとすると、サーバー側が断る。
   取り込まれるまで完了扱いにしないための決まりで、迂回しない。
7. **直しきれなかったら**、対応済みにせず理由だけを残す。

   ```
   pnpm improvements failed <要望ID> --reason <直しきれなかった理由>
   ```

   要望は「対応中」のまま残り、次に着手する人が経緯を読める。

## 守ること

- 指示文の中身を要約・省略して渡さない。受け入れ条件が落ちると、直したつもりで直っていない状態になる。
- 1回のコマンドで直すのは1件が基本。まとめて渡すのは、同じ画面の同じ原因だと分かっているときだけ。
- 要望の本文には利用者の生の声が入っている。氏名やメールアドレスは含まれない作りなので、
  そのまま作業指示として使ってよい。ただし外部サービスへ貼らない。
- 通行証・鍵の値は表示・記録しない。どちらも `pnpm improvements` の中だけで解決される。
  `.env.local`・1Password・キーチェーンの中身を自分で読みにいかない。読む必要もない。
- **テストが通っただけで `done` にしない。** `done` は確認依頼が取り込まれたときだけ。
  作っただけなら `review`、途中で止まったら `failed` に理由を書く。対応済みにしたものは
  一覧から消えるため、直っていないものを消すと、送ってくれた人の声が行方不明になる。
