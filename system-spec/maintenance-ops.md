**問**

maintenance-ops の要件（検査・E2E・報告の切り分け）は何か。（R1〜R3 の決定と実装に合わせた改訂版）

**答**

(1) 次の検査を pnpm test に入れ、違反が 0 件でなければ失敗にする。入口を通らない書き込み（server-actions-contract.test.ts）、batch の外で 2 つ以上の表を書く関数（write-atomicity-contract.test.ts）、送り元の二重の検査（action-origin.test.ts）。 (2) 画面の通し試験（Playwright、pnpm test:e2e）で、6 つの経路（同じタブ・強制再読み込み・2 つのタブ・別の端末・戻る・bfcache からの復元）と控えの畳み方を確かめる。375px・768px の幅でも、同じタブの反映と控えの畳み方を確かめる。相手はローカルの preview だけにし、ローカル以外には向けられないよう止める（LOCAL_HOSTS）。 (3) 『反映されない』という報告を受けたときの切り分け手順を文書にする（deploy-notes §7）。応答の生成時刻のヘッダー、Workers Logs、ゾーンのキャッシュ規則を、読み取りだけで順に確かめる。会社の追加の取り消しが失敗した記録（compensation_failed）と、パスワード変更の続きが失敗した記録（rollforward_failed）を Workers Logs で見つけ、本番 DB を手で書き換えずに直す手順も同じ文書に書く（rollforward_failed は、ご本人にもう一度パスワードを変えてもらうと、続きがやり直される）。 (4) pnpm test と pnpm run check:docs を通し、新しい画面を足すときは鮮度の契約を使うことを README の文書の入口から辿れるようにする。

## To-Be / Delta

> 本章の**規範**。上位概念 (要件定義書 U3 ゴール / U4 目標 / U9 具体的やりたいこと) を本章の serves_goals で絞り込んだ射影であり、設計知識 card (非規範の参考資料) とは役割が異なる。As-Is (現行実装の姿) は spec-state.json の管轄外のため本節では断定せず、到達点と、その到達を判定する観測点だけを規範として置く。

### 到達すべき状態 (To-Be)

- **G2**: 通常・強制の再読み込みや URL の直接表示は、直前の書き込み結果を必ず含む。
- **G4**: 画面や書き込み API を追加しても、鮮度の保証が個別実装に頼らず共通契約として適用され、適用漏れは検査で落ちる。

### 受入条件 (Delta の判定点)

| 目標 | 到達点 | 達成の観測点 (measure) |
|---|---|---|
| O2 | 書き込み直後の再読み込みで反映率 100%。 | 書き込み→強制再読み込みの E2E と、ローカル preview の再現スクリプトで新しい行が毎回含まれる。加えて、リリース後の本番で、作成の直後に ⌘+Shift+R をして新しい行が出ることと、応答の生成時刻ヘッダーが作成より後であることを確かめる（作成は利用者のふだんの操作で行い、エージェントは本番に書き込まない）。前提として、ゾーンに HTML・/api を保存するキャッシュ規則が無いことを読み取りだけで確かめる。 |
| O4 | 鮮度契約を通らない書き込み経路を 0 件にする。 | 静的検査が、共通の包みを通らない Server Function と、画面から書き込みの fetch を直接呼ぶ箇所を 0 件と報告する |

### 本章がかなえる具体的やりたいこと (U9)

- **I1**: 書き込みを Server Functions の共通の包みにまとめ、成功したら同じ応答で今の画面を作り直す（next/cache の refresh）。他タブへの通知と、将来のキャッシュの無効化の置き場も、この包みと画面側の共通口に持たせ、全ての書き込み画面をそこへ寄せる。
- **I5**: 共通の包みを通らない書き込み経路を検出する静的検査と、4 経路の E2E を加える。
- **I6**: 応答に鮮度の手がかり（生成時刻）を載せ、反映されない報告を切り分けられるようにする。

### 本章に効く確定意思決定

- **D-002**: 書き込みの直後に同じタブの一覧・件数・会社切替メニューを最新にするには、書き込みの経路をどう組むか。
  - 採択: 書き込みを Server Functions（Server Actions）へ移し、成功したら同じ応答で表示中の画面を作り直す（next/cache の refresh） (`opt-server-functions`)
  - 目的適合: G1 を満たす（Next.js の文書では、Server Functions から呼んだ revalidatePath は表示中の画面をすぐ更新する）。ただし移行が終わるまでは二つの経路が混在し、G4 の検査が複雑になる。（2026-10-01 追記：確定後、表示中の画面の作り直しは I1 のとおり next/cache の refresh にそろえた。revalidatePath は、将来サーバー側にキャッシュを入れるときの無効化の置き場として共通の入口に残す。移行は今回すべて終えたので、二つの経路の混在は残っていない。）

### 本章での適用

Clean Code の『一つの規則は一か所に書き、検査で守る』を、鮮度と原子性の契約に当てはめた。書き込みの順序を共通の入口に集め、入口を通らない書き込み・batch の外で 2 つ以上の表を書く関数・送り元の検査の欠けを、pnpm test の 3 つの契約試験で 0 件に保つ（qa-r-ops-3 (1)）。取り消しややり直しまで失敗したときは compensation_failed・rollforward_failed を構造化したログに残し、それを手掛かりに本番 DB を手で書き換えずに直す手順を文書にする（同 (3)）。規則を人の記憶ではなく、検査と記録に持たせる（G4・G5）。

### Clean Code — deep knowledge card

- 出典カード: `ref-system-design-knowledge/references/clean-code.md`

#### 目的

codeを、次の変更者が意図・制約・failureを短時間で理解し、安全に変更・検証できる作業媒体にする。

#### 解決する問題

- 名前と抽象度が意図を表さず、readerが実装詳細からbusiness ruleを逆算する。
- 一つの変更理由が複数moduleへ散り、副作用とerror pathを予測できない。
- 重複したruleが別々に更新され、仕様のSSOTが崩れる。
- testがimplementation detailへ結合し、refactoringを妨げる。

#### 適用条件

- 複数人・長期保守・高変更頻度・重要ruleがあり、理解と変更の費用が支配的。
- test/lint/review/observabilityで改善効果をfeedbackできる。
- domain languageとcoding conventionをteamで合意・更新できる。

#### 非適用条件

- throwaway explorationでは全規則を先行適用せず、学習後に残すcodeだけを整理する。
- generated/vendor codeへ手動styleを強制しない。generation inputとboundaryを管理する。
- 短い関数、class化、DRY等を絶対値として扱い、局所的な明瞭さを悪化させる場合は適用しない。

#### トレードオフ・失敗モード

- naming/refactoring/testへ時間を使うため、寿命とriskが低いcodeでは投資超過になり得る。
- micro-function化でcontrol flowが多数fileへ散り、かえって読みにくくなる。
- DRYを急ぎ、異なるdomain conceptを一つの抽象へ結合して変更を難しくする。
- commentを全否定して、理由、trade-off、外部制約、security decisionまで消す。
- coverageやlint scoreを目的化し、重要behaviorの未検証を隠す。

#### goalへの寄与

- goalに関わるbusiness ruleを名前とtestで明示し、仕様→code→evidenceのtraceを短くする。
- maintenance objectiveには変更lead time、review指摘、escaped defect、rollback率などのoutcomeを使う。
- 無料toolの導入自体を成功とせず、teamが継続運用でき、重要riskを減らすかで判断する。
