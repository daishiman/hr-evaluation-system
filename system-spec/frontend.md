## To-Be / Delta

> 本章の**規範**。上位概念 (要件定義書 U3 ゴール / U4 目標 / U9 具体的やりたいこと) を本章の serves_goals で絞り込んだ射影であり、設計知識 card (非規範の参考資料) とは役割が異なる。As-Is (現行実装の姿) は spec-state.json の管轄外のため本節では断定せず、到達点と、その到達を判定する観測点だけを規範として置く。

### 到達すべき状態 (To-Be)

- **G1**: 書き込み成功を表示した時点で、同じタブの一覧・件数・ナビゲーション（会社切替など）がすべてその結果を含んでいる。
- **G3**: 同じ利用者の他のタブや、スマホ・タブレットでの画面復帰（bfcache 復元・タブ復帰）でも、古い一覧のまま操作を続けない。
- **G4**: 画面や書き込み API を追加しても、鮮度の保証が個別実装に頼らず共通契約として適用され、適用漏れは検査で落ちる。
- **G6**: 等級の呼び名は、その会社の等級名だけで表す。行動指針の向け先・評価セットの区分・昇格の要件・警告文・アンケートのタイトル・ボタンのどこにも英語の区分名を出さず、等級名を変えると次の表示からすべてに反映される。
- **G8**: 役割ごとに、どのページを開けて、そこで何ができ何ができないかを、ページ名を単位にした同じ形で確かめられる。表示は実際の権限の判定と食い違わない。
- **G12**: 設定の不足を知らせる表示は、何が足りないか・どう直すか・どこで直すかを短く示し、そこから直す画面へ1回の操作で移れる。
- **G13**: 並び順を持つ全ての編集画面で、矢印のボタンに加えて、長押ししたままのドラッグとキーボードでも並べ替えられる。
- **G14**: アンケートの選択肢を押しても何も起きない画面を無くす。見本として表示している画面では、見本であることと回答できない理由が分かる。
- **G15**: 画面の幅に対して内容が片側に寄り、右側の余白が目立つ画面を無くす。
- **G16**: 2つのページの内容を比べて出す警告は、比べている両方のページを階層つきのページ名とリンクで示し、項目ごとにどちらのページにあってどちらに無いかを表で示す。既定ではズレがあることと件数だけを1行で出し、中身は押すと開く。どちらのページから見ても、相手のページへ1回の操作で移れる。

### 受入条件 (Delta の判定点)

| 目標 | 到達点 | 達成の観測点 (measure) |
|---|---|---|
| O1 | 全ての作成・更新・削除フローで、成功表示と同じ描画のうちに一覧・件数へ反映する。 | 作成系 E2E で成功表示直後の DOM に新しい行と更新後の件数が含まれる（待機なし）。 |
| O3 | 他タブは通知受信またはタブ復帰から 1 秒以内に最新化する。 | 2 タブ E2E で、片方の書き込み後にもう片方が 1 秒以内に新しい行を表示する。 |
| O4 | 鮮度契約を通らない書き込み経路を 0 件にする。 | 静的検査が、共通の包みを通らない Server Function と、画面から書き込みの fetch を直接呼ぶ箇所を 0 件と報告する |
| O6 | 画面に出る等級の呼び名を、すべてその会社の等級名から作る。 | 等級名を変える結合テストで、行動指針・評価セット・昇格の要件・警告・アンケートのタイトル・ボタンの表示が新しい名前になることを確かめる。区分の英語名（Beginner・Regular・Chief・AM・Manager）を画面の文字として書く箇所が、静的検査で 0 件。既定の等級名と、移行後の本番の等級名が『等級N』『等級N-M』の形である。 |
| O8 | 権限の一覧を1つの定義から作り、実際の判定とのずれを 0 件にする。 | 権限の定義と、ルート台帳の accessClass・サーバー処理の最低ロールを照合する契約テストが通る。権限一覧ページと利用者一覧のモーダルが同じ定義から描かれる。 |
| O12 | 設定不足の表示の全件に、直す画面へのリンクと直し方を持たせる。 | 設定不足を返す処理の全件が、直す画面へのリンクと直し方を持つことを確かめる契約テスト（欠落 0 件）。 |
| O13 | 並び順を持つ全ての編集画面で、ドラッグ・矢印・キーボードのどれでも同じ並びになる。 | 並べ替えの部品のテストで3つの操作の結果が一致し、並び順を持つ編集画面がすべてその部品を使うことを静的検査で確かめる。 |
| O14 | 選択肢を押しても何も起きない箇所を 0 件にする。 | 見本画面で選択肢を押すと選んだ表示になり（保存はしない）、見本である旨と回答できない理由が出ること、回答画面で設問名や選択肢を押すと選ばれること、選択肢の値の重複が保存時に拒否されることをテストで確かめる。 |
| O15 | 対象の画面で、右側の余白が目立たない配置にする。 | 375・768・1280・1600 の4つの幅で、評価期間・行動指針・アンケートの見本などの対象画面を撮影し、内容が本文の幅を使っていることを目で確かめる。 |
| O16 | 比べて出す警告の全件に、比べている2つのページの階層つきの名前とリンクを持たせ、既定では1行に畳む。 | 比べる警告を作る処理の全件が2つのページを持つことを確かめる契約テスト（欠落 0 件）と、アンケート一覧・アンケート1本・使うKPIを選ぶの3画面で、閉じた状態が1行・開くと2つのリンクと表が出ることを確かめる画面のテスト。 |

### 本章がかなえる具体的やりたいこと (U9)

- **I1**: 書き込みを Server Functions の共通の包みにまとめ、成功したら同じ応答で今の画面を作り直す（next/cache の refresh）。他タブへの通知と、将来のキャッシュの無効化の置き場も、この包みと画面側の共通口に持たせ、全ての書き込み画面をそこへ寄せる。
- **I2**: 連続作成フォームで一覧の反映を最優先にし、控えをフォームの上に置き続けない。発行した初期パスワードの控えは暗号化して保存し、一覧の行から開き直せるようにする。
- **I3**: 他のタブへの書き込み通知と、タブ復帰・bfcache 復元時の最新化を入れる。
- **I5**: 共通の包みを通らない書き込み経路を検出する静的検査と、4 経路の E2E を加える。
- **I7**: 等級の呼び名を作る共通の関数を作り、区分名・行動指針のセット名・昇格の段階名・警告文・アンケートのタイトルの表示をすべてそこから作る。既定の等級名を『等級1』『等級2』『等級3』『等級4-1』『等級4-2』『等級5-1』『等級5-2』にし、既存の会社の等級名と、英語を含む表示名を一律に書き換える移行を入れる。
- **I9**: ページごとの権限を1つの定義（ページ・操作・役割ごとの可否・説明）にまとめ、『システムを管理する』に権限一覧ページを足し、利用者一覧に開閉できるボタンとモーダルを置く。説明はポインター・フォーカス・タップのどれでも出す。『Claude Code連携の鍵』を『Claude Code連携（システム開発者専用）』に改める。
- **I13**: 設定不足の表示を『何が足りない・どう直す・直す画面へのリンク』の形にそろえ、表示の部品と、文を作る側の両方を改める。
- **I14**: 並べ替えを共通の部品にし、長押しのドラッグ・矢印・キーボードで動かせるようにする。保存には、並び順の全体を送る形を足す。
- **I15**: 見本画面の選択肢を試しに選べるようにし、見本である旨と回答できない理由を出す。回答画面の設問名と選択肢の結びつき、選択肢の値の重複、固定バーとの重なりを直す。
- **I16**: 右側の余白が目立つ画面の配置を見直す。
- **I17**: 比べる警告の型に、2つのページ（階層つきのページ名とリンク）と項目ごとの有無を持たせる。ズレの警告を3画面に、既定は1行・押すと表で開く形で出す。公開後のズレには『この等級だけ新しい版の下書きを作る』を添える。

### 本章に効く確定意思決定

- **D-001**: 同じ利用者の他のタブや、スマホ・タブレットの画面復帰で古い一覧を残さないために、どの方式で最新化するか。
  - 採択: BroadcastChannel で同じブラウザの他タブへ通知し、visibilitychange と pageshow（persisted）でも取り直す (`opt-broadcast`)
  - 目的適合: G3（同じ利用者の他のタブと画面復帰）をそのまま満たす。通知はすぐ届くので O3 の 1 秒以内に収まる。別の利用者への配信は scope.out なので不要。
- **D-002**: 書き込みの直後に同じタブの一覧・件数・会社切替メニューを最新にするには、書き込みの経路をどう組むか。
  - 採択: 書き込みを Server Functions（Server Actions）へ移し、成功したら同じ応答で表示中の画面を作り直す（next/cache の refresh） (`opt-server-functions`)
  - 目的適合: G1 を満たす（Next.js の文書では、Server Functions から呼んだ revalidatePath は表示中の画面をすぐ更新する）。ただし移行が終わるまでは二つの経路が混在し、G4 の検査が複雑になる。（2026-10-01 追記：確定後、表示中の画面の作り直しは I1 のとおり next/cache の refresh にそろえた。revalidatePath は、将来サーバー側にキャッシュを入れるときの無効化の置き場として共通の入口に残す。移行は今回すべて終えたので、二つの経路の混在は残っていない。）
- **D-005**: 並び順を持つ編集画面で、長押ししたままのドラッグによる並べ替えを何で作るか。
  - 採択: Pointer Events で共通の hook を自作する (`opt-pointer-hook`)
  - 目的適合: 長押しの時間やスクロールとの区別を要件どおりに作れるので、G13 を満たせる。キーボードと矢印のボタンも同じ部品に入れる。
- **D-006**: 権限一覧（役割ごとに、どのページを開けて、そこで何ができるか）を、システム管理のページと利用者一覧のモーダルでどう見せるか。
  - 採択: 1つの表に役割のタブでの絞り込みを足し、スマホの幅ではページごとのカードに切り替える（①②③の組み合わせ。利用者の回答から足した案） (`opt-combined`)
  - 目的適合: 役割の違いを表で比べ、タブで1つの役割だけに絞り、スマホではカードで縦に読めるので、ページ名を単位にした同じ形で G8 を満たせる。
- **D-007**: 権限の定義（各ページでできる操作と、その説明）をどこに置くか。
  - 採択: route-ledger.json に操作と説明を足す (`opt-route-ledger-extend`)
  - 目的適合: ページの可否・操作・説明が1つの台帳に揃い、表示が判定と食い違わないという G8 を満たせる。

## 適用された設計知識

> 以下の deep knowledge card は設計判断を支援する**非規範の参考資料**であり、実装済み・検証済みの証拠ではない。カード内の `採否: applied` は設計採用を意味し、実装状態は意味しない。規範となる差分は本章の To-Be / Delta 節と参照先仕様で管理する。

### 本章での適用

Clean Architecture の『方針を詳細から切り離す』を画面側に当てはめた。同じタブの反映は Server Function の応答に載った新しい描画が担い、各画面は useSaveAction の結果 {ok, message} を出すだけにする（qa-r-frontend-3 (1)）。成功の結果は createCommitGate で新しい描画が終わるまで返さないので、言葉と一覧がずれない。他タブの通知・タブ復帰・通信の回復・bfcache 復元で取り直す方針は FreshnessSync という一つの共通口が持ち、BroadcastChannel・visibilitychange・online・pageshow という詳細はその内側に閉じる（同 (3)(4)）。 （2026-10-13 追記：G6〜G15）Clean Architecture の『方針を詳細から切り離す』を部品に当てはめた。並べ替えの方針（持ち上げる・動かす・置く・戻す・読み上げる）を一つの共通部品に置き、Pointer Events の長押し・矢印のボタン・キーボードという入力の詳細はその内側に閉じる（qa-v22 (2)、D-005）。権限一覧の表・タブ・カード・説明は同じデータから描く共通部品にし、ページとモーダルで使い回す（同 (3)、D-006）。設定不足の表示も共通の部品にして、各画面は構造化された値を渡すだけにする（同 (4)）。等級名はサーバーから受け取り、部品は英語の区分名を持たない（同 (1)）。 （2026-10-14 追記：G16）Clean Architecture の『方針を詳細から切り離す』を比べる警告に当てはめた。『閉じた1行に件数・押すとその場で開く・2つのページのリンクと表とボタン』という見せ方の方針を ComparisonGapNotice という一つの部品に置き、3画面はサーバーから受け取った ComparisonGap の値を渡すだけにする（qa-w07 (8)）。開閉の詳細は既存の InlineDetail（<details>/<summary>）の内側に閉じ、画面ごとに <details> を書かない。表の読み上げ（th の scope、○ と — の『ある』『ない』）も部品の中で一度だけ決めるので、使う画面が増えても抜け落ちない（同 (8)）。

### Clean Architecture — deep knowledge card

- 出典カード: `ref-system-design-knowledge/references/clean-architecture.md`

#### 目的

変化しやすいUI、DB、framework、外部サービスから、長く保持したい業務ルールとuse caseを隔離し、技術交換やテストを目的達成の阻害要因にしない。

#### 解決する問題

- 業務ルールがcontroller/ORM/UI lifecycleへ埋まり、単体で検証できない。
- 外部技術変更が内側のuse caseまで波及し、置換費用を予測できない。
- 入出力形式やvendor型が境界を越え、責務と所有者が曖昧になる。

#### 適用条件

- business ruleが外部I/Oより長寿命で、UI/DB/providerの変更可能性がある。
- 複数delivery channelや外部integrationから同じuse caseを再利用する。
- 重要なpolicyを高速・決定論的にテストする価値が、境界導入費を上回る。

#### 非適用条件

- 寿命の短い検証用prototypeで、交換可能性より学習速度が明確に優先される。
- domain ruleがほぼ無い単純変換scriptで、port/adapterが実質的な抽象を生まない。
- 外部製品そのものがsystemの目的で、抽象化すると必要機能が失われる。ただしsecurity/audit boundaryは別途必要。

#### トレードオフ・失敗モード

- 境界、DTO、mapping、dependency injectionの量が増え、小規模systemでは認知負荷が先行する。
- 「4層を作ること」が目的化すると、変化軸のないinterfaceやpass-through use caseが増える。
- domain modelを万能化してdelivery固有の制約を隠すと、現実のlatency/transaction/error semanticsを見失う。
- portを外側が定義したりinner layerがORM型を返したりすると、名前だけcleanな依存逆転になる。

#### goalへの寄与

- `essential_purpose`に直結するpolicyを外部詳細から守り、goal達成ロジックの検証を速くする。
- 制約に「vendor lock-in低減」「複数platform」「高い変更頻度」がある場合、変更範囲と移行riskを局所化する。
- 適用判断は「何層あるか」でなく、守るgoal、予想される変更、boundary testで観測する。

### Information Design (表現物の情報設計) — deep knowledge card

- 出典カード: `ref-system-design-knowledge/references/information-design.md`

#### 目的

保持しているデータを、受け手が**その利用文脈で最短の認知コストで目的を達成できる形**へ翻訳する。「見た目を良くする」ことではなく、情報の意味的な順序付け・取捨選択・加工を設計判断として明示し、視覚表現をその写像として導出できる状態にする。

#### 解決する問題

- 保存形式 (DB の値・API のフィールド) をそのまま表示形式として採用し、受け手が頭の中で変換させられる (生年月日を見せて年齢を計算させる、絶対日時を見せて「何日前か」を計算させる)。
- 全要素が同じ大きさ・同じ濃度で並び、どこから見ればよいか分からない (強弱の欠如)。
- ラベル・罫線・説明文など「無くても伝わる要素」が削られず、本体の情報を圧迫する。
- 最初に一つの形式 (表・リスト・箇条書き・JSON ダンプ) を作ってしまい、他の形式との比較機会が失われる (早期形式固定)。
- 装飾が「今風に見せる」ために使われ、操作可能性・状態・重要度といった意味を運んでいない。
- 情報の物理的な近さがグループの意味と一致せず、無関係な要素が隣接して誤読を生む。
- 「設計」と「デザイン」を別工程・別担当に分割し、前工程の出力が後工程の到達可能な品質の上限を決めてしまう。

#### 適用条件

- 人間が読む表現物を生成・レビューするとき (UI 画面、report、slide、ダッシュボード、CLI 出力、通知、エラーメッセージ、仕様書)。
- 出せる情報量が受け手の一度に処理できる量を上回り、取捨選択が避けられないとき。
- 受け手と利用文脈が一つに定まる、または文脈ごとに別表現を作る余地があるとき。

#### 非適用条件

- 機械が消費する成果物 (JSON/DB スキーマ/ログの構造化フィールド) — ここでは網羅性・安定性・後方互換が優先し、削減や加工はむしろ有害。
- 監査・法定表示・原本性が要件で、**元の値をそのまま**提示する義務があるとき (加工は併記に留める)。
- 習熟した専任者が長時間・大量に操作する高密度業務画面。一覧性と一括操作の効率が学習容易性より重い場合、表形式・高密度・等価表示が正解になりうる (Nielsen のユーザビリティ 5 指標のうち efficiency を優先する状況)。
- 探索的な使い捨て成果物で、寿命が短く投資が回収できないとき。

#### トレードオフ・失敗モード

- **学習容易性 ⇄ 効率性**: 情報を削って強弱を付けるほど初見は分かりやすくなるが、熟練者の一覧性・一括操作は落ちる。どちらを取るかは context of use が決めるのであって、原則が決めるのではない。
- **加工 ⇄ 検証コスト**: 表示値を加工するほど元データとの突合テストが増える。加工の各件に「どの task を助けるか」を書けないなら加工しない。
- 優先順位付けを飛ばしたまま視覚変数だけ調整し、「なんとなく今風」だが読み順が崩れた表現物を作る (最頻の失敗)。
- 削減を進めすぎて、文脈を持たない受け手が識別できなくなる (会員 No. のラベルまで落とす等)。削減の停止条件は「ラベルなしで受け手が識別できるか」。
- 「シンプルにする」を目的化し、必要な状態表示・エラー理由・可逆性の手がかりまで削る。
- 原則を checklist 化して機械適用し、非適用条件 (高密度業務画面・監査表示) に当てはめて品質を落とす。
- 強弱を色だけで表現し、色覚特性・モノクロ印刷・低コントラスト環境で情報が消える。

#### goalへの寄与

- 要件定義段階で「この表現物の受け手・task・優先順位」を宣言させることで、実装後の主観的な「なんかダサい」を**設計判断への差し戻し**に変換できる (レビューが好みの表明でなくなる)。
- 順位・グループ・削除理由・加工理由が構造化データとして残るため、生成 AI・人間のどちらが作っても同じ根拠で検証できる。決定論ゲート (`../../../scripts/validate-information-priority.py`) が手順の順序制約 (装飾より前に順位が確定していること) を機械検査する。
- 成果は「見た目の評価」ではなく outcome で測る: 目的達成までの操作数・初見での到達率・誤操作率・問い合わせ件数。装飾の量では測らない。
