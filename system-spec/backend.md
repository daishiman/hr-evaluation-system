#### 主たる接地根拠: `qa-r-backend-4`

**問**

backend の要件（書き込み API と鮮度の契約）は何か。（R1〜R3 の決定と実装に合わせた改訂版）

**答**

(1) 画面から呼ぶ書き込みを Server Functions（src/actions の 19 ファイル）へ移す。外部のエージェントが呼ぶ API（Bearer 鍵・端末の承認）、離脱時に送る利用記録（sendBeacon）、外観の選択の記録、認証、読むだけの検索・書き出しは Route Handler のまま残す。画面からしか呼ばれなくなった Route Handler は消し、書き込みの経路を二重にしない。 (2) Server Functions は共通の入口 runAction を通す。入口は、送り元の検査と認可（apiViewer）→ 大きさの上限（413）→ 入力の検証（zod）→ 本体 → 成功したときだけ next/cache の refresh、の順に行い、新しい画面を同じ応答に載せて {ok, message} の形で結果を返す（本番で例外の中身が隠れても、画面に理由を出せる）。読むだけの呼び出し（控えを開くなど）は runRead で受け、描き直さない。将来サーバー側にキャッシュを入れるときの無効化（revalidatePath・revalidateTag）の置き場もこの入口に持つ。 (3) 一つの操作で複数の表を書く書き込みは、次の 3 つの型のどれかで守る（D-003 案 A）。(a) 1 回の D1 batch に入るものは batch で書く（全部書けるか、何も書かれないか）。(b) batch に入りきらない会社の追加だけ、段階ごとの書き込みと取り消しの組で書き、途中で失敗したら逆順に取り消す（withCompensation）。取り消しも失敗したら compensation_failed を Workers Logs に残し、画面には失敗したことと管理者への連絡を出す。(c) 取り消せない認証ライブラリの書き込み（パスワードの変更）の続き（仮パスワードの印を外す・控えを消す）は 1 回の batch にし、失敗したら 1 回だけやり直して揃える（rollForward）。それでも失敗したら rollforward_failed を残し、画面には変更は済んだことと管理者への連絡を出す。batch の外で 2 つ以上の表を書く関数は、契約試験（write-atomicity-contract.test.ts）で見つけて落とす。 (4) 入口を通らない書き込み（画面側の書き込みの fetch、runAction を通らない Server Function、runRead の中での書き込み）を静的検査（server-actions-contract.test.ts）で見つけて落とす。例外（利用記録の sendBeacon・外観の選択の記録）は検査の中に理由付きで列挙する。新しい書き込みや画面を足すときも入口を使うことを、文書と検査で求める（I5・O4、G4）。

#### 裏付け質疑: `qa-d01`

**問**

公式文書で確かめた revalidatePath と OpenNext のキャッシュの扱いは、backend と infrastructure の要件にどう効くか。

**答**

Next.js 16.3.7 の文書によると、Route Handler で呼んだ revalidatePath は、パスに再検証の印を付けるだけで、次にそのパスを訪れたときに作り直す。表示中の画面をすぐに変えるのは Server Functions から呼んだ場合だけである。このアプリの書き込みはすべて Route Handler なので、同じタブの即時反映（G1）は画面側の router.refresh が担う。backend 要件（2）の revalidatePath は、将来のサーバー側キャッシュへの備えにとどまる。OpenNext for Cloudflare の文書によると、App Router で revalidatePath / revalidateTag を効かせるには Tag Cache の設定が要る。このアプリは既定の設定で Tag Cache を持たないため、サーバー側キャッシュを入れる場合は Tag Cache の設定と組にすることを条件にする。

#### 主たる接地根拠: `qa-r-backend-4`

**問**

backend の要件（書き込み API と鮮度の契約）は何か。（R1〜R3 の決定と実装に合わせた改訂版）

**答**

(1) 画面から呼ぶ書き込みを Server Functions（src/actions の 19 ファイル）へ移す。外部のエージェントが呼ぶ API（Bearer 鍵・端末の承認）、離脱時に送る利用記録（sendBeacon）、外観の選択の記録、認証、読むだけの検索・書き出しは Route Handler のまま残す。画面からしか呼ばれなくなった Route Handler は消し、書き込みの経路を二重にしない。 (2) Server Functions は共通の入口 runAction を通す。入口は、送り元の検査と認可（apiViewer）→ 大きさの上限（413）→ 入力の検証（zod）→ 本体 → 成功したときだけ next/cache の refresh、の順に行い、新しい画面を同じ応答に載せて {ok, message} の形で結果を返す（本番で例外の中身が隠れても、画面に理由を出せる）。読むだけの呼び出し（控えを開くなど）は runRead で受け、描き直さない。将来サーバー側にキャッシュを入れるときの無効化（revalidatePath・revalidateTag）の置き場もこの入口に持つ。 (3) 一つの操作で複数の表を書く書き込みは、次の 3 つの型のどれかで守る（D-003 案 A）。(a) 1 回の D1 batch に入るものは batch で書く（全部書けるか、何も書かれないか）。(b) batch に入りきらない会社の追加だけ、段階ごとの書き込みと取り消しの組で書き、途中で失敗したら逆順に取り消す（withCompensation）。取り消しも失敗したら compensation_failed を Workers Logs に残し、画面には失敗したことと管理者への連絡を出す。(c) 取り消せない認証ライブラリの書き込み（パスワードの変更）の続き（仮パスワードの印を外す・控えを消す）は 1 回の batch にし、失敗したら 1 回だけやり直して揃える（rollForward）。それでも失敗したら rollforward_failed を残し、画面には変更は済んだことと管理者への連絡を出す。batch の外で 2 つ以上の表を書く関数は、契約試験（write-atomicity-contract.test.ts）で見つけて落とす。 (4) 入口を通らない書き込み（画面側の書き込みの fetch、runAction を通らない Server Function、runRead の中での書き込み）を静的検査（server-actions-contract.test.ts）で見つけて落とす。例外（利用記録の sendBeacon・外観の選択の記録）は検査の中に理由付きで列挙する。新しい書き込みや画面を足すときも入口を使うことを、文書と検査で求める（I5・O4、G4）。

## To-Be / Delta

> 本章の**規範**。上位概念 (要件定義書 U3 ゴール / U4 目標 / U9 具体的やりたいこと) を本章の serves_goals で絞り込んだ射影であり、設計知識 card (非規範の参考資料) とは役割が異なる。As-Is (現行実装の姿) は spec-state.json の管轄外のため本節では断定せず、到達点と、その到達を判定する観測点だけを規範として置く。

### 到達すべき状態 (To-Be)

- **G1**: 書き込み成功を表示した時点で、同じタブの一覧・件数・ナビゲーション（会社切替など）がすべてその結果を含んでいる。
- **G2**: 通常・強制の再読み込みや URL の直接表示は、直前の書き込み結果を必ず含む。
- **G4**: 画面や書き込み API を追加しても、鮮度の保証が個別実装に頼らず共通契約として適用され、適用漏れは検査で落ちる。
- **G5**: 一つの操作で複数の表を書く書き込みが途中で失敗しても、一部だけ反映された中途状態（会社はあるが管理者が無い等）を残さない。取り消し・やり直しの処理まで失敗したときは、その事実が記録に残って検知でき、手作業で直せる。

### 受入条件 (Delta の判定点)

| 目標 | 到達点 | 達成の観測点 (measure) |
|---|---|---|
| O1 | 全ての作成・更新・削除フローで、成功表示と同じ描画のうちに一覧・件数へ反映する。 | 作成系 E2E で成功表示直後の DOM に新しい行と更新後の件数が含まれる（待機なし）。 |
| O2 | 書き込み直後の再読み込みで反映率 100%。 | 書き込み→強制再読み込みの E2E と、ローカル preview の再現スクリプトで新しい行が毎回含まれる。加えて、リリース後の本番で、作成の直後に ⌘+Shift+R をして新しい行が出ることと、応答の生成時刻ヘッダーが作成より後であることを確かめる（作成は利用者のふだんの操作で行い、エージェントは本番に書き込まない）。前提として、ゾーンに HTML・/api を保存するキャッシュ規則が無いことを読み取りだけで確かめる。 |
| O4 | 鮮度契約を通らない書き込み経路を 0 件にする。 | 静的検査が、共通の包みを通らない Server Function と、画面から書き込みの fetch を直接呼ぶ箇所を 0 件と報告する |
| O5 | 会社追加を含め、複数の表を書く書き込みが途中で失敗しても、一部だけが残る状態を 0 件にする。取り消し・やり直しまで失敗した場合は、記録が必ず残る。 | 会社の追加は、途中の段階を失敗させる結合テストで会社・制度ひな形・利用者・アカウントのどの行も残らないことを確かめ、取り消しも失敗させてログが出ることを確かめる。ほかの経路は、batch の外で2つ以上の表を書く関数が 0 件であることを契約テストで確かめ、CSV 取込と評価の集計は batch の途中で失敗させる結合テストでも確かめる。パスワード変更は、後片付けを2回とも失敗させる試験で、ログが出て「変更済み」と伝わることを確かめる。 |

### 本章がかなえる具体的やりたいこと (U9)

- **I1**: 書き込みを Server Functions の共通の包みにまとめ、成功したら同じ応答で今の画面を作り直す（next/cache の refresh）。他タブへの通知と、将来のキャッシュの無効化の置き場も、この包みと画面側の共通口に持たせ、全ての書き込み画面をそこへ寄せる。
- **I2**: 連続作成フォームで一覧の反映を最優先にし、控えをフォームの上に置き続けない。発行した初期パスワードの控えは暗号化して保存し、一覧の行から開き直せるようにする。
- **I4**: 1回の D1 batch に入る書き込みは batch で書く（利用者の発行・メンバー追加・期間・設問・制度設定・KGI 実績・改善要望の状態変更・端末の引き取り・利用状況など）。batch に入りきらない会社追加は、段階ごとの「書く処理」と「取り消す処理」の組（補償）で書く。戻せない認証ライブラリの書き込みの続きは、やり直して揃える。batch の外で2つ以上の表を書く関数は、契約テストで検出する。
- **I5**: 共通の包みを通らない書き込み経路を検出する静的検査と、4 経路の E2E を加える。
- **I6**: 応答に鮮度の手がかり（生成時刻）を載せ、反映されない報告を切り分けられるようにする。

- **D-003**: 一つの操作で複数の表を書く書き込み（会社追加を含む）で、途中の失敗による中途状態をどう防ぐか。
  - 採択: batch に入るものは batch、入りきらない会社追加は補償、戻せない書き込みの続きはやり直し (`opt-batch-first`)
  - 目的適合: 1回の batch に入る経路は G5 を保証する。会社追加は補償まで失敗したときだけ中途状態が残り得るが、記録が残り手順で直せる（改訂後の G5）。パスワード変更は、取り消せない書き込みの後をやり直して揃える。

### Clean Architecture — deep knowledge card

- 出典カード: `ref-system-design-knowledge/references/clean-architecture.md`

#### 目的

変化しやすいUI、DB、framework、外部サービスから、長く保持したい業務ルールとuse caseを隔離し、技術交換やテストを目的達成の阻害要因にしない。

#### 解決する問題

- 業務ルールがcontroller/ORM/UI lifecycleへ埋まり、単体で検証できない。
- 外部技術変更が内側のuse caseまで波及し、置換費用を予測できない。
- 入出力形式やvendor型が境界を越え、責務と所有者が曖昧になる。

#### 適用条件

- business ruleが外部I/Oより長寿命で、UI/DB/providerの変更可能性がある。
- 複数delivery channelや外部integrationから同じuse caseを再利用する。
- 重要なpolicyを高速・決定論的にテストする価値が、境界導入費を上回る。

#### 非適用条件

- 寿命の短い検証用prototypeで、交換可能性より学習速度が明確に優先される。
- domain ruleがほぼ無い単純変換scriptで、port/adapterが実質的な抽象を生まない。
- 外部製品そのものがsystemの目的で、抽象化すると必要機能が失われる。ただしsecurity/audit boundaryは別途必要。

#### トレードオフ・失敗モード

- 境界、DTO、mapping、dependency injectionの量が増え、小規模systemでは認知負荷が先行する。
- 「4層を作ること」が目的化すると、変化軸のないinterfaceやpass-through use caseが増える。
- domain modelを万能化してdelivery固有の制約を隠すと、現実のlatency/transaction/error semanticsを見失う。
- portを外側が定義したりinner layerがORM型を返したりすると、名前だけcleanな依存逆転になる。

#### goalへの寄与

- `essential_purpose`に直結するpolicyを外部詳細から守り、goal達成ロジックの検証を速くする。
- 制約に「vendor lock-in低減」「複数platform」「高い変更頻度」がある場合、変更範囲と移行riskを局所化する。
- 適用判断は「何層あるか」でなく、守るgoal、予想される変更、boundary testで観測する。

### API Design Patterns — deep knowledge card

- 出典カード: `ref-system-design-knowledge/references/api-design-patterns.md`

#### 目的

consumerとproviderの独立変更を支える安定した契約を作り、再試行、失敗、並行更新、pagination、evolutionを予測可能にする。

#### 解決する問題

- resource/operationの意味、error、null、time、identifierがendpointごとに揺れる。
- timeout後の再試行で二重処理が起き、clientが成功/失敗を判断できない。
- collection増大や並行更新でoffset paginationと全件responseが破綻する。
- version/evolution方針がなく、provider変更がconsumerを突然壊す。

#### 適用条件

- 複数client/team/organizationが独立releaseで同じservice boundaryを利用する。
- network failureとretryが通常事象で、operation結果の重複や不明状態を制御する必要がある。
- contractの長期互換性とobservabilityが局所的な実装簡潔性より重要。

#### 非適用条件

- 同一process内のprivate callで、network boundaryや独立versioningが存在しない。
- hard real-time stream、双方向session、巨大event flowなど、request/response RESTが問題形状に合わない。
- 単純CRUD表面化がdomain invariantを迂回させる場合。use-case operationまたは別interaction modelを選ぶ。

#### トレードオフ・失敗モード

- version、idempotency ledger、schema governance、compatibility testに運用費がかかる。
- 「名詞URL」だけ守ってtransaction、authorization、error semanticsを設計しない表層RESTになる。
- offset paginationは簡単だが大規模/更新中datasetで遅延・重複・欠落を起こす。
- idempotency keyのscope/TTL/payload bindingが曖昧だと、別requestを誤って同一視する。
- breaking changeを新versionで逃がし続けると、複数version保守とsecurity patch負担が増える。

#### goalへの寄与

- mobile/web/desktop間で一貫したbusiness capabilityを共有し、platform別再実装を減らす。
- reliability goalにはretry-safe operationと明示的error、delivery goalにはcontract testとadditive evolutionを結ぶ。
- 選択はAPI様式の流行でなく、consumer、latency、consistency、offline、security、cost constraintsへの適合で評価する。

### Domain-Driven Design — deep knowledge card

- 出典カード: `ref-system-design-knowledge/references/ddd.md`

#### 目的

businessの重要なruleと用語をmodel/code/会話で一致させ、複雑性を適切な境界へ閉じ込め、継続的な学習をsoftwareへ反映する。

#### 解決する問題

- 仕様語、画面語、DB列、code名がずれ、変更時に意味を再解釈する。
- 異なる業務文脈の同名概念を一modelへ押し込み、巨大で矛盾したmodelになる。
- invariantとtransaction ownerが不明で、どこからでもdataを変更できる。
- legacy codeのtechnical構造がbusiness capabilityを隠し、改善順を決められない。

#### 適用条件

- rule、例外、用語、状態遷移が多く、domain expertとの継続的なmodel学習が価値を持つ。
- team/部門ごとに言葉やownershipが異なり、integrationで翻訳が必要。
- core domainの差別化がsystemの本質的目的に直結する。

#### 非適用条件

- 単純CRUD、汎用supporting機能、既製serviceで十分なgeneric subdomain。
- domain expertへアクセスできず、用語とruleを検証するfeedback loopを作れない段階。
- bounded contextをservice数へ機械変換する目的。monolith内moduleでも境界は成立する。

#### トレードオフ・失敗モード

- workshop、model、mapping、専門語彙の維持に継続的な時間が必要。
- aggregateを大きくしすぎてlock/latencyを増やす、細かくしすぎてinvariantをeventual consistencyへ漏らす。
- 「Repository/Entity」等のpattern名だけ採用したanemic modelになり、business ruleがserviceへ散る。
- bounded contextを組織図やDB tableから決め、実際の言語・capability境界を検証しない。
- eventを事実でなくcommandとして命名し、ordering/idempotency/failure recoveryを設計しない。

#### goalへの寄与

- U1-U9の語彙をmodelへ接続し、goalがどのcontext/capability/invariantで実現されるかを示す。
- core domainへ設計投資を集中し、generic領域は無料/低コストserviceや標準実装も比較対象にできる。
- refactoringは一括rewriteでなく、重要なbusiness rule周辺からstrangler/bubble context等で境界を育てる。
