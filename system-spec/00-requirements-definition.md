## U1 本質的目的 (essential_purpose)

利用者が作成・変更・削除した結果を、成功表示の直後の画面・再読み込み・他のタブと画面復帰のどれでも必ず確認できるようにし、『本当に保存できたのか』を疑わずに次の作業へ進める状態をシステムとして保証する。あわせて、等級の呼び名・役割ごとにできること・各人の等級と評価・アンケートの提出状況・設定の足りない所を、どの画面でも同じ言葉で、見てよい人にだけ示し、利用者が『誰が何をできるか』『どこで何を直せばよいか』を迷わずに判断して操作できる状態にする。さらに、管理者・直属の上司・本人が、その人が評価に値するかどうか・点数・項目ごとの強みと弱み・過去の推移を、毎回同じ型で作られる個人別の評価レポートで一目で確かめられるようにする。そのために、アンケートの設問と回答・昇給の設定・KPI 評価セットが、同じ評価期間の定義で食い違わずにつながり、評価の結果がいつ作っても同じになる状態を保つ。使っていない事業所KGIの仕組みは残さない。評価に値するかの結論は、点数の判定だけで決めず、評価を確定する上司が理由とともに記録した判断を合わせて決め、その理由は本人にも同じ文で示す。さらに、設定（等級要件・行動指針・KPI・評価セット）とアンケートの設問のどちらを後から変えても、後から変えた方を正として、もう一方と、その写しを持つ全ての画面と機能が追従する状態を保つ（確定した評価と評価レポートは確定した時点のまま残す）。行動指針と KPI・評価セットの画面は、最初に見る量を判断に要るものだけに絞り、操作に応じて詳しい内容を開ける形にして、設定の作業の認知の負荷を下げる。

## U2 背景 (background)

2026-09-30 の報告で、会社追加の成功メッセージとパスワード控えが出ても会社一覧（6社）に新しい会社が現れず、再読み込み（⌘+Shift+R を含む）でも出ないまま、しばらく後に反映される事象が確認された。利用者登録・アンケート作成など新規作成の全機能で同様とされる。コード調査で、書き込み後の鮮度を保証する共通の仕組みが無く、34 ファイルが個別に useRefreshAfterSave（router.refresh）を呼ぶだけで、サーバー側の revalidatePath と Server Actions は 0 件だった。連続作成フォーム（RecordForm の generate 経路）では、控えを残すため refresh 自体が次の送信まで省略される。会社追加 API は会社・管理者・所属を別々に書き込み、途中失敗で中途状態が残り得る。2026-10-12 の依頼（画像9枚）で、次の問題が報告された。等級名が『等級１：Beginner』のように英語を含み、行動指針や評価セットでは『Regular』『Chief』などの区分名がそのまま出て、等級名とそろっていない。等級名を変えても、画面の文やボタンに反映されない所がある。役割ごとにどの画面で何ができるかを確かめる手段が無い。利用者一覧から、各人の等級と最新の評価を確かめられない。複数の会社に所属するマネージャーを、メールアドレスが登録済みのため2社目に登録できない。アンケートで誰が提出していないかが一覧で分からない画面がある。設定不足の警告が『Chief: 選んだ項目のうち1件の基準(A〜E)が未設定です。』のように、何をどこで直すかが分からない。並べ替えが矢印のボタンだけで、ドラッグできない。アンケートの選択肢を押しても選べない。評価期間などの画面で右側の余白が目立つ。コード調査で、等級名を表示用に整える共通の関数が無く、区分（pointGroup）の英語名が結合キーと表示を兼ねていること、users.email が一意で会社への所属を表す表が無いこと、警告が文字列だけで直す画面へのリンクを持たないこと、ドラッグ用の部品が無いこと、権限の一覧表がコードのどこにも無いことを確かめた。 2026-10-14 の依頼（画像1枚）で、アンケート一覧の警告が、どのページとどのページの内容が食い違っているかを示さず、たどれないことが報告された。同じ日の追加の指示で、警告の文が長く並んで読みにくいため、既定では出さずに押すと出す形にし、直すところを箇条書きや表で示すよう求められた。コード調査で、警告の型（SetupGap）がリンクを1本しか持てず、ズレの片側しか指せないこと、ズレがアンケート一覧にしか出ないこと、公開後のズレを直すには全等級の新しい版を作るしかないことを確かめた。 2026-10-19 の依頼（画像2枚：評価・結果を確認する画面とアンケートの画面）で、次のことが求められた。サイドバー『運用を補う』の『事業所KGIの達成率』は、仕組みが整っておらず当面使わないため、将来の再導入で競合しないよう完全に消す。昇給の設定とアンケートの回答を踏まえた個人別の評価レポートを、図やグラフ（評価に値するか・点数・三角形〜六角形のレーダー図・過去のその等級の点数・等級ごとの点数・過去の実績）で、再現性のあるテンプレートに沿って毎回作れるようにする。担当者と権限のある人が、部下の評価結果の中身を見られるようにする。全項目を確かめられるテストデータを入れる。アンケートの全機能（URL・回答・回答一覧・内容の確認と編集・締め切る・評価項目とのズレの直すところ）を確かめ、アンケート・昇給の設定・KPI 評価セットの依存関係を整える。コード調査で次を確かめた。KGI は賞与（仮）の計算（個人Pt＝KPI評価点の合計×KGI係数）と一体で、3つの表と評価の表の2列を持つ。本番の Deploy はマイグレーションをコードより先に当てる。個人別のレポートの画面は無い。シードは受付中の評価期間の評価を作らず、評価結果の中身を確かめられない。CSV の書き出しはマネージャーにも会社の全員分を返し、管理者向けのメモがマネージャーに見える。評価項目とのズレは KPI 項目だけを比べ、等級要件と行動指針を比べず、項目ごとの直すリンクが無い。下書きの新しい版がズレていなければ、回答を集めている公開中の古い版の警告が消える。ズレを比べる評価セット（会社の有効なもの）と、アンケートを作る・点数を計算する評価セット（評価期間に指定したもの）が別々に決まる。アンケートの状態の変更（締切済みから公開中など）をサーバーで止めていない。古い版を締め切る処理と版の番号を決める処理が会社で絞っていない。締め切ったアンケートの延長で、画面に無い操作を案内する。 同日の追加の依頼で、個人別の評価レポートを A4 で印刷できるようにすることが明示された。 さらに同じ作業の途中で、昇給・昇格を点数の判定だけで決めず、上司のコメントと判断（例：アンケートの基準は満たしているが上げない）を合わせて決め、それをレポートとして本人・上司・管理者に渡せるようにすることが求められた。コード調査で、昇給と昇格の可否は点数で自動に決まり、上司のコメントの欄は判定に効かず、上司が止めるには項目の実績値を書き換えるしかないことを確かめた。 2026-10-22 の依頼（画像5枚：行動指針、KPI・評価セットの入口、KPI 項目の一覧、アンケートと評価項目のズレの表、評価・結果を確認する）で、次が求められた。行動指針の分け方の既定を、等級1・2で1つ、等級3・4-1・4-2で1つ、等級5-1・5-2は出さない形にする（呼び名は会社ごとに変わるが、考え方は同じ）。行動指針と KPI・評価セットの画面の認知の負荷を下げる（最初は少なく見せて操作に応じて出す、等級ごとの表示を境界のはっきりしたカードやブロックにする、KPI 項目の文の長さと改行を整える、1画面に並ぶ複数の作業を分ける）。後から設定した方を正とし、設定とアンケートのどちらを後から直しても他の画面へ反映することを、全ての画面と機能で行う。評価を作る画面を試すため、提出済みの回答を含む仮のデータを作る。カードとボタンのグラデーションなど、共通部品の見た目を華やかにする。コード調査で次を確かめた。画像の行動指針は、等級1だけが等級3〜4-2のまとまりへ移った状態（製品仕様 §28-12 と DD-010 に記録された本番の状態）で、「行動指針の初期設定について」の文はいまの割り当てを読まずに既定の形を示す。設定とアンケートは設定からアンケートへの一方向の写しで、反映は回答0件の下書きの作り直しと新しい版を作る操作の2つだけ。アンケートから設定へ戻す経路は無く、下書きに設定とつながった設問を新しく足すこともできない。評価セットの保存は、等級区分ごとの項目数・固定枠・20点枠をサーバーで検査する。行動指針と KPI・評価セットの入口は、説明と警告と最大7つの作業を1画面に並べ、KPI 項目の一覧は、聞くことと計算式を全角空白でつないだ1行で出す。本番の見本の会社は5期すべて締め済みで、提出済みの回答のある受付中の期を持たない。グラデーションは見出しの面の微グラデ1か所だけで、色は意味のトークンと契約テストで固定されている。

## U3 ゴール (goals)

| ID | ゴール |
|---|---|
| G1 | 書き込み成功を表示した時点で、同じタブの一覧・件数・ナビゲーション（会社切替など）がすべてその結果を含んでいる。 |
| G2 | 通常・強制の再読み込みや URL の直接表示は、直前の書き込み結果を必ず含む。 |
| G3 | 同じ利用者の他のタブや、スマホ・タブレットでの画面復帰（bfcache 復元・タブ復帰）でも、古い一覧のまま操作を続けない。 |
| G4 | 画面や書き込み API を追加しても、鮮度の保証が個別実装に頼らず共通契約として適用され、適用漏れは検査で落ちる。 |
| G5 | 一つの操作で複数の表を書く書き込みが途中で失敗しても、一部だけ反映された中途状態（会社はあるが管理者が無い等）を残さない。取り消し・やり直しの処理まで失敗したときは、その事実が記録に残って検知でき、手作業で直せる。 |
| G6 | 等級の呼び名は、その会社の等級名だけで表す。行動指針の向け先・評価セットの区分・昇格の要件・警告文・アンケートのタイトル・ボタンのどこにも英語の区分名を出さず、等級名を変えると次の表示からすべてに反映される。 |
| G7 | 等級名を変えられるのは、システム全体管理者と、その会社の会社管理者だけにする。マネージャーと一般の社員、他社の会社管理者は、画面からもサーバー処理からも変えられない。 |
| G8 | 役割ごとに、どのページを開けて、そこで何ができ何ができないかを、ページ名を単位にした同じ形で確かめられる。表示は実際の権限の判定と食い違わない。 |
| G9 | マネージャー・会社の管理者・システム全体管理者は、見てよい範囲の利用者について、今の等級と、確定した最新の評価の KPI評価点と等級要件の達成率を一覧で確かめられる。一般の社員には見えない。 |
| G10 | 同じメールアドレスの人が、1つのアカウントのまま複数の会社に所属でき、会社ごとの役割・等級・上司で使える。所属していない会社のデータは見えない。 |
| G11 | アンケートごとに、対象者の誰が提出済みで、誰が入力途中か未回答かを一覧で確かめられる。 |
| G12 | 設定の不足を知らせる表示は、何が足りないか・どう直すか・どこで直すかを短く示し、そこから直す画面へ1回の操作で移れる。 |
| G13 | 並び順を持つ全ての編集画面で、矢印のボタンに加えて、長押ししたままのドラッグとキーボードでも並べ替えられる。 |
| G14 | アンケートの選択肢を押しても何も起きない画面を無くす。見本として表示している画面では、見本であることと回答できない理由が分かる。 |
| G15 | 画面の幅に対して内容が片側に寄り、右側の余白が目立つ画面を無くす。 |
| G16 | 2つのページの内容を比べて出す警告は、比べている両方のページを階層つきのページ名とリンクで示し、項目ごとにどちらのページにあってどちらに無いかを表で示す。既定ではズレがあることと件数だけを1行で出し、中身は押すと開く。どちらのページから見ても、相手のページへ1回の操作で移れる。 |
| G17 | 事業所KGIの達成率の仕組み（メニュー・画面・計算・保存・表・列・文書・テスト）を残さず消す。賞与（仮）は KGI を使わない式（個人Pt＝KPI評価点の合計、賞与額＝個人Pt×昇給の設定の1点あたりの円）で出し続ける。 |
| G18 | 個人別の評価レポートを、開くたびに確定した評価から同じテンプレートで作る。評価に値するか（昇給と昇格の判定とその理由）・点数・項目ごとのレーダー図・その等級にいた期の点数と同じ等級の平均・等級ごとの点数・過去の実績を、図とグラフで一目で分かるように示す。 |
| G19 | レポートと評価結果の中身を、見てよい人にだけ見せる。全体管理者と会社の管理者は会社の全員、マネージャーは直属の部下と自分、本人は自分の分を見られる。本人向けは点数の数値と他の人との比較を出さない。範囲の外のデータは、CSV の書き出しとメモを含めてサーバーが返さない。 |
| G20 | 全ての画面と項目（評価結果の中身・レポートの全ての図・アンケートの各状態・ズレの各種類・役割ごとの見え方）を、ローカルと E2E で確かめられるテストデータを用意する。本番には入れない。 |
| G21 | アンケートの配布 URL・回答・回答一覧・内容の確認と編集・公開・締め切る・延長が、アンケートの状態と締切に合った操作と案内だけを出し、サーバーも同じ規則で守る。 |
| G22 | 評価項目とアンケートのズレを、KPI 項目・等級要件・行動指針の全てで比べ、項目ごとに直す画面へのリンクを出す。新しい版が下書きの間は、回答を集めている古い版の警告を消さない（今の設定と一致した新しい版を公開して古い版が締め切られたら出さない）。 |
| G23 | アンケートの設問と回答・昇給の設定・KPI 評価セット・評価の結果を、評価期間に指定した評価セットを基準につなぎ、ズレの比較・アンケートの作成・点数の計算・レポートの作成が同じ定義を使う。つながりの抜けを1か所で確かめられる。 |
| G24 | 昇給と昇格の可否を、点数の判定と、評価を確定する上司が理由とともに記録した判断（点数の判定どおり／変える）を合わせて決め、その結論と理由を、評価レポート・画面・CSV で本人・直属の上司・管理者に同じ形で示す。点数の判定は書き換えずに残す。 |
| G25 | 行動指針の分け方の既定（等級1・2で1つ、等級3・4-1・4-2で1つ、等級5-1・5-2は出さない。呼び名を変えた会社でも、等級の内部の識別子で同じ分け方にする）を、新しい会社と、既定からずれた既存の会社の両方で成り立たせる。画面の初期設定の説明は、いまの割り当てを読んで示す。 |
| G26 | 行動指針と KPI・評価セットの画面を、最初は判断に要る状態・件数・次にやることだけを見せ、操作に応じて詳しい説明と編集を開く形にする（情報は消さず、見せ方を変える）。KPI・評価セットは作業ごとに画面を分け、等級区分ごとの設定を境界のはっきりしたカードで示し、KPI 項目を読みやすい区切りで示す。 |
| G27 | 設定（等級要件・行動指針・KPI・評価セット）とアンケートの設問のどちらを後から変えても、後から変えた方を正として、もう一方と、その写しを持つ全ての画面と機能が追従する。確定した評価と評価レポートは確定した時点のまま残し、確定前の評価だけが最新に追従する。 |
| G28 | 評価・結果を確認する画面で「提出済みの回答から評価を作る」を試せるよう、提出済みの回答を含む受付中の評価期間の仮のデータ（氏名は実在しない「サンプル」など）を、手元の見本と本番の見本の会社の両方に用意する。 |
| G29 | ボタンだけでなく、カード・見出しの面・選ぶ部品・状態の印・進み具合・数の面・知らせ・表・いまいる場所の印など、全ての画面の共通部品に、いまのテーマの変数から作る、はっきりしたグラデーションと色の変化を持たせ、押した・選んだ・開いたが分かる手応えと、主の操作が一目で分かる強弱をそろえる。全ての系統・明暗・コントラストを強くする設定・印刷で読みやすさを保つ。平賀配色へは移さない。 |

## U4 目標 (objectives)

| ID | 目標 | 測定基準 |

## U5 成功基準 (success_criteria)

- 会社追加の直後に、会社一覧・件数・会社切替メニューへ新しい会社が出る（連続作成で控えを表示したままでも出る）。
- 利用者登録・メンバー追加・アンケート作成など全作成フローで、同じ条件を満たす。
- 書き込み直後の強制再読み込み・直接 URL 表示で結果が見える。
- 別タブ・スマホのタブ復帰で古い一覧が残らない。
- 会社追加を含め、一つの操作で複数の表を書く書き込みが途中で失敗したとき、一部だけが残らない（会社だけ・管理者だけが残らない、を含む）。1回の D1 batch で書く経路は何も書かれず、会社の追加は書いた行を取り消し、取り消せない書き込みの続き（パスワード変更の後片付け）はやり直して揃える。取り消し・やり直しまで失敗した場合は Workers Logs に記録が残り、文書の手順で手作業で直せる。
- pnpm test と pnpm run check:docs が通り、鮮度の静的検査が 0 件で通る。
- 等級名を『等級4-1』の形に変えると、行動指針・評価セット・昇格の要件・警告・アンケートのタイトル・ボタンのすべてが同じ名前で表示される。新しい会社の既定の等級名に、英語や『ビギナー』などの呼び名が入らない。既存の会社の等級名も同じ形にそろっている。
- 等級名を変えられるのは、システム全体管理者と自社の会社管理者だけである。
- 『システムを管理する』に権限一覧のページがあり、利用者一覧ではボタンでモーダルの権限一覧を開ける。各項目にポインターを載せる・フォーカスする・タップすると、作業の概要が出る。
- マネージャー・会社の管理者・システム全体管理者の一覧で、各人の今の等級と、確定した最新の評価の KPI評価点と達成率が見える。一般の社員には見えない。
- 登録済みのメールアドレスの人を別の会社にも登録でき、会社を切り替えて使える。
- アンケートの一覧と回答一覧から、誰が提出済み・未提出かが分かる。
- 設定不足の表示から、リンクで直す画面へ移れ、何をどう直すかが短く書かれている。
- 『Claude Code連携の鍵』の画面名が『Claude Code連携（システム開発者専用）』になっている。
- 並べ替えを、長押ししたままのドラッグでも行える。
- アンケートの回答と見本で、選択肢を押すと選ばれる。
- 評価期間などの画面で、右側の余白が目立たない。
- ズレの警告から、比べている両方のページへ、ページ名を見て1回の操作で移れる。
- ズレの警告は既定で1行に収まり、押すと直すところが表で出る。
- サイドバーとどの画面にも『事業所KGIの達成率』が無く、KGI の表と列が本番 DB に無い。評価の画面の賞与（仮）は、KPI評価点の合計から計算されている。

- マネージャーは直属の部下の評価結果の中身とレポートを見られ、部下でない人のものは見られない（CSV とメモを含む）。

- 行動指針と KPI・評価セットの画面を開いた直後は、状態と次にやることだけが見え、詳しい説明と編集は開いたときに出る。KPI・評価セットの作業は、それぞれ別の画面で行える。
- 下書きのアンケートで設定とつながった設問を変えて保存すると、元の設定と、同じ設定を使う画面が同じ内容になる。評価セットの決まりに合わなくなる保存は、理由と直す画面とともに断られる。
- 設定を変えると、回答の無い下書きは作り直され、回答のある公開中のアンケートには次の版の下書きができ、確定前の評価は集計し直される。確定した評価と評価レポートは変わらない。
- 手元と本番の見本の会社で、提出済みの回答から評価を作り、評価の一覧と詳細まで確かめられる。
- ボタン・カード・見出し・選ぶ部品・状態の印・進み具合・数の面・知らせ・表・いまいる場所の印の全てにグラデーションと色の変化と押した・選んだ・開いたの手応えが付き、既存のテーマの契約テストが書き換えなしで通り、グラデーションのコントラストと focus-visible の検査も全ての系統と明暗で通る。

## U6 ステークホルダー (stakeholders)

- システム管理者: 会社追加・利用者登録の直後に結果を確かめ、控えを管理者へ渡す。
- 会社管理者: メンバー追加・アンケートや評価セットの作成・制度設定の直後に一覧を確かめる。
- 評価者・被評価者: 評価入力や回答の保存結果を確かめる。
- 開発・運用担当: 反映されないという報告の切り分けと、新しい画面での鮮度保証の維持を担う。
- 等級名を管理する人（システム全体管理者と会社の管理者）: 会社の等級名を決め、全画面の呼び名をそろえる。
- 複数の会社に所属する人（マネージャーなど）: 1つのアカウントで会社を切り替えて使う。
- 直属の上司（マネージャー）: 部下の評価結果の中身とレポートを見て、面談と評価の確定に使う。評価の確定のときに、昇給と昇格の判断と理由を記録する。
- 被評価者（本人）: 自分のレポートで、判定と過去の推移を確かめる。

## U8 制約 (constraints)

- Next.js 16 系（App Router。脆弱性の修正を含む 16.3.8 へ上げる）・OpenNext Cloudflare 1.20 系・Cloudflare Workers・D1・better-auth の構成を変えない。
- 本番 DB は読み取り専用で調べる。外部への変更系通信は preview → CONFIRM → authorize → execute のガードを通す。
- PR は実装後、作る前に必ず利用者の確認を取る。
- 平賀配色へ移行しない。テーマの契約テスト・T2-experience-spec.md §5・globals.css 冒頭の brand_color_* を書き換えない。
- 公開リポジトリのため、文書や見本に実データ（社員名・評価値など）を入れない。
- 1回の D1 batch に入るものは batch で書く。batch に入りきらないもの（今は会社の追加だけ）は、書いた行を逆順に消す処理（補償）で守る。認証ライブラリが先に書くもの（今はパスワード変更だけ）は戻せないので、続きの batch を1回やり直し、それでも失敗したら記録を残す。新しく足す書き込みも、まず batch に入るかを確かめる（D-003）。
- 区分（pointGroup）は結合キーとして値を変えず、画面に出す呼び名だけを等級名から作る。
- 本番の等級名の書き換えはマイグレーションで行い、書き換え前の値を記録に残す。
- 役割による表示の制限は、画面で隠すだけにせず、サーバーが返すデータの段階で行う。
- 並べ替えは、ドラッグだけに頼らず、矢印のボタンとキーボードでも同じ操作ができるようにする。
- ポインターを載せたときだけ出る情報を作らない。同じ情報をフォーカスとタップでも出す。
- 警告のリンク先は、ルート台帳にあり、見ている人の役割で開けるページに限る。
- 警告を畳むときも、ズレがあることと件数は畳まずに出す（仕様 §22-2・§22-4）。
- KGI の削除は2回に分けて出す。1回目でコードから KGI の読み書きを全て外し、2回目でマイグレーションで3つの表と評価の2列を消す（本番の Deploy はマイグレーションをコードより先に当てるため）。消す前の値は Deploy の自動バックアップ（GitHub の Artifact。保管14日）に残り、14日を過ぎると戻せない。
- レポートは保存した写しを持たず、開くたびに確定済みの評価から作る。同じ入力から同じ出力になるよう、並び順・丸め・期の選び方を固定し、作った時刻と元にした評価期間を載せる。
- 同じ等級の平均は、同じ会社の確定済みの評価だけから作り、人数が3人未満なら出さない。本人向けには出さない。
- マネージャーが見られる範囲は、直属の部下（所属の上司が本人）と自分に限る。見える範囲は画面で隠すだけにせず、サーバーが返すデータの段階で絞る。
- テストデータには実在の人名・評価値を使わない（公開リポジトリ）。本番の設定ではシードを動かさない。
- 図は既存の recharts で描き、新しい依存を足さない。色は今のテーマの変数から取り、平賀配色への移行はしない。
- 上司の判断の理由は本人にもそのまま見えるので、性格ではなく行動や事実で書くよう画面で促す。
- 点数の判定（raiseEligible・promotionEligible と理由の文）は上司の判断で書き換えない。判定を変えるためだけに項目の実績値を上書きしなくて済むようにする。
- 行動指針の既定への書き換えは等級の内部の識別子で決め、呼び名では決めない。書き換えるのは割り当てだけで、観点の文と会社が足した観点は書き換えない。DD-010 を改める DD を書く。
- アンケートから設定への反映も、設定の保存と同じ権限（会社の管理者以上）・会社の絞り込み・同時に保存したときの 409・制度の変更の記録を通し、評価セットの決まりの検査を画面に頼らずサーバーで行う。
- グラデーションは globals.css の部品クラスに既存のトークンと color-mix だけで書き、TSX に色を書かない。テーマの契約テストと globals.css 冒頭の宣言を書き換えない。文字はグラデーションの両端で 4.5:1 以上にし、動きは prefers-reduced-motion で止め、印刷・使えない状態・コントラストを強くする設定では平らな面にする。
- 仮のデータは実在しない氏名と見本の会社だけで作り、INSERT と見本の会社に紐づく行の削除だけにする。本番への投入は、実行の前に利用者の確認を取る。
- アンケートから設定への反映（I28）と、設定の保存での下書きの作り直し（I29）は、DD-015（新しい設問を KPI 項目に紐づけず、紐づけは作り直しのときにだけサーバーが書く）と、DD-016 が却下した「聞き方の保存で下書きを書き換える」を改める。DD-015・DD-016 を改める DD を書いてから実装し、公開の前の検査（staleAskingItems）は残す。
