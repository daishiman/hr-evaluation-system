## U1 本質的目的 (essential_purpose)

利用者が作成・変更・削除した結果を、成功表示の直後の画面・再読み込み・他のタブと画面復帰のどれでも必ず確認できるようにし、『本当に保存できたのか』を疑わずに次の作業へ進める状態をシステムとして保証する。

## U2 背景 (background)

2026-09-30 の報告で、会社追加の成功メッセージとパスワード控えが出ても会社一覧（6社）に新しい会社が現れず、再読み込み（⌘+Shift+R を含む）でも出ないまま、しばらく後に反映される事象が確認された。利用者登録・アンケート作成など新規作成の全機能で同様とされる。コード調査で、書き込み後の鮮度を保証する共通の仕組みが無く、34 ファイルが個別に useRefreshAfterSave（router.refresh）を呼ぶだけで、サーバー側の revalidatePath と Server Actions は 0 件だった。連続作成フォーム（RecordForm の generate 経路）では、控えを残すため refresh 自体が次の送信まで省略される。会社追加 API は会社・管理者・所属を別々に書き込み、途中失敗で中途状態が残り得る。

## U3 ゴール (goals)

| ID | ゴール |
|---|---|
| G1 | 書き込み成功を表示した時点で、同じタブの一覧・件数・ナビゲーション（会社切替など）がすべてその結果を含んでいる。 |
| G2 | 通常・強制の再読み込みや URL の直接表示は、直前の書き込み結果を必ず含む。 |
| G3 | 同じ利用者の他のタブや、スマホ・タブレットでの画面復帰（bfcache 復元・タブ復帰）でも、古い一覧のまま操作を続けない。 |
| G4 | 画面や書き込み API を追加しても、鮮度の保証が個別実装に頼らず共通契約として適用され、適用漏れは検査で落ちる。 |
| G5 | 一つの操作で複数の表を書く書き込みが途中で失敗しても、一部だけ反映された中途状態（会社はあるが管理者が無い等）を残さない。取り消し・やり直しの処理まで失敗したときは、その事実が記録に残って検知でき、手作業で直せる。 |

## U4 目標 (objectives)

| ID | 目標 | 測定基準 |
|---|---|---|
| O1 | 全ての作成・更新・削除フローで、成功表示と同じ描画のうちに一覧・件数へ反映する。 | 作成系 E2E で成功表示直後の DOM に新しい行と更新後の件数が含まれる（待機なし）。 |
| O2 | 書き込み直後の再読み込みで反映率 100%。 | 書き込み→強制再読み込みの E2E と、ローカル preview の再現スクリプトで新しい行が毎回含まれる。加えて、リリース後の本番で、作成の直後に ⌘+Shift+R をして新しい行が出ることと、応答の生成時刻ヘッダーが作成より後であることを確かめる（作成は利用者のふだんの操作で行い、エージェントは本番に書き込まない）。前提として、ゾーンに HTML・/api を保存するキャッシュ規則が無いことを読み取りだけで確かめる。 |
| O3 | 他タブは通知受信またはタブ復帰から 1 秒以内に最新化する。 | 2 タブ E2E で、片方の書き込み後にもう片方が 1 秒以内に新しい行を表示する。 |
| O4 | 鮮度契約を通らない書き込み経路を 0 件にする。 | 静的検査が、共通の包みを通らない Server Function と、画面から書き込みの fetch を直接呼ぶ箇所を 0 件と報告する |
| O5 | 会社追加を含め、複数の表を書く書き込みが途中で失敗しても、一部だけが残る状態を 0 件にする。取り消し・やり直しまで失敗した場合は、記録が必ず残る。 | 会社の追加は、途中の段階を失敗させる結合テストで会社・制度ひな形・利用者・アカウントのどの行も残らないことを確かめ、取り消しも失敗させてログが出ることを確かめる。ほかの経路は、batch の外で2つ以上の表を書く関数が 0 件であることを契約テストで確かめ、CSV 取込と評価の集計は batch の途中で失敗させる結合テストでも確かめる。パスワード変更は、後片付けを2回とも失敗させる試験で、ログが出て「変更済み」と伝わることを確かめる。 |

## U5 成功基準 (success_criteria)

- 会社追加の直後に、会社一覧・件数・会社切替メニューへ新しい会社が出る（連続作成で控えを表示したままでも出る）。
- 利用者登録・メンバー追加・アンケート作成など全作成フローで、同じ条件を満たす。
- 書き込み直後の強制再読み込み・直接 URL 表示で結果が見える。
- 別タブ・スマホのタブ復帰で古い一覧が残らない。
- 会社追加を含め、一つの操作で複数の表を書く書き込みが途中で失敗したとき、一部だけが残らない（会社だけ・管理者だけが残らない、を含む）。1回の D1 batch で書く経路は何も書かれず、会社の追加は書いた行を取り消し、取り消せない書き込みの続き（パスワード変更の後片付け）はやり直して揃える。取り消し・やり直しまで失敗した場合は Workers Logs に記録が残り、文書の手順で手作業で直せる。
- pnpm test と pnpm run check:docs が通り、鮮度の静的検査が 0 件で通る。

## U6 ステークホルダー (stakeholders)

- システム管理者: 会社追加・利用者登録の直後に結果を確かめ、控えを管理者へ渡す。
- 会社管理者: メンバー追加・アンケートや評価セットの作成・制度設定の直後に一覧を確かめる。
- 評価者・被評価者: 評価入力や回答の保存結果を確かめる。
- 開発・運用担当: 反映されないという報告の切り分けと、新しい画面での鮮度保証の維持を担う。

## U7 スコープ (scope)

- **対象 (in)**: 全ての作成・更新・削除（会社・利用者・メンバー・アンケート・評価セット/期間・制度設定・CSV 取込・改善要望など）の後の表示鮮度, 同じタブ・再読み込み・他のタブ・画面復帰の 4 経路, 一つの操作で複数の表を書く全ての書き込みを、途中で失敗しても一部だけが残らないようにすること（1回の D1 batch にまとめる。batch に入りきらない会社の追加は取り消しの処理で、取り消せない書き込みの続きはやり直しで守る）, 鮮度契約の静的検査と E2E、反映されない報告の切り分け手段
- **対象外 (out)**: 別の利用者が開いている画面への即時配信（WebSocket 等の push）。別の利用者も次の画面遷移・再読み込みで最新を見られることは G2 で保証する, オフライン編集と同期, 配色・テーマの変更（AGENTS.md と DD-003 により対象外）, 本番データの移行・修正

## U8 制約 (constraints)

- Next.js 16 系（App Router。脆弱性の修正を含む 16.3.8 へ上げる）・OpenNext Cloudflare 1.20 系・Cloudflare Workers・D1・better-auth の構成を変えない。
- 本番 DB は読み取り専用で調べる。外部への変更系通信は preview → CONFIRM → authorize → execute のガードを通す。
- PR は実装後、作る前に必ず利用者の確認を取る。
- 平賀配色へ移行しない。テーマの契約テスト・T2-experience-spec.md §5・globals.css 冒頭の brand_color_* を書き換えない。
- 公開リポジトリのため、文書や見本に実データ（社員名・評価値など）を入れない。
- 1回の D1 batch に入るものは batch で書く。batch に入りきらないもの（今は会社の追加だけ）は、書いた行を逆順に消す処理（補償）で守る。認証ライブラリが先に書くもの（今はパスワード変更だけ）は戻せないので、続きの batch を1回やり直し、それでも失敗したら記録を残す。新しく足す書き込みも、まず batch に入るかを確かめる（D-003）。

| I6 | 応答に鮮度の手がかり（生成時刻）を載せ、反映されない報告を切り分けられるようにする。 | G2 |
