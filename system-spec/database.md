- **I12**: アンケートの一覧と、マネージャーの評価・結果の画面に、提出済み・入力途中・未回答の人の一覧を出す。
- **I14**: 並べ替えを共通の部品にし、長押しのドラッグ・矢印・キーボードで動かせるようにする。保存には、並び順の全体を送る形を足す。

### 本章に効く確定意思決定

- **D-003**: 一つの操作で複数の表を書く書き込み（会社追加を含む）で、途中の失敗による中途状態をどう防ぐか。
  - 採択: batch に入るものは batch、入りきらない会社追加は補償、戻せない書き込みの続きはやり直し (`opt-batch-first`)
  - 目的適合: 1回の batch に入る経路は G5 を保証する。会社追加は補償まで失敗したときだけ中途状態が残り得るが、記録が残り手順で直せる（改訂後の G5）。パスワード変更は、取り消せない書き込みの後をやり直して揃える。
- **D-004**: 1つのアカウント（メールアドレス）のまま複数の会社に所属し、会社ごとの役割・等級・上司で使えるようにするとき、所属と『選んでいる会社』をどこに持つか。
  - 採択: 自前の所属の表を作り、選んでいる会社を cookie（hr_company）で持つ (`opt-membership-cookie`)
  - 目的適合: 会社ごとの役割・等級・上長を所属の表に持てるので、G10 を満たす。
- **D-005**: 並び順を持つ編集画面で、長押ししたままのドラッグによる並べ替えを何で作るか。
  - 採択: Pointer Events で共通の hook を自作する (`opt-pointer-hook`)
  - 目的適合: 長押しの時間やスクロールとの区別を要件どおりに作れるので、G13 を満たせる。キーボードと矢印のボタンも同じ部品に入れる。
- **D-006**: 権限一覧（役割ごとに、どのページを開けて、そこで何ができるか）を、システム管理のページと利用者一覧のモーダルでどう見せるか。
  - 採択: 1つの表に役割のタブでの絞り込みを足し、スマホの幅ではページごとのカードに切り替える（①②③の組み合わせ。利用者の回答から足した案） (`opt-combined`)
  - 目的適合: 役割の違いを表で比べ、タブで1つの役割だけに絞り、スマホではカードで縦に読めるので、ページ名を単位にした同じ形で G8 を満たせる。
- **D-007**: 権限の定義（各ページでできる操作と、その説明）をどこに置くか。
  - 採択: route-ledger.json に操作と説明を足す (`opt-route-ledger-extend`)
  - 目的適合: ページの可否・操作・説明が1つの台帳に揃い、表示が判定と食い違わないという G8 を満たせる。

## 適用された設計知識

> 以下の deep knowledge card は設計判断を支援する**非規範の参考資料**であり、実装済み・検証済みの証拠ではない。カード内の `採否: applied` は設計採用を意味し、実装状態は意味しない。規範となる差分は本章の To-Be / Delta 節と参照先仕様で管理する。

### 本章での適用

DDD の集約境界を会社追加に当てはめた。会社・制度ひな形の複製・管理者の利用者・ログイン用アカウント・所属・控えは、『会社を追加したら全部そろって存在する』という一つの不変条件（qa-f02）を持つ一つの集約として扱う。D1 は対話的なトランザクションを持たず、ひな形の複製が数百行になりうるため、この集約は 1 回の batch に入らない。そこで書き込みを 3 段階に分け、各段階に取り消しを組にして、途中で失敗したら逆順に消す（qa-r-database-3 (1)、D-003 の opt-batch-first）。集約の外にある他社の行には触れず、companyId を会社境界として保つ。ほかの複数の表を書く経路は、操作ごとの不変条件が 1 回の batch に収まるので batch で書き、取り消しの組を増やさない（同 (2)）。制度マスタの監査記録は実体ごとの番号を一意にし、同時保存の後のほうを丸ごと失敗させる（同 (6)）。 （2026-10-13 追記：G6〜G15）DDD の集約境界を所属に当てはめた。会社ごとの役割・等級・事業所・上司は『利用者と会社の組』という所属の集約が持ち、users に残っていた会社ごとの列は所属を正として、移行で既存の利用者全員に1件ずつ作る（qa-v26 (1)、D-004）。等級の呼び名は、等級の名前という一つの値から導く派生値として扱い、行動指針のセット名やアンケートの既定のタイトルに写しを保存しない（同 (4)）。等級名の一律の書き換えでは結合キーの pointGroup と id を不変条件として保ち、表示名だけを変える（同 (3)）。一覧の等級と点数も確定した評価から読み、写しの列を作らない（同 (5)）。権限の定義は業務データではなく仕様の台帳（route-ledger.json）の定義なので DB に持たない（同 (9)、D-007 ①）。

### Domain-Driven Design — deep knowledge card

- 出典カード: `ref-system-design-knowledge/references/ddd.md`

#### 目的

businessの重要なruleと用語をmodel/code/会話で一致させ、複雑性を適切な境界へ閉じ込め、継続的な学習をsoftwareへ反映する。

#### 解決する問題

- 仕様語、画面語、DB列、code名がずれ、変更時に意味を再解釈する。
- 異なる業務文脈の同名概念を一modelへ押し込み、巨大で矛盾したmodelになる。
- invariantとtransaction ownerが不明で、どこからでもdataを変更できる。
- legacy codeのtechnical構造がbusiness capabilityを隠し、改善順を決められない。

#### 適用条件

- rule、例外、用語、状態遷移が多く、domain expertとの継続的なmodel学習が価値を持つ。
- team/部門ごとに言葉やownershipが異なり、integrationで翻訳が必要。
- core domainの差別化がsystemの本質的目的に直結する。

#### 非適用条件

- 単純CRUD、汎用supporting機能、既製serviceで十分なgeneric subdomain。
- domain expertへアクセスできず、用語とruleを検証するfeedback loopを作れない段階。
- bounded contextをservice数へ機械変換する目的。monolith内moduleでも境界は成立する。

#### トレードオフ・失敗モード

- workshop、model、mapping、専門語彙の維持に継続的な時間が必要。
- aggregateを大きくしすぎてlock/latencyを増やす、細かくしすぎてinvariantをeventual consistencyへ漏らす。
- 「Repository/Entity」等のpattern名だけ採用したanemic modelになり、business ruleがserviceへ散る。
- bounded contextを組織図やDB tableから決め、実際の言語・capability境界を検証しない。
- eventを事実でなくcommandとして命名し、ordering/idempotency/failure recoveryを設計しない。

#### goalへの寄与

- U1-U9の語彙をmodelへ接続し、goalがどのcontext/capability/invariantで実現されるかを示す。
- core domainへ設計投資を集中し、generic領域は無料/低コストserviceや標準実装も比較対象にできる。
- refactoringは一括rewriteでなく、重要なbusiness rule周辺からstrangler/bubble context等で境界を育てる。
