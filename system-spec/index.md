次の仕様は、下の「要件定義書」と「章一覧と集約状態」にある。

- 書き込み後の表示鮮度（作成・変更・削除の結果がすぐ見えること）
- 等級の呼び名・役割ごとにできること・提出状況・設定の足りない所を、どの画面でも同じ言葉で示すこと
- 個人別の評価レポート（毎回同じ型・A4 縦2枚組で印刷）と、昇給・昇格への上司の判断（点数の判定と、判断と理由）
- レポートと評価結果を見てよい人の範囲（CSV の書き出しとメモを含む）
- 事業所の達成率の削除、全画面を確かめるテストデータ、アンケート・昇給の設定・KPI 評価セットのつながり

これらは system-spec-harness が `spec-state.json` と `fetched-references.json` から生成する章で、集約状態は 未着手 / 収集中 / 確定 / 対象外 の 4 値（真理値表で導出）。

機械可読なルート正本は [`route-ledger.json`](./route-ledger.json)。`page.tsx` との完全一致を `pnpm run check:docs` で検査する。

会社所属の現在の契約は、利用者が選んだ `qa-w11`・`qa-w12`（D-008・D-009）と [auth の訂正](./auth.md#現在の契約と過去の逐語)・[security の訂正](./security.md#現在の契約と過去の逐語) を優先します。[DD-009](../docs/product/design-decisions.md) の委任に基づく裁定のうち、最古の有効な所属へ戻す部分は `qa-w12` で会社名の順に変わりました。`spec-state.json` は利用者の委任逐語とエージェントの裁定を区別し、既存の承認の質問・回答は保持します。

評価レポート・上司の判断・事業所の達成率の削除の現在の契約は、利用者が選んだ `qa-z03`・`qa-z04` と、各章の「訂正あり」の囲み（`qa-y10`・`qa-y11`・`qa-y13`・`qa-y16`・`qa-x15`・`qa-z01`・`qa-z02` への訂正）を優先します。決めた中身は [DD-020〜DD-024](../docs/product/design-decisions.md) にあります。dev-graph が取り込んだ写し（`architecture/system-spec-*.md` と `specs/system-spec-requirements.md`）は、次の機能の取り込みで新しくなるまで、この訂正の前の文のままです。

## 更新ルール

1. 画面・API・DB のどれかが変わる変更は、対応する system-spec を同じ PR で更新する。
2. 製品向けの言い回しは `docs/product/spec.md` に書き、ここには判定条件と境界を書く。
3. 反映したら `docs/product/spec-receipts/` に受領書を残す。

## 要件定義書 (上位概念・憲法)

- [要件定義書](./00-requirements-definition.md) — 上位概念 U1-U9 の正本 (確定マーカー: `confirmed`)。各技術章は serves_goals でここのゴールへトレース (anchor) する。
- **本質的目的 (U1)**: 利用者が作成・変更・削除した結果を、成功表示の直後の画面・再読み込み・他のタブと画面復帰のどれでも必ず確認できるようにし、『本当に保存できたのか』を疑わずに次の作業へ進める状態をシステムとして保証する。あわせて、等級の呼び名・役割ごとにできること・各人の等級と評価・アンケートの提出状況・設定の足りない所を、どの画面でも同じ言葉で、見てよい人にだけ示し、利用者が『誰が何をできるか』『どこで何を直せばよいか』を迷わずに判断して操作できる状態にする。さらに、管理者・直属の上司・本人が、その人が評価に値するかどうか・点数・項目ごとの強みと弱み・過去の推移を、毎回同じ型で作られる個人別の評価レポートで一目で確かめられるようにする。そのために、アンケートの設問と回答・昇給の設定・KPI 評価セットが、同じ評価期間の定義で食い違わずにつながり、評価の結果がいつ作っても同じになる状態を保つ。使っていない事業所KGIの仕組みは残さない。評価に値するかの結論は、点数の判定だけで決めず、評価を確定する上司が理由とともに記録した判断を合わせて決め、その理由は本人にも同じ文で示す。さらに、設定（等級要件・行動指針・KPI・評価セット）とアンケートの設問のどちらを後から変えても、後から変えた方を正として、もう一方と、その写しを持つ全ての画面と機能が追従する状態を保つ（確定した評価と評価レポートは確定した時点のまま残す）。行動指針と KPI・評価セットの画面は、最初に見る量を判断に要るものだけに絞り、操作に応じて詳しい内容を開ける形にして、設定の作業の認知の負荷を下げる。
個人情報を扱い、ソースを公開しているシステムとして、データが第三者に渡らず、脆弱性は決めた期限のうちに塞がれ、アプリより前の層・認証の入口・出力・CI の成果物のどこからも、漏れや乗っ取りが起きない状態を保つ。
- **ゴール (U3)**: G1=書き込み成功を表示した時点で、同じタブの一覧・件数・ナビゲーション（会社切替など）がすべてその結果を含んでいる。, G2=通常・強制の再読み込みや URL の直接表示は、直前の書き込み結果を必ず含む。, G3=同じ利用者の他のタブや、スマホ・タブレットでの画面復帰（bfcache 復元・タブ復帰）でも、古い一覧のまま操作を続けない。, G4=画面や書き込み API を追加しても、鮮度の保証が個別実装に頼らず共通契約として適用され、適用漏れは検査で落ちる。, G5=一つの操作で複数の表を書く書き込みが途中で失敗しても、一部だけ反映された中途状態（会社はあるが管理者が無い等）を残さない。取り消し・やり直しの処理まで失敗したときは、その事実が記録に残って検知でき、手作業で直せる。, G6=等級の呼び名は、その会社の等級名だけで表す。行動指針の向け先・評価セットの区分・昇格の要件・警告文・アンケートのタイトル・ボタンのどこにも英語の区分名を出さず、等級名を変えると次の表示からすべてに反映される。, G7=等級名を変えられるのは、システム全体管理者と、その会社の会社管理者だけにする。マネージャーと一般の社員、他社の会社管理者は、画面からもサーバー処理からも変えられない。, G8=役割ごとに、どのページを開けて、そこで何ができ何ができないかを、ページ名を単位にした同じ形で確かめられる。表示は実際の権限の判定と食い違わない。, G9=マネージャー・会社の管理者・システム全体管理者は、見てよい範囲の利用者について、今の等級と、確定した最新の評価の KPI評価点と等級要件の達成率を一覧で確かめられる。一般の社員には見えない。, G10=同じメールアドレスの人が、1つのアカウントのまま複数の会社に所属でき、会社ごとの役割・等級・上司で使える。所属していない会社のデータは見えない。, G11=アンケートごとに、対象者の誰が提出済みで、誰が入力途中か未回答かを一覧で確かめられる。, G12=設定の不足を知らせる表示は、何が足りないか・どう直すか・どこで直すかを短く示し、そこから直す画面へ1回の操作で移れる。, G13=並び順を持つ全ての編集画面で、矢印のボタンに加えて、長押ししたままのドラッグとキーボードでも並べ替えられる。, G14=アンケートの選択肢を押しても何も起きない画面を無くす。見本として表示している画面では、見本であることと回答できない理由が分かる。, G15=画面の幅に対して内容が片側に寄り、右側の余白が目立つ画面を無くす。, G16=2つのページの内容を比べて出す警告は、比べている両方のページを階層つきのページ名とリンクで示し、項目ごとにどちらのページにあってどちらに無いかを表で示す。既定ではズレがあることと件数だけを1行で出し、中身は押すと開く。どちらのページから見ても、相手のページへ1回の操作で移れる。, G17=事業所KGIの達成率の仕組み（メニュー・画面・計算・保存・表・列・文書・テスト）を残さず消す。賞与（仮）は KGI を使わない式（個人Pt＝KPI評価点の合計、賞与額＝個人Pt×昇給の設定の1点あたりの円）で出し続ける。, G18=個人別の評価レポートを、開くたびに確定した評価から同じテンプレートで作る。評価に値するか（昇給と昇格の判定とその理由）・点数・項目ごとのレーダー図・その等級にいた期の点数と同じ等級の平均・等級ごとの点数・過去の実績を、図とグラフで一目で分かるように示す。, G19=レポートと評価結果の中身を、見てよい人にだけ見せる。全体管理者と会社の管理者は会社の全員、マネージャーは直属の部下と自分、本人は自分の分を見られる。本人向けは点数の数値と他の人との比較を出さない。範囲の外のデータは、CSV の書き出しとメモを含めてサーバーが返さない。, G20=全ての画面と項目（評価結果の中身・レポートの全ての図・アンケートの各状態・ズレの各種類・役割ごとの見え方）を、ローカルと E2E で確かめられるテストデータを用意する。本番には入れない。, G21=アンケートの配布 URL・回答・回答一覧・内容の確認と編集・公開・締め切る・延長が、アンケートの状態と締切に合った操作と案内だけを出し、サーバーも同じ規則で守る。, G22=評価項目とアンケートのズレを、KPI 項目・等級要件・行動指針の全てで比べ、項目ごとに直す画面へのリンクを出す。新しい版が下書きの間は、回答を集めている古い版の警告を消さない（今の設定と一致した新しい版を公開して古い版が締め切られたら出さない）。, G23=アンケートの設問と回答・昇給の設定・KPI 評価セット・評価の結果を、評価期間に指定した評価セットを基準につなぎ、ズレの比較・アンケートの作成・点数の計算・レポートの作成が同じ定義を使う。つながりの抜けを1か所で確かめられる。, G24=昇給と昇格の可否を、点数の判定と、評価を確定する上司が理由とともに記録した判断（点数の判定どおり／変える）を合わせて決め、その結論と理由を、評価レポート・画面・CSV で本人・直属の上司・管理者に同じ形で示す。点数の判定は書き換えずに残す。, G25=行動指針の分け方の既定（等級1・2で1つ、等級3・4-1・4-2で1つ、等級5-1・5-2は出さない。呼び名を変えた会社でも、等級の内部の識別子で同じ分け方にする）を、新しい会社と、既定からずれた既存の会社の両方で成り立たせる。画面の初期設定の説明は、いまの割り当てを読んで示す。, G26=行動指針と KPI・評価セットの画面を、最初は判断に要る状態・件数・次にやることだけを見せ、操作に応じて詳しい説明と編集を開く形にする（情報は消さず、見せ方を変える）。KPI・評価セットは作業ごとに画面を分け、等級区分ごとの設定を境界のはっきりしたカードで示し、KPI 項目を読みやすい区切りで示す。, G27=設定（等級要件・行動指針・KPI・評価セット）とアンケートの設問のどちらを後から変えても、後から変えた方を正として、もう一方と、その写しを持つ全ての画面と機能が追従する。確定した評価と評価レポートは確定した時点のまま残し、確定前の評価だけが最新に追従する。, G28=評価・結果を確認する画面で「提出済みの回答から評価を作る」を試せるよう、提出済みの回答を含む受付中の評価期間の仮のデータ（氏名は実在しない「サンプル」など）を、手元の見本と本番の見本の会社の両方に用意する。, G29=ボタンだけでなく、カード・見出しの面・選ぶ部品・状態の印・進み具合・数の面・知らせ・表・いまいる場所の印など、全ての画面の共通部品に、いまのテーマの変数から作る、はっきりしたグラデーションと色の変化を持たせ、押した・選んだ・開いたが分かる手応えと、主の操作が一目で分かる強弱をそろえる。全ての系統・明暗・コントラストを強くする設定・印刷で読みやすさを保つ。平賀配色へは移さない。, G30=CI とリポジトリの公開物（Actions の成果物・ログ・source map）に、本番のデータと秘密を出さない。出す工程は検査で落とす。バックアップの置き場は D-010 で決める。, G31=漏えいの恐れがあるとき、秘密の交換・セッションの失効・パスワードの変更を、利用者の判断で安全に行える手順と仕組みを持つ（用途ごとに鍵を分けることを含む）。, G32=依存とランタイムの脆弱性は、公開から期限のうち（critical と high は48時間）に「修正版へ上げる」か「暫定の防御を入れて、当たらない理由を記録する」のどちらかにする。npm の依存の勧告は、CI の pnpm audit（push・PR のときと週1回の定期実行）で自動で拾う（D-011）。Node 本体の勧告は npm に載らないため、運用の担当（開発・運用担当が兼ねる）が Node.js の公式の通知（nodejs-sec の mailing list とブログ）を受け取り、届いたら確かめる。next は 16.4.1 以上にする。, G33=Node・pnpm・Actions の版を1か所で固定する（.nvmrc を 22.23.4、CI は node-version-file、engines は `>=22.23.4 <23`、engine-strict、Actions はコミット SHA）。deploy の秘密を、依存のコードを実行した後の工程に渡さない。, G34=認証の入口を許可制にする（使っていない口は閉じ、氏名とパスワードの変更はアプリの決まりを通る口だけにする）。回数制限は、送り手が偽れない値で人を見分ける。パスワードの決まり（10文字以上）は、どの口でも同じにする。, G35=出力を安全にする。CSV の式を無害にする（数値は除く）。ログイン後などの戻り先は同じ origin だけにする。ログに DB へ渡した値を出さない。社員の画面に選択肢の配点を送らない。, G36=入口で、入力の量と計算量に上限を置く。本文の上限を共通の関数で確かめる。正規表現は入力の長さに比例する時間で終わるものにする。Server Action の本文の上限を絞る。自前の回数制限の表に上限を付ける。, G37=外から見える面を減らす。`x-powered-by` を出さない。使っていない画像最適化の口を閉じる。公開の入口は D-012 で決める。, G38=監査の全指摘を台帳（docs/security/）で追う。各行に ID・深刻度・状態（直した＋確かめたテストの名前／暫定の防御／受け入れた＋理由）を持たせる。同じ型の再発を止める静的検査を足す（バックアップを成果物に上げる工程・送り手が偽れるヘッダーでの識別・CSV の出力の素通し・先頭の `/` だけを見る戻り先の検査）。low の指摘も台帳に載せて扱う。
