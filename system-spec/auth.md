#### 主たる接地根拠: `qa-y13`

**問**

サーバーと権限の章（backend・auth・security）の auth に次の項目を足して確定しますか？（この内容で確定する／確定を保留する）

**答**

(1) 1つのアカウントが複数の会社に所属できる。ログインはアカウントの単位（メールアドレスとパスワードは1つ）。選んでいる会社は、今システム全体管理者だけが使っている cookie（hr_company。httpOnly・Secure・SameSite=Lax）を全員に広げて持つ（D-004 ②）。getViewer はリクエストのたびに、cookie が指す会社への有効な所属をサーバーで確かめてから、その所属の会社・役割・等級を作る。cookie が無いとき・所属していない会社を指すときは、所属のうち会社名の順で最初の会社を使う。所属が1つの人は今と同じ動きにする。 (2) 選んでいる会社を変える処理（switchCompanyScope）を全ての役割に開き、サーバーで所属を確かめ、所属していない会社は拒否する。システム全体管理者は今どおり全社から選べる。会社の切り替えの部品（CompanyScopeSwitcher）は、所属が2社以上の人にも出す。 (3) 等級名を変えられるのは、システム全体管理者と、その会社の会社の管理者だけにする（qa-v02 問1）。マネージャー・一般の社員・他社の会社の管理者には、画面に変更の欄を出さず、サーバー処理（saveMaster の等級の表と、行動指針の割り当てから呼ぶ処理を含む）でも 403 にする。 (4) 役割ごとに開けるページ（accessClass）に加え、ページでできる主な操作・役割ごとの可否・説明も route-ledger.json の各ページに足し、権限の定義をこの台帳1つにまとめる（D-007 ①）。サイドバー・ページの入口の判定・サーバー処理の役割の指定・session.ts の can〜 の判定・権限一覧の表示が、この台帳だけを読む。 (5) 役割の種類は増やさない（『システム開発者』の役割は作らず、画面名だけを変える）。 【2026-10-19 の追加】 (6) 評価の中身とレポートを開ける人を判定する関数（canViewEvaluationOf）を1つにする。全体管理者は全社、会社の管理者は自社の全員、マネージャーは直属の部下（所属の上司が本人）と自分、一般の社員は自分だけ。間接の部下は含めない。レポートの画面・評価の詳細・CSV の書き出し・メモの読み出しがこれを使う。 (7) 台帳（route-ledger.json）にレポートのページと操作を足して権限一覧に出し、KGI のページと操作を台帳から消す。 【2026-10-20 の追加】 (8) 上司の判断を記録できる人は、評価を確定できる人と同じにする（canActOnEmployeeEvaluation：全体管理者・会社の管理者・直属の上司のマネージャー。自分自身の評価は不可）。判断と理由は、評価の中身を見られる人（canViewEvaluationOf：本人・直属の上司・管理者）に見える。本人に見えるのは確定した後だけ。新しい役割や新しい見える範囲は作らない。台帳（route-ledger.json）の確定の操作の説明に『昇給と昇格の判断を記録する』を足す。

## To-Be / Delta

### 到達すべき状態 (To-Be)

- **G2**: 通常・強制の再読み込みや URL の直接表示は、直前の書き込み結果を必ず含む。
- **G4**: 画面や書き込み API を追加しても、鮮度の保証が個別実装に頼らず共通契約として適用され、適用漏れは検査で落ちる。
- **G7**: 等級名を変えられるのは、システム全体管理者と、その会社の会社管理者だけにする。マネージャーと一般の社員、他社の会社管理者は、画面からもサーバー処理からも変えられない。
- **G8**: 役割ごとに、どのページを開けて、そこで何ができ何ができないかを、ページ名を単位にした同じ形で確かめられる。表示は実際の権限の判定と食い違わない。

- **G27**: 設定（等級要件・行動指針・KPI・評価セット）とアンケートの設問のどちらを後から変えても、後から変えた方を正として、もう一方と、その写しを持つ全ての画面と機能が追従する。確定した評価と評価レポートは確定した時点のまま残し、確定前の評価だけが最新に追従する。

### 本章がかなえる具体的やりたいこと (U9)

- **I1**: 書き込みを Server Functions の共通の包みにまとめ、成功したら同じ応答で今の画面を作り直す（next/cache の refresh）。他タブへの通知と、将来のキャッシュの無効化の置き場も、この包みと画面側の共通口に持たせ、全ての書き込み画面をそこへ寄せる。
- **I5**: 共通の包みを通らない書き込み経路を検出する静的検査と、4 経路の E2E を加える。
- **I6**: 応答に鮮度の手がかり（生成時刻）を載せ、反映されない報告を切り分けられるようにする。
- **I8**: 等級名の変更を、システム全体管理者と自社の会社管理者に限る判定を、画面とサーバー処理の両方に置く。
- **I9**: ページごとの権限を1つの定義（ページ・操作・役割ごとの可否・説明）にまとめ、『システムを管理する』に権限一覧ページを足し、利用者一覧に開閉できるボタンとモーダルを置く。説明はポインター・フォーカス・タップのどれでも出す。『Claude Code連携の鍵』を『Claude Code連携（システム開発者専用）』に改める。

- **I19**: レポートのデータを1つの関数で作り（評価に値するか・点数・項目ごとの判定・その等級の推移・同じ等級の平均・等級ごとの点数・過去の実績）、見る人が本人なら本人向けの形に落とす。画面は1つのテンプレートの部品で描き、A4 縦で印刷できる体裁を付ける。
- **I20**: 評価レポートを開ける人を判定する関数を1つにまとめ（本人・全体管理者・会社の管理者・直属の上司）、レポートの画面がそれを使う。レポートは、誰が開いても確定した評価だけから作る。評価の詳細の2画面は今の判定のままにする。CSV の書き出しは上司側の判定で、メモの読み出しは今の公開範囲の判定で絞り、どちらもこの関数を使わない。台帳にレポートのページを足す。
- **I25**: 評価に、昇給と昇格それぞれの上司の判断（判定どおり／変える）・理由・記録した人・記録した時刻を足し、確定の操作で必ず選ばせる。理由は本人にも同じ文で見せるので、保存のときに本人に見せられない語（点数・配点・必要点数につながる表現）を検査し、引っかかった語を名指しして断る。上司コメントにも保存のときに同じ検査をかける。最終の可否を出す関数を1つ置き、レポートの②・評価の画面・本人の結果・評価期間の一覧・CSV がそれを使う。上司が変えたときは印を付け、点数の判定と並べて見せる。
- **I28**: 下書きのアンケートで、設定とつながった設問を足す（設定の項目を選んで足す）・外す・文を直すと、保存と同時に元の設定（KPI の設問の文・評価セットの項目・行動指針の観点・等級要件）へ反映する。評価セットの決まり（等級区分ごとの項目数・固定枠・20点枠）や KPI の計算に要る設問（分子・分母など）に合わなくなる保存は、アンケートも設定も変えずに断り、合わない決まりと直す画面を示す。反映も、設定の保存と同じ権限（会社の管理者以上）・会社の絞り込み・同時に保存したときの 409・制度の変更の記録を通す。
- **I29**: 設定を保存すると、同じ設定を使う、回答0件の下書きのアンケートを自動で作り直し（設定とつながらない設問は残す）、回答のある公開中のアンケートには次の版の下書きを自動で作る（すでに次の版の下書きがあれば、それを作り直す。公開は人が行う）。締め切ったアンケート・確定した評価・評価レポートは変えず、確定前の評価は自動で集計し直す。どのアンケートと評価が変わったかを、保存の結果の文で示す。
- **I30**: 設定の写しを持つ全ての場所（アンケートの設問、回答の見出し、評価の項目・行動指針・等級要件、ズレの表、評価レポート、CSV など）を一覧にして文書に置き、それぞれを「参照」「追従」「確定した時点の写し」のどれかに決め、契約テストで抜けを落とす。保存の後は、関係する全ての画面を取り直し、他のタブにも知らせる（製品仕様 §27）。いまずれている下書きは、更新時刻の新しい方へそろえる。
- **I35**: 秘密の交換・セッションの失効・パスワードの変更の手順書を書き、用途ごとに鍵を分ける（同じ秘密から用途別の鍵を導く）。

### 本章に効く確定意思決定

- **D-002**: 書き込みの直後に同じタブの一覧・件数・会社切替メニューを最新にするには、書き込みの経路をどう組むか。
  - 採択: 書き込みを Server Functions（Server Actions）へ移し、成功したら同じ応答で表示中の画面を作り直す（next/cache の refresh） (`opt-server-functions`)
  - 目的適合: G1 を満たす（Next.js の文書では、Server Functions から呼んだ revalidatePath は表示中の画面をすぐ更新する）。ただし移行が終わるまでは二つの経路が混在し、G4 の検査が複雑になる。（2026-10-01 追記：確定後、表示中の画面の作り直しは I1 のとおり next/cache の refresh にそろえた。revalidatePath は、将来サーバー側にキャッシュを入れるときの無効化の置き場として共通の入口に残す。移行は今回すべて終えたので、二つの経路の混在は残っていない。）
- **D-004**: 1つのアカウント（メールアドレス）のまま複数の会社に所属し、会社ごとの役割・等級・上司で使えるようにするとき、所属と『選んでいる会社』をどこに持つか。
  - 採択: 自前の所属の表を作り、選んでいる会社を cookie（hr_company）で持つ (`opt-membership-cookie`)
  - 目的適合: 会社ごとの役割・等級・上長を所属の表に持てるので、G10 を満たす。
- **D-006**: 権限一覧（役割ごとに、どのページを開けて、そこで何ができるか）を、システム管理のページと利用者一覧のモーダルでどう見せるか。
  - 採択: 1つの表に役割のタブでの絞り込みを足し、スマホの幅ではページごとのカードに切り替える（①②③の組み合わせ。利用者の回答から足した案） (`opt-combined`)
  - 目的適合: 役割の違いを表で比べ、タブで1つの役割だけに絞り、スマホではカードで縦に読めるので、ページ名を単位にした同じ形で G8 を満たせる。
- **D-007**: 権限の定義（各ページでできる操作と、その説明）をどこに置くか。
  - 採択: route-ledger.json に操作と説明を足す (`opt-route-ledger-extend`)
  - 目的適合: ページの可否・操作・説明が1つの台帳に揃い、表示が判定と食い違わないという G8 を満たせる。
- **D-008**: 他の会社に既にアカウントがある人を、別の会社にも所属させる操作を、誰が行えるようにするか。
  - 採択: 全体管理者だけが専用の操作（addMembership）で所属を足す (`opt-super-admin-only`)
  - 目的適合: G10 の『1つのアカウントのまま複数の会社に所属できる』を、全体管理者の操作で満たす。会社の管理者だけでは足せない。
- **D-009**: 複数の会社に所属している人が、選んでいる会社が無いとき（cookie が無い・所属していない会社を指している）に、どの会社を開くか。
  - 採択: 有効な所属のうち会社名の順で最初の会社を開く（同名は会社 id の順） (`opt-company-name-order`)
  - 目的適合: G10 の『会社ごとの役割・等級・上司で使える』を満たし、切り替えの一覧と同じ順なので、どの会社が開くかを利用者が予想できる。

### 本章での適用

### Secure by Design — deep knowledge card

- 出典カード: `ref-system-design-knowledge/references/secure-by-design.md`

#### 目的

利用者の注意や運用後のpatchへ安全性を押し付けず、systemのdefault、architecture、development lifecycleに安全な結果を組み込み、被害可能性と復旧費を下げる。

#### 解決する問題

- 認証・認可・data protectionが後付けで、business flowと矛盾する。
- defaultが過大権限/公開状態で、利用者の完全な設定に安全性が依存する。
- 単一防御の突破で全面侵害になり、検知・封じ込め・復旧の証拠が無い。
- dependency、secret、build、releaseの供給chain riskが製品境界外として放置される。

#### 適用条件

- identity、個人/機密data、金銭、外部入力、admin操作、multi-tenant boundaryを扱う全system。
- compromise時の影響がgoal、法規、信頼、運用継続を損なう。
- vendor/serviceを使う場合も、共有責任とfailure/exit planを明示できる。

#### 非適用条件

- security自体が不要なsystemは原則ない。asset/threatが極小ならcontrolを軽量化できるが、根拠付きrisk acceptanceが必要。
- controlがthreatを減らさず、accessibility/availability/safetyを重大に損なう場合はそのcontrolを採用しない。代替・補償統制を設計する。
- checklist準拠だけでproject固有のtrust boundaryとabuse caseを置き換えない。

#### トレードオフ・失敗モード

- friction、latency、delivery費、運用負荷が増えるため、risk reductionと明示的に釣り合わせる。
- security theaterとしてcontrol数だけ増やし、owner、evidence、responseを持たない。
- fail closedを無差別適用してavailability/safety incidentを起こす。degraded modeとbreak-glass監査が必要。
- secretを隠しても過大権限や長期credentialを残す、暗号化してもkey lifecycleを設計しない等の局所最適。
- free tier製品を価格だけで選び、audit、export、retention、MFA、incident support不足を見落とす。

#### goalへの寄与

- stakeholderの安全・信頼・継続性をsuccess criteriaへ変換し、threat/control/evidenceをgoalへトレースする。
- security controlは「導入済み」ではなく、阻止/検知/復旧時間、権限範囲、data exposureで効果を測る。
- 予算0制約でも、secure default、最小data、短命credential、標準機能、open-source検査を優先し、残余riskを隠さない。
