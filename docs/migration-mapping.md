# 移行マッピング表（元スプレッドシート → データベース）

いまスプレッドシート・Googleフォーム・GASでやっている運用を、このシステムのどこに置き換えたかの対応表。
「元のどのシートの・どの行／設問が」「どのテーブルの・どのレコードになったか」を1対1でたどれるようにしてある。

- 元データは **読み取りのみ**。スプレッドシート・フォームには一切書き込んでいない。
- 抽出した中身は `data/*.json` に保存し、`scripts/seed-data.mjs` がこれを読んでDBに投入する。
  読み取り直しをしなくても、同じデータを何度でも入れ直せる。
- 投入先は **システム標準テンプレート会社（`cmp_template`）** と、**実際に運用している給付事業（`cmp_kyufu`）** の2社。
  新しい会社を作るとテンプレートが丸ごと複製され、その会社だけで自由に直せる。

## 4. 補足・注意

- **`data/kpi-ranks.json` は33項目×5ランク＝165行がそろっている**（元シート166行＝ヘッダー1行＋165行）。欠けている行はなく、補完した値はない。
- **「新規（素案）」と書かれていたKPI項目**は `is_provisional = 1` で入れてあり、画面に「仮」と表示される。決まった内容に直して保存すれば表示は消える。
- **昇給ルールは元シートが「（仮）」**のため、`raise_policies` / `raise_settings` / `promotion_thresholds` / `scheme_rank_ratios` / `kgi_coefficients` はすべて「仮」扱いで投入している。`/admin/raises` から直せる。
- **仮名化はしていない**。元の回答スプレッドシート7本は `test` 行だけで個人情報を含んでおらず、デモに出てくる社員は架空の人物のため。
- 基準マスタの更新時刻は、投入時に `2025-01-01` を入れている（過去サイクルの評価より前）。ここを投入日にすると、投入直後から「基準を直したのに再集計していない」と警告が出てしまうため。

### 9-6. 等級要件達成率の分母（2026-08-10 確定・第3案）

#### 決まったこと

```
達成率 ＝ 達成した数（○の数） ÷ その等級のアンケートで実際に出題した等級要件の項目数 × 100
```

- 未回答の項目も **分母に含め、未達として数える**（回答を空欄にすると分母が減って達成率が上がる、という抜け道を作らないため）。この扱いは評価詳細画面に明記している。
- 等級要件が1件も出題されていないアンケートでは、達成率を **0%ではなく「判定外」** にする。「聞いていない」を「全部できていない」に化けさせないため。
- 判定した時点の **分子・分母を `evaluations.requirement_achieved` / `requirement_total` に保存**する。あとからアンケートの設問を増減させても、確定済みの評価は動かない。

#### 元の制度設計との違い（重要）

元の制度は「半期に数件の目標を立て、その達成率を見る」考え方で、分母は等級ごとの **半期の目標設定上限数**（Beginner〜Chief 5件、AM 3件、Manager 2件）だった。第3案はこの考え方から変わる。

| | 元の制度（GAS） | 第3案（本アプリ） |
|---|---|---|
| 分母 | 半期の目標設定上限数（2〜5件） | そのアンケートで出題した等級要件の項目数（5〜20項目） |
| 実際の値 | 上限超えの達成が続き、**ほぼ全員100%**（例: Chief 17件÷上限5件） | 30〜100%に分散（例: Chief 17項目÷20項目＝85%） |
| この項目の役割 | 事実上の飾り（差がつかない） | 8項目のうちの実質的な評価軸として機能する |
| アンケート | 等級要件の全項目に○×で回答 | **変更なし**（同じアンケートのまま） |

採らなかった案: **A案**＝元の式のまま（全員100%で飾りになる）／**B案**＝「今期の目標として選ぶ」欄をアンケートに追加（元の制度に忠実だが、アンケートの作り直しと運用変更が必要）。

`grades.target_cap`（半期の目標設定上限数）はマスタとして残しているが、**達成率の計算には使わない**。目標設定の運用ルールを画面で案内するための値になった。

#### ランク基準（A〜E）の閾値 ─ **妥当性は検証できていない（2026-08-10 訂正）**

初期値の閾値は「100%以上=A ／ 80%以上=B ／ 60%以上=C ／ 40%以上=D ／ 40%未満=E」。**この値が制度として妥当かどうかは、現時点では検証できない。**

- **実運用のデータが1件も存在しない。** 移行調査の結論のとおり、元のスプレッドシートにあった回答4件はすべて氏名が `test` の動作確認用で、移行すべき過去実績は無かった（→ §9-3）。
- データベースに入っている評価48件（さくら福祉会・みらい支援ネット・給付事業（1社目）の3社ぶん。テンプレート会社には社員がいない）は、**すべて `scripts/seed-data.mjs` が作ったデモ用のデータ**である。○×は社員ごとに手で置いた「実力の目安」（`STRENGTH`）を種にした擬似乱数で生成している。
- したがって「達成率が30〜100%に分散し、A〜Eすべてにばらける」という分布は **シードの作り方が生んだ人工的な結果**であり、閾値の妥当性の根拠にはならない。以前この節に書いていた「実データで妥当性を確認した」という記述は誤りで、取り消す。
- **判断: 閾値は初期値のまま据え置く（仮置き）。** 検証できない以上、いま動かす理由が無い。なお「Aの下限を下げる」方向の変更だけは、全項目達成した人と1項目落とした人が同じAになり差がつかなくなるため、実データが出てからでも慎重に扱う。
- `src/lib/domain/scoring.test.ts` の分布テストは、**シードデータに対する回帰テスト**（シードや計算式を触ったときに分布が崩れたら気づくためのもの）であって、制度の妥当性の証明ではない。テストのコメントにもその旨を書いてある。
- 閾値は `kpi_rank_criteria` に入っており「仮」バッジ付きで `/admin/scheme` からいつでも変更できる（会社ごとに別の値にできる）。
- **実運用のデータが一定件数溜まった段階で、等級要件達成率を含む閾値の分布を再検証する**（→ 残課題リスト）。

#### すでに確定している過去の評価

確定済みの評価は **作り直さない**（過去評価の不変性）。保存済みの達成率と項目数の割合が合わない評価には、評価詳細画面で「以前の決まりで確定済み」と理由を表示する。

なお現在DBにある48件は、移行で運び込んだ実データではなく `scripts/seed-data.mjs` が作った**デモ用データ**である（→ §9-6）。元スプレッドシートに過去の回答実績が無かったため、移行すべき過去の評価は存在しない。

### 9-7. 等級要件の構造の確認（2026-08-10）

制度としての正しい形は「**支援について / 運営について の2区分、それぞれ最大10項目。10項目ちょうどである必要はなく、1項目でも0項目でもよい。会社ごと・等級ごとに決める**」。
移行済みのデータ構造とデータがこの形になっているかを点検した。

- `grade_requirements` は `company_id` × `grade_id` × `category`（support / operation）× `seq` の構造で、**すでにこの形を満たしていた**。データ構造の変更・マイグレーションは不要。
- 本番データの実際の件数（さくら福祉会）: Beginner 支援5・運営5 ／ Regular 8・7 ／ Chief 10・10 ／ AM Ⅰ 2・3 ／ AM Ⅱ 1・4 ／ Manager Ⅰ 1・4 ／ **Manager Ⅱ 支援0・運営5**。区分ごとの最大は10で、上限超えは1件もなかった。支援0件の等級が実在するため「0〜10の可変」で正しい。
- 達成率の分母は **支援の登録数 ＋ 運営の登録数**（上限10や合計20を分母にしない）。→ §9-6、`src/lib/domain/grade-requirements.ts` の `denominatorOf`。

不足していたのは構造ではなく **上限の担保と画面**の2点で、次のように直した。

1. **上限10をサーバー側で担保**（`/api/masters` の `gradeRequirement`）。画面で追加ボタンを止めるだけでは、直接APIを叩かれたときに超えられるため。
2. **等級要件の専用画面を新設**（`/admin/masters/requirements`）。旧・制度マスタ画面に混ざっていた一覧を切り出し、2区分を別の塊にして「いま何項目 / あと何項目」を常時表示、追加・並べ替え・見直し・回答者プレビューをその場でできるようにした。

#### 「わかりにくい」の原因（実装を見て特定したもの）

| # | 原因 | 直した内容 |
|---|---|---|
| 1 | 支援と運営が**1つの一覧に混ざって**並び、区分は各行の小さな補足文字でしか分からなかった | 区分ごとに別のカードに分け、見出しに区分名を大きく出した |
| 2 | **何項目まで登録できるのかが画面のどこにも無かった**（上限10も、いまの件数も、残数も） | 各区分の見出しに `5 / 10` と「あと◯項目登録できます」を常時表示 |

### 10-3. 突合で見つけた計算の不具合（正本の突合とは別に発見）

**1項目でも分母が0・未回答だと、その人の評価がまるごと作られなかった。**

`src/lib/evaluate.ts` で実績値を出す `computeActualValue()` は、分母0と未回答のときに例外を投げる。
この呼び出しが8項目のループの中にあり、受け止める `try` がその人の集計全体を囲む位置にしか無かった。
そのため8項目のうち1つでもつまずくと、残り7項目の判定も含めて中断し、`evaluations` が1行も作られなかった。

制度上の扱いは「**その項目だけ判定外**（ランクEに落とさない＝実績が無いのに未達と断定しない）」であり、
固定枠（等級要件達成率）には既にその処理が書かれていた。書かれていた
「計算に必要な回答が不足しているため、実績値を出せませんでした（判定外）」というメッセージは、
例外が先に飛ぶため **他の項目からは一度も表示されない状態**だった。

→ 項目ごとに受け止めるよう修正し、分母0のときは分母0であることを日本語で残すようにした。

### 10-4. 範囲判定（ランク→得点）の担保

`src/lib/domain/authoritative-criteria.test.ts` が正本のTSVを直接読み、33項目すべてについて次を固定している。

- A〜Eの5行がそろっていること
- **数直線を過不足なく覆っていること**（穴も重なりも無い）
- 表に出てくる全境界値とその前後（±0.1）、および表の外側の極端な値が、**必ず1つのランクにだけ当たる**こと
- 逆転指標が No.8 残業率 / No.15 欠員日数 / No.31 ミス件数 の3項目だけであること。
  判定は**評価方向カラムから導出**しており、項目Noはコードに書いていない
- 通常指標は `下限 ≦ x < 上限`、逆転指標は `下限 < x ≦ 上限`

閾値の重複・欠落は `checkRangeCoverage()`（`src/lib/domain/kgi.ts`）で検査でき、
ランク基準とKGI係数表の両方から使う。

### 10-5. 事業所KGI達成係数の境界の穴

元シートの表は `121%以上 / 111〜120% / 100〜110% / 95〜99% / 90〜94% / 89%以下` と整数％で書かれており、
**99%と100%の間、110%と111%の間が抜けていた**。99.5% のような小数の実績はどの区分にも入らない。

→ 下限以上・上限未満で連続させる形に補完した（`111〜120%` は `111 ≦ x < 121` として持つ）。
補完したことは画面に注記として出す。テスト（`kgi.test.ts`）で、元シートのままの表なら穴として検出され、
補完後の表なら問題なしになることを固定している。
