# 秘密を替える手順書

- 本番の秘密が漏れたおそれがあるときと、2026-10-22 の監査の対応を本番に出したあと（[台帳](./audit-ledger.md) の「利用者の作業」）に使う。決めごとは [DD-032](../product/design-decisions.md) の1と16。
- 依存と Node 本体の脆弱性の勧告が届いたときは、末尾の「勧告への対応」に従う（DD-032 の14）。
- 本番を操作するのは利用者だけ。手順はどれも本番の DB と秘密を書き換えるので、上から順に1つずつ行い、終わるごとに結果を確かめる。
- この手順書には、秘密の値・本番の URL・メールアドレスを書かない。値は、作るときに手元で作り、そのまま `wrangler secret put` に渡す。

## 順番

| 順 | 替えるもの | 替えた後に起きること |
|---|---|---|
| ① | BETTER_AUTH_SECRET | 古いセッションの cookie が通らなくなる。取り込みの下見の途中の印も通らなくなる |
| ② | セッションの表 | 全員がログインし直す |
| ③ | CREDENTIAL_ENC_KEY | 初期パスワードの控えを包み直すまで、控えを開けない |
| ④ | 連携の API の鍵 | 古い鍵を使う道具が止まる |
| ⑤ | 利用者のパスワード | 次のログインで変更を求める |

①と②は続けて行う。①だけでは、DB に残ったセッションの行が残る。

## ① BETTER_AUTH_SECRET を替える

1. 新しい値を手元で作る（32 バイト以上の乱数。例：`openssl rand -base64 32`）。
2. `npx wrangler secret put BETTER_AUTH_SECRET` を流し、聞かれたら値を貼る。値をコマンドの引数やファイルに残さない。
3. 替えた後は、cookie の署名が合わなくなるので、古いセッションは使えなくなる。
4. 確認用の印（社員の取り込みの下見など）も BETTER_AUTH_SECRET から導くので、替える前に始めた下見は確定できない。下見からやり直す。

## ② セッションを消す

1. 次を流す。条件を付けずに全部の行を消す。

   ```bash
   npx wrangler d1 execute hr-evaluation-db --remote --command "DELETE FROM sessions;"
   ```

2. 消した後は、全員（管理者を含む）がログインし直す。流す前に、利用者へ知らせておく。
3. 一部の人だけを残す消し方はしない。漏れたおそれのあるセッションを選び分けられないためである。

## ③ CREDENTIAL_ENC_KEY を替える

CREDENTIAL_ENC_KEY は、初期パスワードの控え（管理者が後で見せるためのもの）を包む鍵の元である。控えは利用者の id に結び付けて AES-GCM で包んであり、鍵を替えると、包み直すまで開けない。包み直すには、今の値（古い鍵）が要る。

包み直しの道具は `scripts/rewrap-credential-vault.mjs`（`pnpm run credential:rewrap`）。wrangler にログインした手元の端末で、リポジトリの直下から流す。

1. 古い鍵と新しい鍵を、シェルの変数に入れる。`read -rs` は打った文字を画面に出さない。新しい値は乱数で作り、画面に出さずに変数へ入れる。

   ```bash
   read -rs OLD_KEY        # 今の値を貼って Enter
   NEW_KEY="$(openssl rand -base64 32)"
   ```

   新しい値は、パスワード管理の道具などに控える。次に替えるとき、古い鍵として要る。

2. 件数だけを見る。鍵は標準入力の2行で渡す（1行目が古い鍵、2行目が新しい鍵）。鍵を引数や環境変数に置くと、道具が断る。

   ```bash
   printf '%s\n%s\n' "$OLD_KEY" "$NEW_KEY" | pnpm run credential:rewrap -- --remote
   ```

3. 出た4つの件数を確かめる。この段では何も書かない。

   | 件数 | 意味 |
   |---|---|
   | 読めた件数 | 古い鍵か新しい鍵で開けた控え |
   | 包み直す件数 | 読めた控えのうち、まだ新しい鍵で包んでいないもの。4で書く |
   | 期限切れで飛ばす件数 | 発行から14日を過ぎた控え。開けないので触れない（次に仮パスワードを発行するときに消える） |
   | 読めない件数 | どちらの鍵でも開けない控え。その人には⑤で仮パスワードを再発行する |

4. 件数が合っていれば、`--apply` を付けて、同じ鍵で書き込む。

   ```bash
   printf '%s\n%s\n' "$OLD_KEY" "$NEW_KEY" | pnpm run credential:rewrap -- --remote --apply
   ```

5. 書き終えたらすぐに、新しい値を入れる。4から5までの間は、包み直した控えをアプリが開けない。

   ```bash
   printf '%s' "$NEW_KEY" | npx wrangler secret put CREDENTIAL_ENC_KEY
   ```

6. もう一度2を流し、包み直す件数が0件になったことを確かめる。0件でなければ、4から5までの間に古い鍵で包まれた控え（その間に発行したもの）が残っている。4だけを流し直し、もう一度この6を確かめる。
7. 終わったら `unset OLD_KEY NEW_KEY` で変数を消す。

鍵を替えずに古い形式だけを移すとき：2026-11-30 の日本時間の終わりを過ぎると、古い形式の控え（DD-032 の1 の変更より前に包んだもの）は開けなくなる。それまでに残った控えを移すときは、2行とも今の鍵を渡して2〜4を流す。鍵は替わらないので5は要らない。

代わりの道：控えは発行から14日で読めなくなる。急がないときは鍵を替えて14日待ち、その間に控えが要る人には⑤の仮パスワードの再発行で代える。

## ④ 連携の API の鍵を替え、古い鍵を失効させる

連携の API の鍵は2本ある。どちらも、漏れたおそれがあれば新しい鍵を入れてから古い鍵を失効させる。

- 画面から発行した鍵：全体の管理の「連携の鍵」の画面（/system/agent-keys）で新しい鍵を発行し、道具に入れ替えてから、古い鍵を失効させる（画面のボタンは「この鍵を止める」）。接続した端末は「この端末を止める」で止める。
- サーバーの設定値の鍵（AGENT_API_KEY）：`npx wrangler secret put AGENT_API_KEY` で新しい値を入れる。設定値の鍵を使わないなら、同じ画面の切替で設定値の受け付けを止める。

## ⑤ パスワードの変更を求める

1. 社員は社員の画面（/admin/members/[id]）、全体の利用者は利用者の画面（/system/users/[id]）を開く。
2. 「仮パスワードを再発行する」から「この仮パスワードを発行する」を押す。パスワードは10〜72文字。
3. 発行すると、次のログインでパスワードの変更を求める印が付く。仮パスワードは本人に直接渡し、メールやチャットに残さない。

## 本番へ出す工程を流し直すとき

- 再実行と復旧判断は、[デプロイ時の注意 §8](../deploy-notes.md#8-失敗時) に従う。失敗した job だけでは成果物が既に消えている場合があるため、ワークフロー全体を流し直す。

## DB を戻すとき（Time Travel）

- 戻す元は D1 の Time Travel だけにする。DB の書き出しを成果物やリポジトリに置かない（台帳の PLT-01）。
- Summary に記録した bookmark を渡すと、その時点へ戻せる。

  ```bash
  npx wrangler d1 time-travel restore hr-evaluation-db --bookmark=[記録した bookmark]
  ```

- 戻すと、その時点より後の書き込み（回答・評価・ログインなど）はすべて失われる。戻す前に、利用者へ知らせ、失われる範囲を確かめる。

## 勧告への対応

決めごとは [DD-032](../product/design-decisions.md) の14（G32）。

### 誰がいつ見るか

- 運営者（リポジトリの持ち主）が、`security-audit.yml` の週1回の実行（毎週月曜 09:00、日本時間）の結果を、その日のうちに Actions の画面で見る。
- push と PR の実行で赤になったときも、同じに扱う。
- 赤の step の名前で、本番に入る依存（本番用）か、開発とビルドだけで使う依存（全体）かを見分ける。

### critical と high

勧告の公開から48時間以内に、次のどちらかを行う。

1. 直った版へ上げる。直接の依存は版を上げ、間接の依存は `package.json` の `pnpm.overrides` で直った版に寄せる。上げた後に `pnpm test` と `pnpm run cf:dry-run` を流す。
2. すぐに上げられないとき（直った版が無い、上げると壊れるなど）は、暫定の防御を入れるか、このアプリに当たらない理由（本番の Worker に入らない、使っていない機能だけに当たるなど）を確かめる。

どちらの場合も、[台帳](./audit-ledger.md) に、勧告・選んだ対応・当たらない理由・見直す時期・確かめた日を書く。48時間を過ぎたときは、過ぎた理由も書く。

### Node 本体の勧告

- Node 本体の勧告は `pnpm audit` に出ない。Node.js の Google Group の nodejs-sec（https://groups.google.com/group/nodejs-sec）を購読し、Node.js のブログ（https://nodejs.org/en/blog）の告知と合わせて受け取る。
- 届いた時点で、22 系の直った版を確かめ、`.nvmrc` と `package.json` の engines を上げるかを決める。本番は Cloudflare Workers（workerd）で動き、Node 本体は CI と手元でだけ使う。
- 確かめた日と結果を、台帳の「Node 本体の通知」の欄に書く。週1回の確認では通知の受信漏れを点検し、workerd の更新の告知も見る。
