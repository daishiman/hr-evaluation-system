## フェーズ1：思考リセット・俯瞰

既存レビューの結論を前提にせず、現在の差分、README の文書の入口、製品仕様、設定の写しの一覧、今回の feature と受け入れ条件を読み直した。思考リセットに伴う成果物の削除は行わない。

- 対象は現在の作業場所 `daishiman/情報量削減` の未確定の変更。行動指針の既定割り当て、設定画面の情報量削減、設定とアンケートの双方向追従、見本データ、共通部品の状態表現、配布前の保全が中心。
- 画面・振る舞いは `docs/product/spec.md`、API・データ・認証は `system-spec/`、設計判断は `docs/product/design-decisions.md` を正とする。`features/`・`tasks/` の計画文書は別の仕様の正本にしない。
- 第一印象の検証論点は、追従・ずれの整列・通常保存で同じ規則が複製されていないか、設定画面で取得・集計・説明を繰り返していないか、写しを保つ境界（回答済み・締切済み・確定済み）を共通化で壊さないか、文書と実装の対応が切れていないか。
- 制約は、既存の作業差分を取り消さないこと、テーマ契約を変えないこと、本番のデータを書き換えないこと、大幅な構造変更は判断を仰ぐこと。異なる責務を見かけの類似だけで統合しない。
- 成功の証拠は30思考法ごとの対象・観察・判断と、矛盾・漏れ・整合性・依存関係の4条件に対応する試験・照合結果。未検証の範囲を PASS としない。

俯瞰完了後に、論理・構造（9種）、メタ・発想（9種）、システム・戦略・問題解決（12種）を独立に並列検証する。3件の分析が揃うまで実装改善には進まない。

### システム・戦略・問題解決（12種）

| 思考法 | 対象・観察 | 判断・改善先 |
|---|---|---|
| システム思考 | 保存→追従→評価→描画更新→別タブ通知の途中で例外が漏れる | 保存と追従の成功境界を分け、通知まで保つ |
| 因果関係分析 | 追従読取失敗→失敗応答→更新なし→再保存の誘発という連鎖 | 応答・保存済み状態・更新・評価継続をまとめて検証する |
| 因果ループ | アンケート→設定→同じアンケートの循環はskipで遮断するが、整列の実行中失敗IDはskipから漏れる | 失敗登録と除外集合の更新を一元化する |
| トレードオン思考 | 即時追従と履歴保全は状態分岐で両立できる | 全保存を巨大なトランザクションへ拡大しない |
| プラスサム思考 | 共通追従層の修正は、保存者・別タブ・復旧担当の全員に効く | 各画面へ強制再読込を足す対症療法を避ける |
| 価値提案思考 | 本質は設定が使う場所へ届き、過去の回答と判断が守られること | ファイル数削減より保存結果の正確さ・失敗対象保全を優先する |
| 戦略的思考 | 正本・派生・記録の分類は有効だが、旧仕様の再掲が競合する | 既存正本へ参照を寄せ、別の仕様書を増やさない |
| why思考 | なぜ古い表示か→refreshされない→失敗応答→追従例外漏れ→準備読取の境界不足。保存と追従を一つの成功として扱うことが根本 | 共通層の失敗隔離と、その故障を再現する回帰試験を採用する |
| 改善思考 | 失敗登録・D1設問INSERT・旧説明に小さな重複がある | `questionInsertStatements` など既存の共通口を使う |
| 仮説思考 | 「回答一覧だけ失敗させる」「先行整列だけ失敗させ後続を成功させる」で問題を反証可能 | 正常系だけでなく障害注入試験を追加する |
| 論点思考 | 同名のdomain/action/DB層は責務が違う。似たファイルの数自体は問題ではない | 同じ変更理由の規則・読取・説明に限り共通化する |
| KJ法 | 指摘を保存結果・状態/循環・単一規則/説明・運用境界に整理 | 上位3群を局所改善。本番鍵の用意や未配布の反映は別の運用課題として保持する |

whyの5段階は、①なぜ画面が古いか：refreshされない、②なぜrefreshされないか：保存が失敗応答になる、③なぜ保存済みなのに失敗応答か：追従例外が漏れる、④なぜ漏れるか：準備SELECTの一部だけがcatch外、⑤なぜ境界の漏れを見逃したか：保存と追従を1つの成功として扱い、通常の状態遷移試験だけでは保存後の読取故障を固定していなかった、という確認を行った。試験は実装をなぞるのではなく、保存済みの事実と利用者へ返る結果を確かめる。

改善前の4条件はすべて未達。矛盾は旧説明、漏れは故障分岐と台帳、整合性は応答、依存関係は追従障害の波及に見つかった。段階選択肢の設定時刻を整列が見ない点は追加調査へ回した。改善フェーズで、段階保存後の追従が失敗すると復旧対象から落ちることを結合試験で再現し、生成入力に含む段階の時刻も比較する最小補正を採用した。

## フェーズ3：改善の実行

全分析を受けて、保存・追従処理と画面の説明整理を別担当へ分けて並列実行し、共有先に依存する修正は各担当内で直列に行う。文書は統合担当が更新する。大幅な構造変更を伴わず、データの所有者・単位・数え方は変えない。

- 優先1：追従準備読取の例外漏れと、整列の実行中失敗対象の保全。
- 優先2：フォーム候補の読取・表示名・並びと、既存設問INSERTヘルパーの共通利用。
- 優先3：反映範囲の共通説明、保存応答の責務整理、共通注意枠の適用漏れ、正本と台帳の補正。
- 保持：回答・評価の履歴の写し、公開済みの設問、確定済みの判断、等級要件等の版、テーマ契約。

再レビューで、並べ替えだけでは既存下書きを作り直さない実装に対し、今回の版管理文書が順序の自動追従まで保証していた点を補正した。中身が同じなら並びの違いを無視し、次に生成するとき新しい順序を使う。

文字数上限の定数化は候補として評価したが、現在の上限は一致しており、今回の復旧・説明整合を直すうえで必要ないため見送った。似たCRUD画面の生成器、異なる開示部品の統合、履歴の写しの削除も採用しない。

### 整列の境界

段階の選択肢を設定側で変更したときは、その更新時刻を整列へ含める。一方、アンケート側だけで直した必須・補足・選択肢などを一律に設定へ戻す機能は追加しない。設問の文・追加・除外の差がなく、下書きが新しい場合、これらの属性だけの差は整列対象にしない既存の境界を保つ。`plan.statements.length === 0` を無条件で再生成へ変えると、その独自編集を失うため採らなかった。一時診断でも対象0件・値の保持を確認したが、恒久的な受け入れ試験の成功件数へは加えない。

### 最終の4条件

判定対象は、今回のワークツリーで整理した設定・アンケート追従、共通説明、関連する正本・台帳。独立した再レビューと上記の実行結果を合わせて判定した。

| 矛盾なし | PASS | 旧一方向の説明・保存応答・正本を現在の追従規則へ補正。順序だけの違いとフォーム独自属性の境界も確認 |
| 漏れなし | PASS | 全30思考法を使用。準備読取の失敗、実行中失敗対象の保全、段階時刻、写しの属性・生成元を補い、障害回帰と画面操作で検証 |
