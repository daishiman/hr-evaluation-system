# 人事評価管理システム — 軽量仕様メモ

最終更新: 2026-08-11 / サイズ判定: **L**（画面20枚超・4ロール・マルチテナント）

## 0. 誰の・何の課題か（一文）

**複数の福祉事業会社**の**評価される側と評価する側**が、Googleフォーム＋スプレッドシート＋GASに散在している等級要件・行動指針・KPI評価基準を、**1つのシステム上で「基準の設定 → アンケート回答 → 自動集計 → 昇格/昇給判定 → 説明できるレポート」まで一気通貫**で回せない、という課題。

## 1. 登場人物（4ロール）

| ロール | できること | 見えないもの |
|---|---|---|
| SUPER_ADMIN（システム全体管理者） | 全会社の情報を閲覧・会社の作成 | — |
| COMPANY_ADMIN（会社管理者） | 自社の全マスタ編集・評価セット設定・フォーム作成・評価確定 | 他社のデータ |
| MANAGER（マネージャー／上長） | 自社の評価対象者の情報・評価結果・評価基準を**閲覧のみ** | 他社のデータ・マスタ編集 |
| EMPLOYEE（一般） | 自分に割り当てられたフォームへの回答・自分の結果の閲覧 | **配点・ランク閾値・昇格必要点数・他人の結果**（APIレスポンスからも除外） |

## 2. データの数え方（最初に決めたこと・後から変えると移行が要る）

- **1件 = 1人 × 1評価サイクル（半期）** で評価結果1レコード（`evaluations`）。
- 評価サイクルは**半期**（例: 2026年度上期 = 2026-04-01〜2026-09-30）。
- フォーム回答は **1人 × 1フォーム（＝会社×等級×サイクル×版）で1レコード**（`form_responses`）。
- 金額は**円・整数**。率は**%・小数1桁まで**。日付は **ISO文字列(YYYY-MM-DD)**。
- **全業務テーブルに `company_id`** を持たせ、行レベルでテナント分離する。
- **等級要件は「支援について」「運営について」の2区分のみ。各区分は会社ごと・等級ごとに 0〜10 項目**（10項目ちょうどである必要はない）。上限10は制度上の決まりで、画面と API の両方で止める（`GRADE_REQUIREMENT_MAX`）。
- **等級要件達成率 = 達成した項目数 ÷ そのアンケートで実際に出題した等級要件の項目数**（未回答は未達として分母に残す。出題0件なら判定外）。判定時点の分子・分母を評価レコードに保存し、あとから設問を増減しても過去の評価は動かさない（2026-08-10 確定・→ `docs/migration-mapping.md` §9-6）。

## 2-1. 等級別の配点（100点の作り方）— 2026-08-11 確定・正式仕様

**評価は等級区分を問わず100点満点。100点で次の等級に昇格する。** ただし「何項目で100点を作るか」は等級区分ごとに違う。

| 等級区分 | 等級要件達成率（固定枠） | 20点枠 | 10点枠 | 選ぶ項目数 | 選択可能な項目数 |
|---|---|---|---|---|---|
| Beginner | 100 | 0個 | 0個 | 1 | 1 |
| Regular | 80 | 0個 | 2個 | 3 | 10 |
| Chief | 40 | 1個 | 4個 | 6 | 26 |
| AM | 30 | 1個 | 5個 | 7 | 32 |
| Manager | 20 | 1個 | 6個 | 8 | 33 |

- 数字の正本は `grade_point_rules`（会社ごとに編集可）。**コードにも画面にも直書きしない**。
- **等級要件達成率（No.1）は全等級で必須の固定枠**。差し替え不可。等級が上がるほど配点が下がり、成果指標の比重が上がる。
- **20点枠は「金銭系」から1つだけ**選ぶ。金銭系は **No.6 単価率 / No.9 売上達成率 / No.24 利益率** の3つのみ（`kpi_items.is_monetary`）。ただし **No.24 利益率は Chief では選べない**（元の配点表にその行が無い）。
- **「その等級区分でこの項目を選べるか」は `kpi_reference_points` に行があるかどうかが正**。元表で「-」だった組み合わせは行を作っていない。
- **AMⅠ・Ⅱ、ManagerⅠ・Ⅱ は配点が同一**で、等級要件の中身だけが異なる（`grades.point_group` でまとめる）。
- **Beginner の他項目は「0点」ではなく評価対象外**。`scheme_items` に行を作らず、レーダーにも出さない（0点だと「取れなかった」に見えてしまうため）。
- 選ばれた項目は等級区分ごとに `scheme_items.point_group` で持ち、合計は必ず `total_points`（既定100）ちょうど。

### 経緯（同じ読み違いを繰り返さないために）

正本TSV `data/_authoritative-kpi-criteria.tsv` の「8項目・等級を問わず100点満点」という記述を、**「どの等級でも8項目を選ぶ」と読んで実装したのが今回の作り直しの根本原因**。実際には8項目は Manager の場合の数であり、「等級を問わず100点満点」だけが全等級に共通する記述だった。
**読むべきだった読み方**: 「100点満点」は全等級共通の制約、「8項目」は配点表（`data/kpi-points.json`）の等級区分ごとの列を数えて確かめるべき派生値。**正本TSVの散文と配点表が食い違ったら、配点表（行の有無・点数）を正とする。**

## 3-1. サイドバー（全画面共通のナビゲーション）

定義は `src/lib/nav.ts` の1箇所だけ。画面側に条件分岐を書き足さない（テストは `src/lib/nav.test.ts`）。

| ロール | 見出しと項目 |
|---|---|
| EMPLOYEE | ホーム／**半期の実績**（実績を報告する・評価の結果を見る）／**内容を確認する**（アンケートの中身） |
| MANAGER | ホーム／**評価を進める**（評価・結果を確認する）／**人を見る**（メンバー）／**基準を確認する**（評価の基準・アンケートの中身） |
| COMPANY_ADMIN | ホーム／**制度を順番に設定する**（制度設定ガイド→等級の設定→等級要件（支援・運営）→昇格の条件・要件→行動指針→KPI・評価セット）／**評価を順番に進める**（評価期間→アンケート→評価・結果）／**運用を補う**（事業所KGIの達成率→昇給の設定）／**人を管理する**（社員）／**基準を確認する** |
| SUPER_ADMIN | ホーム／**システムを管理する**（会社一覧・利用者一覧）＋ COMPANY_ADMIN と同じ会社別グループ |

- 見出しは利用者の言葉（動詞ベース）にする。「マスタ管理」のようなシステム内部の言い方はしない。
- **分類の切れ目にだけ罫線を引く**（`.sidebar-group + .sidebar-group`）。見出しの下や項目の間に横棒を足さない。見出しがあるグループの項目は字下げして、分類の中にあることを見た目で示す。
- **EMPLOYEE には制度設定・評価基準のメニューを一切出さない**。ただし**メニューを出さないことは権限の制御ではない**。URLを直接開かれても通さないのは各画面の `requireRole` と API 側の判定（`src/lib/session.ts`）。
- **アンケートは「中身」と「回答」を分けて考える**（`src/lib/session.ts`）。中身（設問文・補足・選択肢・答え方）は `canSeeFormContent` で全ロールに開く。配る前に「この聞き方で適切か」を確かめられる人が作った本人だけだと、文面の誤りが配布後まで誰にも気づかれないため。一方で回答（誰がどう答えたか）は `canSeeFormResponses`、作成・編集・公開・締め切りは `canEditForm` で **COMPANY_ADMIN 以上のまま**にする。中身が読めることは回答が読めることを意味しない（`src/lib/session.test.ts` で固定）。
- **「読めるか」はロール、「答えられるか」は等級**（`src/lib/domain/form-entry.ts`）。中身は自社のものならロールを問わず読める。回答できるのは自分の等級のアンケートだけで、等級が割り当てられていない人（会社の管理者・システム管理者）はどのアンケートにも回答できない。この線引き（`canAnswerForm`）は回答画面・配布用URL・保存API（`POST /api/responses/[formId]`）が同じ関数を使う。画面から入力欄を消すだけでは、URLを直接叩かれたときに素通りするため、保存APIで必ず弾く（下書きの自動保存も同じ）。
- 自分のアカウント操作はサイドバーに重複して置かない。**全ロール共通のヘッダー右上にあるアカウントポップオーバー**へまとめ、氏名・メールアドレス・役割（SUPER_ADMIN では所属会社ではなく現在の操作対象会社）を確認できるようにする。操作は `/account`（自分の情報）、`/account/password`（パスワードを変える）、ログアウトの3つ。
- PC は折りたたみ可能（状態はブラウザに記憶。`localStorage` キー `hr:sidebar:v1`。ちらつき防止のため描画前にインラインスクリプトで復元）。1023px 以下は引き出し式。
- 現在地はハイライトする。`/admin/masters` と `/admin/masters/requirements` のように前方一致が重なる場合は、長い方だけを現在地にする。

## 3-2. 利用者プロフィールとアカウントの不変条件

### 本人が変更できる項目

- 会社ごとの正本は `profile_field_policies`（`company_id + field` で一意）。本人に開放できるのは **氏名 `name`・所属 `department`・社員番号 `employeeCode`・入社日 `hiredAt` の4項目だけ**。
- 設定行が無いときの既定は、**氏名だけ本人変更可**、所属・社員番号・入社日は会社の管理者のみ。既定値の解釈は画面ごとに書かず、共通の profile field policy で埋める。
- **役割 `role`・等級 `gradeId`・上長 `managerId`・在籍状態 `isActive` は、設定でも本人に開放できない**。画面から入力欄を隠すだけでなく、APIも同じ許可表で拒否する。
- `/account` の表示と `/api/account/profile` の更新判定は、必ず同じ会社・同じ policy 解決結果を使う。変更できるように見えるのにAPIで拒否する状態、または画面で鍵付きなのにAPIでは変更できる状態を作らない。
- policy を変更できるのは **COMPANY_ADMIN 以上**。COMPANY_ADMIN は自社に固定し、SUPER_ADMIN はサイドバーで選んだ操作対象会社にだけ設定する。
- SUPER_ADMIN は会社に所属しない。本人プロフィールの既定値と、会社別業務のために選ぶ**操作スコープは別の概念**として扱い、SUPER_ADMIN 自身の `/account` に操作対象会社の policy を適用しない。

### システム全体の利用者管理

- 利用者を保存するときは、入力差分ではなく保存後の `role / companyId / gradeId / managerId / isActive` の組み合わせを検証する。
- **SUPER_ADMIN は `companyId / gradeId / managerId` を持たない**。COMPANY_ADMIN・MANAGER・EMPLOYEE は、実在する（ひな形ではない）会社への所属を必須とし、利用中のアカウントは有効な会社にだけ所属できる。
- 等級と上長は利用者と同じ会社に属するものだけを指定できる。上長は有効な MANAGER 以上とし、本人自身または循環する上長関係を指定できない。所属会社を変える場合、旧会社の等級・上長を残さず、いったん解除するか新会社の値を同時に検証して保存する。
- **停止中の会社に属する利用者を active にできない**。認証時も利用者自身だけでなく所属会社が有効かを確認し、会社停止を利用者の再開・新規作成から迂回できないようにする。
- 有効な最後の SUPER_ADMIN は、降格・利用停止できない。この判定は同時更新でも0人にならない形で行う。
- 管理者がパスワードを再発行したときは `mustChangePassword = true` とし、対象利用者の既存セッションを失効させる。利用者情報・credential・セッション失効は途中状態を残さない単位で保存する。

## 4. 業務フロー（各1行）

1. **制度を作る**: 管理者が 等級・等級要件（支援/運営）・昇格要件 → 行動指針 の順で登録・確認する（初期値はシード投入済み）。
2. **評価セットを決める**: **等級区分ごとに**「等級要件達成率（固定枠1）」＋20点枠（金銭系から1つ）＋10点枠を選ぶ。項目数と配点は §2-1 の表（`grade_point_rules`）で決まり、合計は必ず100点。
3. **サイクルを開く**: 半期のサイクルを作り、評価セットを紐づける。
4. **フォームを作る**: 等級ごとにフォームを自動生成（等級要件・昇格要件・行動指針・KPI設問から組み立て）し、ビルダーで調整して公開する。
5. **回答してもらう**: 対象の方が公開URLで回答する（点数・閾値は一切表示しない）。
6. **集計する**: 分子・分母 → 実績値 → ランク基準テーブル参照でA〜E → 等級別配点 × ランク割合で得点化 → その等級区分の項目を合計（100点満点）。
7. **判定する**: 昇格＝必要点数到達 かつ 昇格要件ゲート（受講後報告書提出）を満たす／昇給＝**選んだ項目がすべてA**。
8. **説明する**: 判定根拠（どの項目が何点で、なぜそのランクか）を保存し、レーダーチャートと一覧で提示する。

## 5. 入力作法（全画面で1組に統一）

- **空欄の意味**: 空欄＝未入力（0ではない）。数値0は明示的に「0」と入力する。
- **自動計算値**: 欄の中に初期値として入り、「自動」バッジを付ける。手入力すると「手入力」バッジに変わり、「自動に戻す」リンクが出る。
- **Enter**: 次の欄へ移動（フォーム送信はしない）。送信は明示的なボタンのみ。
- **分母のゼロ**: 分母欄は1以上を必須とし、0または空欄なら送信をブロックして日本語エラーを表示する。
- **単位**: 欄の右側に接尾辞で常時表示（件／%／日／点／円）。
- **判定の出し方**: 欄から離れたときに出し、直している最中は消す（打っている途中で赤くしない）。
- **満たすべき条件**: 打ち込む前から画面に出す（打ってから初めて怒られない）。満たしたかどうかは色だけでなく印と読み上げ用の文字でも示す（`.rule-list` / `.rule-mark`）。
- **パスワードの欄**: 表示・非表示の切り替えを文字のボタン（「表示する／隠す」）で付ける。目のアイコンだけのボタンは作らない。`autocomplete` は「いまの」＝`current-password`、「新しい」＝`new-password` を必ず付ける（取り違えるとブラウザが古い値を新しい欄に入れる）。画面に出す文字数の条件はサーバーの判定と同じ数字にする（`src/components/PasswordChangeForm.test.ts` で固定）。

## 5-1. 参考データは「開いたときだけ読む」

参考として見るだけで、いつも使うわけではないデータ（ランク基準の一覧・元の配点表）は、
画面を開いた瞬間には読まない。折りたたみを開いた・ボタンを押したときに初めて読みに行く。

- 共通の読み込み処理は `src/components/useLazyJson.ts`（一度読んだものは覚えておき、閉じて開き直しても読み直さない）。
- 保存できたときは控えを捨てて読み直す（`RecordForm` の `onSaved`）。古い値を持ったまま開き直して、
  それを上書き保存してしまうと、他の人が直した内容が消えるため。
- **2026-08-11 時点で、この仕組みを使っている画面は無い**（`src/components/useLazyJson.ts` と `/api/reference-points` は残っているが呼び出し元が無い。残課題に記録済み）。
  - 元の配点表（`/api/reference-points`）は、採点を「等級別の配点 × ランクの割合」へ一本化した時点で画面から外れている。
  - ランク基準は「開いたときだけ読む」の対象から外した（2026-08-11）。手順2の画面が**その等級区分で選んだ項目だけ**（最大8項目）を扱うようになり、
    全項目ぶんを抱える必要がなくなったため。折りたたみに隠すより、選んだ項目を最初から並べるほうが「何が未設定か」が分かる。
- **一覧して確かめること自体が目的の画面（`/criteria` 採点の基準）は「開いたときだけ読む」の対象にしない**。中身が本題なので、データはサーバー側で一度に読んでから描く。
  - ただし**折りたたみ（`<details>`）は使う**。等級区分によっては選べる項目が33件あり、1項目ずつの採点の流れ（設問・計算式・閾値・点数）を全部並べると読めなくなるため。**開閉はブラウザの中だけで完結し、追加の読み込みは発生しない**（畳んでも中身は既に手元にある）。

## 5-2. 認知負荷を増やさない表示作法

- 各ロールのホームは、全情報の一覧ではなく**その人が次に行う操作**を先頭に置く。管理者は制度/運用の詰まり、マネージャーは未確認・未確定、本人は未回答を最優先にする。
- 設定画面は依存順を共通にする: **等級要件・昇格要件 → 行動指針 → KPI・評価セット → 評価期間 → アンケート → 評価・結果**。
- 初期表示は、判断に必要な状態・件数・主要入力だけにする。長い背景説明、履歴、例外、補助設定は共通の折りたたみパネルで、利用者が開いたときだけ見せる。
- 複数候補から選ぶ設定では、選択操作とは別に比較できること。KPIは最大5件を同じ軸（目的・単位・Aの目安）で並べる。
- 表は監査履歴や正確な行比較が必要な場面に限定し、状況把握はカード、件数、割合バーで示す。装飾だけのグラフや、次の判断につながらない数値は置かない。

## 5-3. 画面の見出しの組み立て（全画面共通）

見出しは `PageTitle`（`src/components/ui.tsx`）1つだけで作る。画面ごとに `<h1>` や
独自の帯を書かない。並び順は上から固定する。

1. **パンくず**（`breadcrumb`）— いまの画面より上の階層だけを並べる。**いまの画面は入れない**（見出しと同じ語を2回読ませない）。
   サイドバーに項目がある画面（＝それ自体が入口）にはパンくずを出さない。詳細・下位の画面にだけ出す。
2. **タイトル**（`title`）— サイドバーの項目名と**同じ語**にする（→ §5-4 用語表）。
3. **説明**（`lede`）— 1〜2文。固定表示にすると隠れるので、必ず読ませたい事実は 4 に置く。
4. **札**（`tags`）— 対象者・期間・等級・状態など、スクロール中も見えていてほしいもの。`.tag` と `Badge` を使う。
5. **操作**（`actions`）— この画面から出ていく操作（別画面へのリンク・書き出し）。
   **「一覧に戻る」ボタンは置かない**（1 のパンくずが担う）。保存・提出などの主要操作は §6 の固定バーへ。

## 5-5. 表かカードか（情報の器の選び方・全画面共通）

**表（`<table>`）は既定の器ではない。** 表は「同じ属性を持つ多数の行を、上から下へ見比べる」ためだけの道具で、
それ以外の用途に使うと、狭い画面で横スクロールが出る・1件の中身が読み取れない・行ごとに違う操作が入って崩れる。

### 判定（先に上から順に当てる）

| 問い | はい → | いいえ → |
|---|---|---|
| 1件だけの中身（項目と値の羅列）か | **定義リスト**（`DefList`） | 次へ |
| 同じ粒度の数値を数個ならべるだけか | **サマリー**（`StatGrid`） | 次へ |
| 1件を「名前＋補足1行＋状態（＋右の数値）」で言い切れるか | **行の一覧**（`CardRow`） | 次へ |
| 行ごとに取れる操作が違う／長い文章（理由・補足）が入る／情報量が多い | **カードの一覧**（`RecordList`） | 次へ |
| 出来事の記録（履歴・改定・取り消し）か | **カードの一覧**（`RecordList`。時系列で1件＝1枚） | 次へ |
| 列が3本未満、または行が3件未満か | **カードの一覧**（列が1〜2本の表は表ではない） | 次へ |
| 同じ項目が全行に揃っていて、上から見比べる／数値を突き合わせるのが目的か | **表**（`DataTable`） | **カードの一覧** |

### 実装の決め事

- 表を書くときは `components/DataTable.tsx` だけを使う。`<table>` を画面に直接書かない。
- カードの一覧は `RecordList`、1件の中身は `DefList`、指標の並びは `StatGrid`。**同じ用途に2つ目の組み方を作らない。**
- `RecordList` の並びは上から **見出し（＋状態の札）→ ラベル付きの値 → 長い文章 → 操作** で固定する。画面ごとに変えない。
- カードを並べる箱は `.card-grid`（1列 → 640px以上で2列 → `card-grid-3` を足すと1024px以上で3列）。独自のブレークポイントを作らない。

### 行と、カードの頭（`CardRow` / `CardHead`）

同じ形を画面ごとに手で組み直していたため、部品を2つ足して1箇所に集約した（`components/ui.tsx`）。

- **`CardRow`** — 読むだけの1行（ホーム・一覧の既定）。並びは **見出し → 補足 → 右の数値 → 状態の札** で固定。
  狭い画面では自動で折り返す。補足が数行になるときだけ `alignTop`。
  `RecordList` との境目は上の判定表のとおりで、**長い文章が主役ならカード（`RecordList`）**、名前で言い切れるなら行（`CardRow`）。
- **`CardHead`** — カード1枚の頭（名前＋状態の札／補足／そのカードから出ていく操作）。
  1件＝カード1枚で中に編集フォームや明細を抱える画面（評価期間・アンケート・会社・制度設定ガイド）で必ず使う。
  左に読むもの・右に押すものの並びを画面ごとに書き起こさない。カードが画面の節そのものなら `heading` を付けて見出しとして読ませる。
- 素の `.card-row`（CSSのクラス単体）を画面で直接使ってよいのは、**行の中身が入力欄で画面ごとに違う編集画面だけ**。
  現在の例外は `PointDesign.tsx` / `FormAnswer.tsx` / `GradeRequirementEditor.tsx` / `PromotionRequirementEditor.tsx`、
  カードの中の節見出しに同じ並びを使う `SchemeGroupPicker.tsx`、および `ManagerDashboard` の「ほか N件は…」の注記行のみ。
  例外を増やすときは `components/ui-rules.test.ts` の許可リストに理由付きで足す（黙って増やすと作法が崩れる）。
- これらの作法は `components/ui-rules.test.ts` がソースを走査して固定している（`<table>` は `DataTable` のみ、`<dl>` は `ui.tsx` のみ、
  `row-main` は `CardRow` のみ、カードの頭の並びは `CardHead` のみ）。

### 押すもの・見出し・確認（`ui.tsx` と `ConfirmButton` に集約）

- **ボタンは3つだけ**: `Button`（その場で動く）／ `LinkButton`（画面が変わる。Next.js の Link）／ `DownloadButton`（`/api/export` などサーバーがファイルを返すURL。素の `<a>`）。
  画面に `className="btn …"` を直接書かない。書くと押せる大きさと見た目の段階がその箇所だけ揃わなくなる。
- **節見出しは `SectionHeading` だけ**。見出しの下の1行説明は `help` に渡す（段落を画面ごとに書き起こさない）。
  見出しタグを画面に直接書いてよい例外は、`AdminDashboard` の「次の一手」1箇所のみ（その画面で唯一の視覚的な主役として、あえて大きい文字にしている）。
- **取り消しのきかない操作の確認は `ConfirmButton` だけ**。ブラウザの確認ダイアログ（`window.confirm`）は使わない。
  何が起きるか・何が残るかを画面のその場に出し、確認は1回だけにする。`ActionButton` も内部でこれを使う。

### 読みやすさの下限（全画面共通・テストで固定）

- **文字の大きさは `globals.css` の `@theme` だけで決める**。画面側にも共通CSSにも `text-[13px]` のような
  px の直書きをしない（1画面だけ大きさが変わる原因になる。テストで禁止している）。
- **段は次の12段だけ**（2026-08-12 に全体を +2px。見出しと本文の差は変えていないので、階層は前と同じ）。

  | 名前 | いま | 前 | 使うところ |
  |---|---|---|---|
  | `text-note` | 14px | 12px | 補足・札・単位・注記・パンくず |
  | `text-sub` | 15px | 13px | 表のセル・値・節見出し・リード文・入力欄 |
  | `text-body` | 16px | 14px | 本文 |
  | `text-strong` | 17px | 15px | 少し強めたい本文 |
  | `text-head` | 18px | 16px | 固定した帯の中のページ見出し |
  | `text-title` | 21px | 18px | ページ見出し |
  | `text-name` | 22px | 20px | 氏名など |
  | `text-num-s` / `-m` / `-l` | 24 / 28 / 30px | 22 / 26 / 28px | 数字 |
  | `text-hero-sp` / `text-hero` | 36 / 44px | 据え置き | 主役の数字 |

- **文字の段は14px未満にしない**（前は12px）。グラフの中の文字（SVGはclassが効かない）も
  `Charts.tsx` の `CHART_FS_TICK` / `CHART_FS_TEXT` の2つだけで決め、13px未満にしない。
- 本文16pxに合わせて、サイドバーの幅（232→248px）・定義リストのラベル幅（8→9rem）・
  自分のメニューの幅（268→292px）を対で広げている。文字だけ大きくすると折り返しが増える。
- **白文字を載せる面は `--accent-on-white-bg`（#c74e0b）を使う**。`--accent`（#e8590c）に白文字だと 3.58:1 で本文の基準（4.5:1）に届かない。
  `--accent` は36px以上の太字の数字（大きい文字の基準 3:1 で足りる）の文字色としてだけ使う。
- **指で押す端末（`pointer: coarse`）では、押せるものを44px以上にする**。マウス環境まで太らせると一覧の密度が落ちるため、その環境だけに効かせる。

### 表を残す箇所の整え方（`DataTable` に集約済み）

- **列見出しは固定する**: `thead th` を `position: sticky` にし、固定ヘッダー（＋あれば見出しの帯）の下に貼り付ける。
  オフセットは `--table-head-top`（`body:has(.page-head[data-sticky="true"])` で帯のぶんを足す）。§6 の固定方針と対で保つ。
- **数値の列だけ右揃え＋等幅**（`num: true` → `.col-num`）。文字列の列には付けない。
- 行の区切りは1pxの罫線のみ。**ゼブラ（縞塗り）は使わない**（色を意味以外に使わない方針のため）。行の識別はホバーの淡い塗りで足りる。
- 空セルは空白にせず `—` を出す（値が無いのか読み込めていないのかを黙らせない）。

### 狭い画面での自動カード化（採用する）

- **採用する。** 容器の幅で判定し（画面幅ではない）、`DataTable` が同じ列定義から表とカードの両方を出す。
  折りたたみの中や狭い欄に置いても正しく畳まれるようにするため、メディアクエリではなくコンテナクエリを使う。
- しきい値: 容器 **640px 未満**でカード。列が **5本以上**の表は横に潰れる前に **900px 未満**でカード（`data-cards="wide"`、自動判定）。
- カードでの並びは列定義の `role` で決める: `title`（1行目＝その行が何か）／ `mark`（1行目の右の札）／ 省略（ラベル付きの値として縦積み）。
  **列の並び順＝重要度の順**にすること。カードでも同じ順で読まれる。
- 横スクロールする表は作らない（`table { min-width: 640px }` は廃止した）。

### いまの棚卸し（2026-08-11 時点・全10箇所）

| 場所 | 中身 | 判定 |

## 6. 常時表示要素（適用範囲）

固定するものは3種類だけ。どれも実装は共通部品1箇所で、画面ごとに `position: sticky` を書かない。

| 種類 | 実装 | 出すもの |
|---|---|---|
| 見出しの帯（上） | `PageTitle` の `sticky`（`.page-head[data-sticky="true"]`） | パンくず・タイトル・札（対象者・期間・等級・状態） |
| カードの頭の帯 | `CardHead` の `pinned`（`.card-head-sticky`） | いま入力している対象の名前と、打ちながら参照し続ける値 |
| 操作の帯（下） | `components/layout/StickyActionBar.tsx`（`.action-bar`） | 進み具合・保存状態・締切と、主要ボタン1〜2個 |

### カードの頭の帯（`CardHead` の `pinned`）

長いカードの中を上から順に入力していくと、単位・配点・判定ルールが画面の外へ出てしまい、
いま打ち込んでいる「80」が何なのかを確かめるために毎回上へ戻ることになる。それを無くす。

- **帯に載せるのは「打ちながら参照し続けるもの」だけ**: 対象の名前・配点・単位・大小の向き・
  下限上限の含み方・残り枠。**一度読めば済む説明文（計算式・実績値の出し方・空欄の意味）は
  帯に入れない**。帯が厚いと入力欄が画面から押し出され、帯の目的そのものを壊す。
  この線引きは型で縛っている（`pinned` のときは注記 `detail` を渡せない）。
- **貼り付く位置は `--sticky-top` の1つだけ**。表の列見出し（`--table-head-top`）も同じ値を読む。
  この値は **`components/StickyOffset.tsx` が見出しの帯の高さを実測して入れる**。
  帯の高さは画面ごとに違う（パンくずの有無・札の行数・折返し）ため、CSSに数値を書き込むと
  上の帯の下に潜り込んで読めなくなる。`scroll-padding-top` も同じ値から取る。
- **重なりの順**: 見出しの帯 15 ＞ カードの頭 5 ＞ 表の列見出し 4。
- **親に `overflow: hidden` を作らない**（`.card` / `.card-pad` / `.stack`）。作ると無言で固定が効かなくなる。
- **狭い画面（〜639px）と低い画面（高さ〜560px）では固定をやめる**。375×700 の実測で、
  上の固定物が約195px・下の操作バーが約116px を使い、そこに帯（約93px）を足すと
  入力欄に残る高さが画面の半分を切る。狭い画面では見出しの帯が現在地を持っているのでそちらに任せる。
- **適用した画面**: `/admin/scheme/[等級区分]/criteria`（項目ごとのカード。配点・単位・判定ルール）、
  `/admin/masters/requirements`（支援・運営の区分。いま何項目・あと何項目）、
  `/admin/masters/promotion`（種類ごとの塊。いま何項目）、
  `/admin/behavior`（観点ごとのカード。5段階の文章を続けて書くため）、
  `/me/forms/[id]`（アンケート回答。まとまりごとのカード。節の名前と答え方の決まり）、
  `/admin/forms/[id]`（アンケート組み立て。**編集を開いているカードだけ**。何問目・どの答え方・どの単位）。
  （回答・組み立ての2つは §16 で追加。それ以前は「適用しない」としていた）
- **適用しない箇所と理由**:
  - 1画面に収まるカード（サマリー・件数・短い設定） — スクロールしないので固定する意味がない。
  - 一覧・履歴のカード（`RecordList`）・提出済みの回答（`ResponseSnapshot`）・確認用の下見（`FormPreview`） —
    読むだけで入力しない。参照し続ける値がない（`ui-rules.test.ts` で固定）。
  - 表（`DataTable`） — 列見出しの固定がすでに同じ役目を果たしている。二重にしない。
  - アンケート組み立ての**閉じているカード** — 2行しかなく、貼り付く前に流れ去る。

- **見出しの帯を固定する画面**: `/me/forms/[id]`（アンケート回答）、`/admin/forms/[id]`（アンケート組み立て）、`/admin/scheme/[等級区分]`・`/admin/scheme/[等級区分]/criteria`（KPI・評価セットの手順1・2。入口の `/admin/scheme` は短いので固定しない）、`/admin/masters`（等級の設定）、`/admin/masters/requirements`（等級要件）、`/admin/masters/promotion`（昇格の条件・要件）、`/criteria`（評価の基準）、`/manager/evaluations/[id]`・`/me/results/[id]`（評価詳細）。
- **操作の帯を出す画面**: `/me/forms/[id]`（提出）、`/admin/forms/[id]`（設問を保存）、`/admin/scheme/[等級区分]`（保存して次へ）、`/admin/scheme/[等級区分]/criteria`（次の等級区分へ）。
- **適用しない画面と理由**:
  - ログイン・エラー画面 — アプリの枠の外にあり、スクロールしない。
  - 一覧系・ダッシュボード（`/admin`・`/manager`・`/me`・各一覧） — 退避先がサイドバーとヘッダーで足りる。
  - `/admin/masters/requirements` の操作の帯 — 項目ごとにその場で保存する作りで、まとめて押す主要ボタンが無い。
  - `/admin/members/[id]`・`/system/users/[id]` — 区画ごとに保存するため、固定できる主要ボタンが1つに決まらない。
  - `/account/password`（パスワードの変更） — 入力欄が3つで、狭い画面でも押すものが視野から出ない。帯を出すと本文とボタンが二重になる（上の「同じ主要ボタンを両方に置かない」に反する）。
- **同じ主要ボタンを本文と帯の両方に置かない**（押す場所を1つにする）。
- 固定要素の下にフォーカスやアンカー先が潜り込まないよう、`globals.css` の
  `scroll-padding-top` / `scroll-padding-bottom` を帯の高さと対で保つ。

## 7. データのライフサイクル方針

1. **取込値と手修正を別枠で持つ**: フォーム回答（`form_answers`）は原本として不変。評価側の修正は `evaluation_items.override_*` に別枠で保存し、どちらの値を使ったか画面に出す。
2. **確定済みサイクルはマスタ変更で据え置き**: `evaluations.status = finalized` のサイクルは、その時点のランク基準・配点を `evaluation_items` にスナップショット保存する。後からマスタを変えても確定結果は動かない。再集計可能な確認中評価がある場合だけ「集計し直す」導線を出し、確定済みしかない場合は据え置きであることだけを通知する。KPIランク基準と評価セットは `/admin/scheme`（入口）、KGI係数は `/admin/kgi` でも同じ共通通知を表示する。
3. **移行前の配点は参考値として保管**: 元スプレッドシートの配点表（項目×等級区分×ランク）を `kpi_reference_points` にそのまま保管する。評価の計算には**使わない**。ただし**「その等級区分でその項目を選べるか」は、この表に行があるかどうかが正**（§2-1）。評価セットの項目を差し替えたときに「元はこの等級で何点だったか」を画面に出し、`参考` バッジ付きで**操作したときだけ**配点欄に入る（自動適用しない）。
4. **突合は正規化キー**: 社員はメールアドレス（小文字化・trim）、KPI項目は `company_id + no`、設問は `company_id + question_key` を正規化キーとする。
5. **行動指針は公開時の写しを評価する**: 行動指針の観点名・段階文言・選択肢はアンケート作成時に設問へ写す。`/admin/behavior` の変更は次に作るアンケートだけに反映し、公開済みアンケートと既存評価を stale にしない。
6. **行動指針の基準セットは会社ごとの行として持つ**: 基準セット（`behavior_band_sets`）は会社ごとに追加・複製・改名できる。識別子（`code`）は作成後に変えない（`grades.behavior_band` と `behavior_guidelines.band` がこの文字列で結ばれているため）。会社が変えるのは呼び名（`name`）だけ。**どれかの等級に出す設定になっているセットは使用を止められない・消せない**（先に等級の割り当てを変える順番を強制し、設問が黙って消えないようにする）。既定の呼び名は等級名にそろえる（`Beginner・Regular向け` / `Chief・AM向け`）。

7. **制度設定の項目は「使わない」と「完全に消す」の2段階**（2026-08-12 / §7-7 に詳細）: 一度でも使った実績があるものは `is_active=false` に留め、一度も使っていないものだけ物理削除を許す。

### 7-7. 制度設定の項目を消すときの決まり

利用者が試しに作った項目が一覧に残り続けるのを防ぐため、**「使わない（一覧に残す）」に加えて「完全に消す」**を用意した。ただし過去の記録を守るため、消せる条件をサーバー側で固定する。

- **消せる条件**: その項目の id が `form_questions`（下書きを含む全アンケートの設問）にも、`evaluation_behaviors` / `evaluation_requirements` / `evaluation_gates`（評価の記録）にも**1件も現れないこと**。1件でもあれば `400` で拒否し、「どこで使っているか」を含む理由を返す。判定は `src/lib/master-usage.ts`、実行は `src/app/api/masters/delete-master-item.ts`。
- **下書きのアンケートも「使用中」に数える**: 設問は作った時点の写しなので、まだ公開していなくても消すと設問の出どころが説明できなくなる。
- **画面のボタンの出し分けに頼らない**: 画面は同じ判定を先に行ってボタンを出し分けるが、`DELETE /api/masters` 側でも必ず数え直す。権限は `COMPANY_ADMIN` 以上、会社は本人の所属から取る（本文の会社idは受け取らない）。他社の id は「見つからない」（404）として扱う。
- **対象**: 行動指針の基準セット / 行動指針の観点（5段階の文章ごと消える）/ 等級要件 / 昇格要件。等級・事業所・利用者・アンケートは対象外（過去の評価が必ずぶら下がるため、使用停止だけを持つ）。
- **使用しない状態の見た目**（2026-08-12 に強め直した）: `Card` / `CardRow` / `RecordList` の `off`、`DataTable` の `rowOff` から `data-off="true"` を付ける。見た目は**面を灰色（`--off-surface`）・枠線を破線（`--off-line`）・中の色を落とす（grayscale）・「使わない」の札**の4点。**本文の文字色は薄くしない**（読みやすさの下限のため）。定義は `src/app/globals.css` の1箇所。
  - 最初は `--subtle`（#f5f6f8）で沈めたが、白との差が2%しかなく実際の画面で見分けられなかった。**見た目の変更は必ず `build` → `preview` で目視確認する**（テストが通ることは見え方を保証しない）。
  - 取りこぼしは `src/components/off-state.test.ts` が機械で検出する。「利用停止／使用しない／締め切り済み／取り消し済み」と画面に書いてあるのに沈める指定が無いファイルがあると落ちる。沈める対象が無い画面は同ファイルの許可リストに理由を書いて外す。
  - **一覧と詳細の両方で沈める**: 締め切り済みのアンケートは一覧のカードだけでなく、開いた先（`/admin/forms/[id]` と `/forms/[id]`）の要約カードも沈める。一覧では灰色なのに開くと白い、という食い違いを作らない。
  - **等級・事業所は対象外**: データ上は使用中／使用しないの欄があるが、切り替える操作が画面のどこにも無い（到達できない）。到達できない見た目は足さず、切り替えを足したときに落ちる検査を `off-state.test.ts` に置いている。

### 7-8. 等級要件・昇格要件は、本文を上書きせず版として残す

等級要件と昇格要件は、過去のアンケートと評価が「そのとき何を聞いたか」を説明するための定義である。
本文など意味が変わる修正は、使用中の行への上書き保存にしてはならない。

**操作の要約**

| 操作 | 保存 | 過去への影響 |
|---|---|---|
| 内容を直す | 新id + `previous_version_id` | 旧行・作成済みフォーム・評価は不変 |
| 今後使わない / もう一度使う | 現行版の同じidの `is_active` | 次に作るアンケートの候補だけが変わる |
| 過去内容の再採用 | 現行版の後続となる新id | 過去版を直接 active にしない |

詳細な不変条件・API command・UI用語・行動指針の等級割当は次に分離した（500行上限）。

→ [`docs/product/spec-master-definition-revisions.md`](./spec-master-definition-revisions.md)

## 10. ランク→点数の換算方式（2026-08-11 に一本化）

**採点方式は「等級別配点 × ランク割合」の1つだけ**（`evaluation_schemes.scoring_mode = ratio`）。割合は A=100% / B=80% / C=60% / D=40% / E=0%（`scheme_rank_ratios`。会社ごとに変更可・値は仮）。配点は §2-1 の等級別配点。

- 一本化した理由: 等級区分ごとに項目を選び直す制度になったため、項目を差し替えるたびに等級区分×ランクの点数表を作り直す方式では運用が止まる。重みは配点だけで決まる形にして、説明も1行で済ませる。
- **廃止**: 項目別絶対点方式（`absolute`。項目ごとの点数表 `kpi_reference_points` を直接使う方式）。**新しく選ぶことはできない**（APIで拒否）。
- ただし **`scoring_mode` 列と `evaluations.scoring_mode_snapshot` は残す**。`absolute` で確定した過去の評価は、当時の方式のまま保持・表示する（過去評価の不変性。§7-2）。
- 移行前の配点表は `kpi_reference_points` に保管したまま。いまの役割は「点数の計算」ではなく **「その等級区分でその項目を選べるか」の判定と、参考配点の表示**（§7-3）。

## 11. 事業所KGI達成係数と賞与（すべて仮）

`kgi_coefficients`（会社ごとに編集可）。個人Pt ＝ KPI評価点合計 × 達成係数、賞与額 ＝ 個人Pt × `raise_policies.bonus_yen_per_point`（3,200円 / 原資930,000円）。

元資料の区分は 95〜99% と 100〜110% の間、111〜120% と 121%以上 の間が**とびとび**で、達成率99.5%・110.5%のときに係数が決まらなかった。上の区分の下限にそろえる形（99%までは0.6、100%からは1.0）で埋め、埋めた旨を管理画面に明記している。保存時は `checkRangeCoverage` で抜け・重なりを検査し、問題があれば日本語で警告を返す（保存自体は止めない。1行ずつ直す途中では必ず一時的にずれるため）。

### 11-1. 達成率の入力（`/admin/kgi`）

達成率は事業所ごとに別表から手で持ってくる値で、アンケートの中に聞く設問が無い。そのため `/admin/kgi`（COMPANY_ADMIN以上）で事業所×サイクルごとに登録する。`office_kgi_results` に1行1事業所で保存し、**未登録は「行が無い」状態にする**（0% で保存しない。0% は「まったく達成していない」を意味し、最小の係数が当たってしまうため）。値が取れないときは個人Pt・賞与額を 0 ではなく **null** にし、「達成率が未登録のため出せない」と理由を残す。

**保存したときに何を計算し直すか**：その事業所・そのサイクルの評価のうち、**確認中（draft）のものだけ**、賞与の欄（達成率・係数・個人Pt・賞与額・判定根拠）を入れ直す（`src/lib/kgi-apply.ts`）。

- 賞与の欄だけにする理由: 達成率が変わっても KPI のランク判定・得点は動かない。賞与は保存済みの `total_score` × 係数 × 単価だけで決まる純粋な計算なので、評価そのものを作り直す必要がない。作り直すと達成率と無関係な基準変更（ランク基準の編集など）まで巻き込み、「達成率を入れただけなのに点数が変わった」が起きる。
- 確定済みを書き換えない理由: 過去評価の不変性。確定して本人に伝えた賞与額が後から黙って変わることを避ける。据え置いた件数は保存時のメッセージと画面に出して隠さない。
- `office_kgi_results` は再集計の検知対象（`src/lib/impact.ts` の WATCHED）に**入れない**。保存時にその場で反映しているため、あとから「集計し直してください」と促す必要がなく、入れると無関係なサイクルまで再集計対象と表示されてしまう。

**どの事業所の評価とみなすか**は `effectiveOfficeId`（`src/lib/domain/kgi.ts`）で決める。評価に写し取った所属（`evaluations.office_id`）→ 回答時点の所属（`form_responses.office_id`）→ いまの所属（`users.office_id`）の順。期中に異動した人に異動先の達成率が遡って当たらないようにするため、この順番を守る。どれも空なら null にして、どの達成率も当てない。

変更履歴は `office_kgi_revisions`（誰が・いつ・何％から何％へ・理由）に残す。`raise_revisions` と同じ作法。

個人Pt・賞与額は**評価する側（MANAGER以上）にだけ**表示する。個人Pt ÷ 係数で、一般（EMPLOYEE）に隠している KPI評価点合計 が逆算できてしまうため、API レスポンス（`getEvaluationDetail`）の段階で落とす。

## 12. 評価の数値を、どこまでテストで固めているか

評価は「1点の狂いが昇給・昇格を変える」ため、計算・保存・表示の3つを別々に固定している。

### 12-1. 3層の分け方

| 層 | 何を確かめるか | どこ |
|---|---|---|
| 計算 | 点数・ランク・係数・昇格昇給の判定そのもの（純関数） | `src/lib/domain/*.boundary.test.ts` |
| 保存 | 計算結果がデータベースの列に入り、読み出すと同じ値になるか | `src/lib/evaluate.integration.test.ts` |
| 表示 | 画面へ渡す値が、保存されている値と食い違わないか（本人には配点・閾値が渡らないか） | 同上（`scopeEvaluationRow` / `scopeEvaluationItem` / `buildRadarValues` を通す） |

保存・表示の層は、**メモリ上のSQLiteに `drizzle/migrations/*.sql` をそのまま適用した本物の表**に対して走る（`src/test-support/sqlite-d1.ts`）。drizzle が D1 に対して行う呼び出し（`prepare` → `bind` → `run` / `all` / `raw` / `batch`）を node:sqlite で満たす薄い層で、production のコードは1行も分岐させていない。下ごしらえは `src/test-support/evaluation-fixture.ts` に集約する。

### 12-2. 境界の決まり（試験で固定している内容）

- **通常の項目（高いほど良い）**: 下限は含み、上限は含まない（`下限 ≤ 実績値 < 上限`）。下限80なら 79.9 は下のランク、80 と 80.1 は当該ランク
- **逆転指標（低いほど良い）**: 上限を含み、下限を含まない（`下限 < 実績値 ≤ 上限`）
- **行動指針**: 3 / 2 / 1 / 0 / **-1** の5段階。未回答は 0 として数え、-1 にはしない
- **等級要件達成率**: 分母は「そのアンケートで実際に出題した項目数」。出題が0件なら **0% ではなく空**（判定外）
- **ゼロ除算**: 計算式の分母が0なら、その項目だけを判定外にする（E に落とさない・ほかの項目の計算は続ける）
- **未入力**: 空欄は 0 と読み替えない。値が無い設問を使う項目は判定外にする
- **丸め**: 点数は小数第1位、実績値は第2位、個人Ptは整数。ちょうど「第3位が5」に見える値（1.005 など）は下に寄る（現状の記録。backlog H1）
- **確定済み**: 基準表を書き換えたあとに集計し直しても、確定済みの評価は1列も変わらない
- **集計し直し**: 同じ評価IDを使い回し、内訳の行が二重にならない

### 12-3. 網羅率の測り方と下限

`pnpm run test:coverage` で測る。対象は `src/lib/domain/**` と `src/lib/evaluate.ts` / `src/lib/impact.ts`（評価の計算・保存・判定に関わるファイル）。

下限は `vitest.config.mts` の `thresholds` に置き、**行100% / 関数100%** を割ったらコマンドが失敗する。CI（`.github/workflows/ci.yml`）はこのコマンドを実行するので、テストの無いまま評価の分岐を増やすと main に入れられない。

文と分岐が100%でない残り7か所は、型・データベースの参照制約・定数によって実際には通らない保険であり、テストが書けていないのではない（backlog H3 に一覧）。

### 12-4. 計算まわりは網羅率100%を必須にする（2026-08-12 追加）

### 12-5. 「到達しない保険」を残さない方針（2026-08-12 追加）

到達しないコードは、読む人に「そういう場合がある」と誤解させるだけで何も守らない。以下のいずれかに必ず決着させる。

1. **通せるなら通す** — 通せないと思っていたものが実は通ることがある。必ず実際に試して確かめる
2. **通らないと確かめられたら消す** — ただし「通らない前提」そのものを試験で固定してから消す（前提が崩れたら試験が落ちる）
3. どうしても残す場合は、通らない**根拠**をコードのすぐそばに書く

この方針で、以前 backlog H3 に挙げていた7か所はすべて決着させた（詳細は backlog J1）。


## 13. 確認の窓と、入力の少ない画面の幅（2026-08-12 追記・全画面共通）

### 13-1. 確認の窓は画面の中央に出す

- 確認の窓は `ConfirmButton`（`<dialog>` + `showModal()`）に集約する。画面ごとに窓を書き起こさない（テストで固定）。
- **中央に出す指定は `globals.css` の `.confirm-dialog { margin: auto }` 1箇所だけ。**
  ブラウザ標準の `<dialog>` は `margin: auto` で中央に来るが、Tailwind の初期化（preflight）が
  全要素の margin を 0 にするため、指定を書かないと**画面の左上に貼り付く**（実際にそうなっていた）。
- **窓の高さは画面内に収め、あふれた分は窓の中だけをスクロールさせる**
  （`max-height: calc(100dvh - 40px)` + `overflow-y: auto`）。
  はみ出させると「やめる」ボタンに手が届かなくなる。文字を大きくした後は特に起きやすい。
- **狭い画面（〜639px）でも中央のまま**、左右の余白だけ詰める。
  下から出す形（シート）にすると、親指の位置に実行ボタンが来て誤操作が増えるため採らない。
  確認文は2〜3行と短く、中央でも窮屈にならない。
- 背景の暗い部分を押したときは**閉じる（＝何も実行しない）**。
  取り消しのきかない操作は「押さなければ起きない」側に倒すのが安全なので、閉じてよい。
  逆に、閉じたら困る窓（入力途中の内容が消えるもの）はこの部品では作らない。
- Esc で閉じる・開いた先に焦点が移る・背面にキーボード操作が抜けないことは `<dialog>` に任せる。

### 13-2. 入力項目が少ない画面は幅を絞る（`.narrow-form`）

- **幅いっぱいが親切とは限らない。** メールアドレスは40文字も入れば足りるので、
  欄を画面幅まで伸ばしても打ちやすくならず、視線が横に長く動くだけになる。
- 幅の正本は `globals.css` の `.narrow-form`（上限 24rem）。**画面ごとに `max-w-*` を書かない**（テストで固定）。
- **狭い画面（〜639px）では上限を外して幅いっぱいに戻す**。絞ると逆に窮屈になる。
- 適用: ログイン（`/login`）、パスワードの変更（`/account/password`）。
  入力欄が多い画面（アンケートの組み立て、KPIの基準、事業所KGI）には**適用しない**。
  項目が多い画面で幅を絞ると、1項目あたりの行数が増えて縦に伸びるだけになる。

## 15. 外から入る数値の決まり（2026-08-12 追加）

### 15-1. 受け付ける数の上限は 1兆（どの経路でも同じ）

`src/lib/domain/number-input.ts` の `MAX_ABS_NUMBER`（= 1,000,000,000,000）を唯一の正本とする。画面の入力欄・提出の受け口・貼り付け取り込みは、すべてこの1つの値を見る。

なぜ上限が要るか。保存された数値はあとから計算式にかけられる（`q1 ÷ q2 × 100`）。桁が極端に大きい値が1つ紛れ込むと、掛け算の途中で計算機の扱える範囲を超えて結果が「無限大」になる。無限大になった項目はランクのどの帯にも当たらず、**理由の分からない判定外**として静かに落ちる。落とす場所を「計算のあと」ではなく「値を受け取るその場」に移すのが上限の役目。

1兆にした根拠（2026-08-12 時点の本番データで確認）:

| 見たもの | 実際の値 |
|---|---|
| 保存されている回答の数値 | 3,006件、最小 0・最大 5,515、小数もマイナスも0件 |
| 設問の決まりに反している回答 | 0件（下限割れ・上限超え・整数のはずが小数、いずれも0件） |
| KPIのランク基準の下限・上限 | 最大 130 |
| 制度設定の金額の上限（受け口の決まり） | 10,000,000 |

いちばん大きい設定でも1000万なので、1兆はどの実務値より桁違いに大きい。いっぽう 1兆どうしを3回掛けても（1e36）計算機の範囲に十分収まるので、無限大も防げる。**この上限で弾かれる既存データは1件も無い。**

### 15-2. 貼り付け取り込みは、画面から提出したときと同じ決まりで見る

以前は取り込み（`src/lib/import.ts`）だけが独自の数値の読み取りを持っており、`-5`・`3.7`（整数だけの設問）・下限上限の超過・`0x10`・`1e308` がすべて素通りしていた。素通りした値は「回答としては保存されたのに、集計で理由なく落ちる」形でしか表に出ず、原因を追えなかった。

いまは `parseImportedNumber`（= 画面と同じ `parseNumberInput` に、取り込み特有の「末尾の単位を落とす」だけを足したもの）を通す。経路ごとに別の判定を書かないことを規律とする。

| セルの中身 | 結果 |
|---|---|
| `42` / `１２３４` / `1,200` / `12円` / `50%` / `+7` / 前後の空白 | 受け付ける（表計算からの貼り付けで混ざるものは黙って読む） |
| `-5`（0以上の設問） | 断る「0以上の数字を入力してください」 |
| `3.7`（整数だけの設問） | 断る「小数のない数字（整数）を入力してください」 |
| `1000.1`（上限1000の設問） | 断る「1000 以下の数字を入力してください」 |
| 1兆＋1、400桁の数、`1e308` | 断る「1兆より大きい数字は受け付けられません。桁を間違えていないかご確認ください」 |
| `0x10` `0b101` `1E5` `Infinity` `NaN` `1_000` | 断る「数字で入力してください」（`Number()` は黙って 16 や 5 に変えてしまう） |
| 空欄 | 数字として読まない（**0にはしない**） |

**断り方**: 行ごと落とさない。その設問だけを「点数に入らないもの」として扱い、打たれていた文字はそのまま保存したうえで、取り込み結果の一覧に `設問名（「-5」は0以上の数字を入力してください）` の形で出す。何行目の誰の何がなぜ受け付けられなかったかが、その場で読める。

あわせて、選択肢に点数が設定されていない単一選択の設問で、選択肢の値が数字でないときに「数でないもの（NaN）」が保存されていた不具合を直した（同じく理由つきで断る）。

### 15-3. 計算式の複雑さの上限（`FORMULA_LIMITS`）

| 何 | 上限 | 登録済みの実際 |
|---|---|---|
| 式の文字数 | 2,000 | 最長 52 |
| 括弧の深さ | 50 重 | 最深 2 重 |
| 数・記号・設問IDの個数 | 500 | 最多 20 ほど |

以前は上限が無く、括弧が数千重なった式は計算そのものが続けられなくなり、その項目だけが理由の分からない判定外になっていた。いまは「計算式の括弧が深すぎます（50重までです）」のように、制度をいじる人が直せる言葉で断る。**本番の165件の式はすべて上限のはるか手前にあり、1件も弾かれない。**

計算の結果が無限大になった場合も、「計算の途中で数が大きくなりすぎました。回答に桁の多すぎる値が入っていないかご確認ください」として断る（`kind: "overflow"`）。

なお計算式を編集する画面・受け口は存在せず、式が入るのはシード投入とテンプレート会社の複製だけ。上限は「入ってしまったときに読める形で止める」ための保険である。

## 16. カードの頭の固定を、アンケートの2画面へ広げた（2026-08-12）

§6 の「カードの頭の帯」を、アンケートの**回答**と**組み立て**にも適用した（残課題 K3）。
広げるにあたって、**帯に載せてよいもの／載せないもの**を次の1問で判定している。

> **その情報は、1問ごとに当てはめて判断するものか（＝物差し）。それとも一度読めば済む案内か。**
> 物差しなら帯へ。案内なら本文へ。

| 画面 | 帯に載せたもの（物差し） | 本文に残したもの（一度読めば済む） |
|---|---|---|
| 回答（`/me/forms/[id]`） | まとまりの名前と、そのまとまりの**答え方の決まり**（`SECTION_HELP`。「自分の担当として行ったものだけ はい」「受講しただけは いいえ」「合格したものだけ はい」） | 冒頭の説明文、補足欄の案内、期限（下の操作の帯が持つ） |
| 組み立て（`/admin/forms/[id]`） | 何問目・設問文と、**まとまり／答え方／単位／必須任意**（編集中に選び直す値がそのまま映る） | 集計との紐づけ（開いた本文の先頭へ移した） |

- **回答画面の決まりを帯に置いた理由**: 1つのまとまりに はい/いいえ が10問以上並ぶ。
  決まりが画面の外へ出ると、下のほうの設問だけ違う基準で答えてしまい、
  そのズレは提出後に誰も気づけない（点数に直結する）。
- **組み立ては「編集を開いているカード」だけ固定する**。閉じたカードは2行しかなく、
  貼り付く前に流れ去る。全カードに帯を付けると、設問の一覧としての読みやすさだけが落ちる。
- **一覧・履歴には入れなかった**: 提出済みの回答（`ResponseSnapshot`）・アンケート一覧・
  回答一覧・下見（`FormPreview`）はいずれも**打つ欄が無い**。帯は「参照しながら打つ」ための
  ものなので、打たない画面では場所を取るだけになる。回答一覧の表は `DataTable` の列見出しが
  同じ `--sticky-top` に貼り付いており、役目はすでに果たされている。
- **実測（1280×800、Chrome）**: 帯74px（回答・組み立てとも2行）、上の見出しの帯113px、
  固定ヘッダー56px、下の操作バー60px。入力欄に残る高さは約497px（画面の62%）で、
  §6 の「半分を切らない」を満たす。
- 帯の中身は `ui-rules.test.ts` で固定している(回答画面は節の名前＋決まりの2つだけ・
  同じ説明を帯と本文の2箇所に出さない・組み立ては開いているカードだけ・読むだけの画面には入れない)。

### 16-1. スマートフォン（〜639px）では、回答画面だけ例外で固定する

狭い画面の既定は「固定しない」（残課題 K2）。ただし**実際にスマートフォンで回答する人がいる**ため、
**回答画面だけ**例外にした。組み立て画面（管理者が使う）は既定どおり固定しない。

例外にするにあたり、帯を**名前だけの1行**に縮めた。帯から外した「答え方の決まり」は
**消さずにカード本文の先頭へ移す**（`.card-head-sub-narrow`）。読める場所を変えただけで、
広い画面と狭い画面で同じ文が2つ見えることはない。

実測（Chrome、`preview`、回答画面）:

| 画面の大きさ | 帯の高さ | 入力欄に残る高さ | 割合 | 判定 |
|---|---|---|---|---|
| 375×700（小さめの端末・アドレスバーあり） | 35px | 352px | 50% | 半分を下回らないので固定する |
| 390×844（いまどきの端末） | 35px | 496px | 59% | 余裕あり |

375×700 は基準ぎりぎり（2px）である。**この画面で固定物をこれ以上増やしてはいけない。**
上下の内訳は 固定ヘッダー56 ＋ 見出しの帯140 ＋ カードの帯35 ＋ 下の操作バー118。

### 16-2. 文字盤（スマートフォンのキーボード）が出ている間は、固定を全部やめる

文字盤は見える範囲を半分近く奪うのに、**CSSの高さ（`@media (max-height)`）は変わらない**。
実測（375×見える高さ380）では、固定ヘッダー＋見出しの帯＋下の操作バーだけで314pxが埋まり、
**打っている欄が下の操作バーに隠れた**。

そこで `StickyOffset.tsx` が `visualViewport` を見て、見える高さが1/4以上減ったら
`html[data-keyboard="open"]` を立てる。狭い画面でこれが立っている間は

対応後の実測（375×見える高さ380）: 打っている欄は 270〜314px の位置に見えており、隠れない。

回答を1周通した確認（375×700）: はい／いいえ・数値・Enterでの次の欄・自動保存（11/31 → 26/31）・
提出前の確認まで通り、スクロールに合わせて帯の見出しが

## 17. 確定されないまま放置された評価に気づく仕組み（2026-08-12 追加）

### なぜ必要だったか（気づけなかった本当の理由）

件数の出し忘れではなく、**どの画面も「いま開いている評価期間」しか見ていなかった**ことが原因。

- マネージャーのホーム（`src/app/manager/page.tsx`）は `getOpenCycle()` の1期だけを読む。
- 会社の管理者のホーム（`src/app/admin/page.tsx`）も、開いている期が無ければ直近1期を読むだけ。

そのため **評価期間を締め切った瞬間、その期に残っていた未確定の評価はすべての画面から消える**。
本人には結果が表示されないまま、誰の作業一覧にも出てこない状態になる。

### 何を「放置」とみなすか

> **締め切られた評価期間（`evaluation_cycles.status = "closed"`）に残っている、確定に至っていない分。**

- 経過日数は **期間の終了日（`period_end`）から数える**。締め切り操作をした日時はどこにも保存していない（`cycles.updated_at` は名前を直しただけでも動く）ため、業務側が「いつまでの期か」を答えられる `period_end` を起点にする。
- **進行中（open）の期は含めない**。そちらは既存のホームにすでに出ており、混ぜると「いつ見ても数字が立っている」状態になって読まれなくなる。
- 終了日がまだ来ていない期（締め切り前に `closed` にした期）は落とす。

対象は2種類。どちらも本人から見れば「出したのに何も返ってこない」で同じなので、1つの一覧に並べる。

| 種類 | 状態 | 行き先 |
|---|---|---|
| 確定待ち | 評価はあるが `status = "draft"` | `/manager/evaluations/{id}`（その評価票） |
| 集計待ち | 回答は提出済みなのに評価が未作成 | `/manager/cycles?cycle={id}`（その期の一覧） |

### 何日で色を変えるか

| 経過 | 度合い | 画面の呼び名 |
|---|---|---|
| 0〜13日 | `fresh` | 片付け中 |
| 14〜29日 | `overdue` | 対応が必要 |
| 30日〜 | `long` | 長期間そのまま |

- **14日**: 半期評価で、締め後に集計・面談を終える通常の作業期間。
- **30日**: 超えると次の期がすでに動いており、昇給・賞与の反映時期を逃す。
- 既存データからは所要日数の実績が取れない（本番の確定済み88件は移行時に一括投入で `finalized_at` が全件同日）。数字は実績ではなく**運用の節目**として置いた値であり、変えるときは `OVERDUE_DAYS` / `LONG_DAYS` の2定数だけを直す。

### 誰が、どこで気づくか

| 役割 | 見える範囲 | 場所 |
|---|---|---|
| マネージャー | **自分が上長のメンバーの分だけ**（自分で確定できる範囲） | `/manager` の最上部 |
| 会社の管理者 | **自社の全員分**（上長が異動・退職した分の受け皿） | `/admin` の「次の一手」より上 |
| システム全体管理者 | **会社ごとの件数と最長日数のみ。個人名は出さない** | `/system` の最上部 |

- 置き場所はいずれも**ログイン直後のホームの最上部**。締め切った期はどの一覧からも自然には出てこないため、わざわざ見に行く場所に置くと今までと何も変わらない。
- 全体管理者に個人名を出さないのは、他社の個人名を毎日開く画面へ常時並べないため。誰の分かを見るときは「操作する会社」を切り替えて会社のホームを開く。
- **会社の絞り込みはすべてサーバー側**（`src/lib/stalled.ts`）。画面で隠すだけにはしない。

### 伝え方

数字だけを大きく置かない。見出しに必ず「いちばん長いもので◯日」を添え、行として
**「誰の・どの期の・何待ちか・何日」**を出し、押せばその評価そのものへ飛べるようにする。
件数だけの知らせは、増えても減っても同じ見た目になり、じきに読まれなくなる。

### この仕組みがしないこと

**読むだけ。確定も差し戻しも削除も再集計もしない。** 公開済みアンケートと確定済み評価は一切変わらない。
気づかせるところまでを担当し、扱いは人が決める。

### 置き場所

| 役割 | ファイル |
|---|---|
| 判定・並べ替え・文言（純関数） | `src/lib/domain/stalled-evaluations.ts`（網羅率100%必須の対象） |
| DBから読む・会社の絞り込み | `src/lib/stalled.ts` |
| 画面部品 | `src/components/StalledEvaluationsNotice.tsx` |

### 締め切る前に気づかせる（放置を作らせない側）

放置は「締め切った瞬間」に生まれる。あとから知らせるだけでは、気づくのが必ず1回遅れる。
そこで **「受付を締め切る」の確認の窓に、その期間に残っている未確定の件数と、残っている方の名前を添える**。

- **締め切り自体は止めない。** 期末に締められないほうが業務は詰まる。判断材料を渡すところまでを担当する。
- **0件のときは、これまでどおりの確認文だけ**を出す。件数が0でも一言足すと、毎回読み飛ばす癖がつく。
- 名前は**3人まで**。それ以上は「ほか◯名」。全員を並べると「よろしいですか」が窓の外に出る。
- 名前が未登録の方は空欄にせず「名前未設定」と書く。空欄だと、名前が消えたのか人が居ないのかが読めない。
- **窓を開かなくても辿れるようにする**: 期間の見出しに「未確定 ◯件」を添え、「残っている方を見る」で一覧へ送る。
  窓の中だけに書くと、押す気のない人には最後まで届かない。

| 役割 | ファイル |
|---|---|
| 確認文の組み立て（純関数） | `cycleCloseConfirmText` / `unfinalizedNamePreview`（`src/lib/domain/stalled-evaluations.ts`） |
| 誰が残っているかの読み出し（会社の絞り込みはここ） | `listUnfinalizedNamesInCycle`（`src/lib/stalled.ts`） |
| 画面 | `src/app/admin/cycles/page.tsx`（確認の窓は共通部品の `ConfirmButton` を `ActionButton` 経由で使う） |

締め切る前に数えるので、この経路だけは**まだ締め切っていない期間**を見る（放置日数は数えない）。
締め切ったあとに何日経ったかを数えるのは §17 の本体の役目。

## 18. 文字の段を上げたときに崩れる場所（2026-08-12 追加）

## 19. 本人向けの説明文が、共通の言い換え文に化けていた件（2026-08-12 追加）

### 何が起きていたか

本人（一般の方）に見せる説明文には、**2つの仕組み**が関わっている。

1. **作る側**（`src/lib/domain/scoring.ts`）— 評価を集計するときに、本人向けの説明文を作って保存する。
   点数を含まない文をここで作り切る（表示のときに数字を消す作りだと、消し忘れがそのまま本人に見えるため）。

その結果、**作る側が「昇格に必要な水準に達していません」と書き、ふるいにかける側が「昇格に必要」を弾く**、
という食い違いが起きていた。本人の画面には、上長のための判定内容ではなく、
どの人にも同じ共通文だけが出ていた。

### 同じ理由で化けていた文は4種類あった（洗い出しの結果）

報告されていたのは昇格の理由だけだったが、同じ仕組みなので他にも起きていた。
実際に判定を動かして、本人向けの文を1つずつ検査に通して確かめた。

| どの文 | 引っかかっていた語 | 影響 |
|---|---|---|
| 昇格できない理由（KPI） | 「昇格に必要」 | 報告のあった件 |
| 昇格できない理由（行動指針） | 「昇格に必要」 | 同上 |
| 昇給の理由（点数方式の会社） | 「評価点」「満点」 | **今回新たに見つかった** |

- (B) 検査の当て方を変える ← 一部だけ採用（下記）
- (C) 本人向けの文を最初から別に用意する ← 既にそうなっている（列が分かれている）ので、新たに増やさない

**(A) を主にした理由**: 検査は「本人に他人との比較や内部の基準値を出さない」ための最後の砦で、
**緩めれば必ず漏れる側に倒れる**。一方、言い回しは意味を変えずにいくらでも書き直せる。
危ない側を緩めるのではなく、安全な側を書き直すのが筋と判断した。

## 20. 桁の上限を、数値の受け口すべてに当てた（2026-08-12 追加）

### 20-1. 何が問題だったか

`§15` で決めた「1兆（`MAX_ABS_NUMBER`）を超える数は受け付けない」という決まりが、
実際に当たっていたのは**回答の提出**と**貼り付け・CSVの取り込み**の2箇所だけだった。

設定を作る側の受け口は無制限のまま残っていた。

- **アンケートの設問を作るときの「下限・上限」**（`PUT /api/forms/[id]/questions`）
- **ランク基準の「下限・上限」**（`POST /api/masters` の `rankCriteria` / `rankCriteriaSet`）

どちらも実害は出ていなかったが、それは**別の仕組みがたまたま防いでいた**からにすぎない。
設問の下限・上限は「回答を受け取るときに1兆で止まる」から、
ランク基準は「重なり・隙間の検査（`checkRankBoundaries`）で隣と繋がらなくなる」から止まっていた。

**止まる場所が1つしかない状態は危うい。** その1つの仕組みを直したり並べ替えたりした瞬間、
何の予告もなく穴が開く。しかも「なぜ止まっていたのか」がコードのどこにも書かれていないため、
外した本人にも気づけない。だから、防波堤ではなく**受け口そのもの**に決まりを置き直した。

さらに、設問の下限・上限が無制限であることには固有の危うさがあった。
極端な上限（たとえば 10の30乗）を1つ置くと、**その設問を通るすべての回答の許容範囲がその値になる**。
つまり回答側の検査が実質的に無効になり、「回答側で止まるから大丈夫」という前提そのものが崩れる。

### 20-2. どう直したか — 新しい基準を作らない

**上限の値と断り文は1箇所（`src/lib/domain/number-input.ts`）にしか置かない。**
経路ごとに違う上限を作ると「画面からは通るのに取り込みでは落ちる」といった、
誰にも説明できない食い違いが生まれる。既存の `MAX_ABS_NUMBER`（1兆）と、
既存の断り文をそのまま使い回す共通の入口を1つ足しただけにした。

```
checkNumberMagnitude(label, value) → { ok: true } | { ok: false, message }
```

`label` には**利用者が画面で見ている名前**を渡す(設問名・ランク名・選択肢名)。
「エラーが発生しました」ではなく「**どの欄が、なぜ**受け付けられないか」を返すため。
空欄（`null` / 未指定）は「決めていない」という意味なので、ここでは何も言わない。

当てた場所（すべてサーバー側。画面の入力制限だけにはしない）:

| 受け口 | 対象 | 断り文の例 |
|---|---|---|
| `PUT /api/forms/[id]/questions` | 設問の下限・上限 | 「◯◯」の上限（1e+21）は1兆（1000000000000）より大きい数字は受け付けられません。桁を間違えていないかご確認ください。 |
| 同上 | 選択肢の点数 | 「◯◯」の選択肢「はい」の点数（…）は… |
| `checkRankBoundaries`（ランク基準A〜E） | 下限・上限 | ランクBの下限（1e+15）は… |
| `POST /api/masters` の `rankCriteria` | 下限・上限 | ランク基準の下限（…）は… |

ランク基準は `checkRankBoundaries` の**中**に置いた。ここは画面・単体保存・A〜E一括保存の
**3つの経路すべてが通る唯一の場所**なので、1箇所に書けば取りこぼしが出ない。

### 20-3. 桁の検査を、なぜ他の検査より先に出すのか

1兆を超える値を1つ置くと、隣のランクとは必ず繋がらなくなる。そのまま繋がりの検査に流すと
「ランクBとCが繋がっていません」とだけ言われるが、**本当の原因は桁の打ち間違い**であり、
言われたとおりに隣を直しても直らない。原因を指す言葉を先に出し、
そのとき繋がりの話は混ぜない（原因が2つあるように見えると、どちらを直すか分からなくなる）。

桁の打ち間違いには「直し方の提案」（`fix`）を付けない。正しい値はこちらには分からないため。

### 20-4. 既存データが弾かれないことの確かめ方

**決める前に、本番の実データで確かめた。**弾かれるものが1件でもあれば、
上限そのものを考え直す必要があったため。

## 21. ご本人にも「まだ確定していない」という事実を出す（2026-08-12 追加）

§17 で、締め切ったのに確定されていない評価をマネージャー・会社の管理者・全体管理者が
見つけられるようにした。**ご本人（一般）にだけは何も出していなかった**（残課題 N3）。
アンケートを出したあと確定されるまで、本人の画面には結果が並ばない。それが
「まだ途中だから」なのか「自分の提出が届いていないから」なのか、本人には区別がつかない。
**出したのに何も返ってこない状態が、本人からは見えないまま**だった。

### 判定は増やさない

§17 の判定（`buildStalledRows`）の結果をそのまま受け取り、**削るだけ**の関数を足した。
本人向けに別の判定を作らない（判定が2つあると、片方だけ直る日が必ず来る）。

| 役割 | ファイル |
|---|---|
| 本人向けのまとめ・見出し（純関数） | `src/lib/domain/stalled-evaluations.ts` の `myPendingCycles` / `myPendingHeadline` / `MY_PENDING_BODY` |
| DBから読む・**ご本人の分だけに絞る** | `src/lib/stalled.ts` の `listMyPendingCycles` |
| 画面部品 | `src/components/MyPendingResultsNotice.tsx` |
| 置き場所 | `src/app/me/results/page.tsx`（「評価の結果を見る」） |

### 何を出さないか（意図的な欠落）

| 出さないもの | 理由 |
|---|---|
| **経過日数**（何日そのままか） | 本人は確定を自分で進められない。「45日そのまま」は、できることが何も増えないまま焦りだけを増やす。日数は**動かせる人の画面にだけ**置く |
| **確定待ち / 集計待ちの区別** | どちらも本人から見れば「出したのに返ってこない」で同じ。社内の作業がどの段で止まっているかは本人の関心事ではなく、区別すると「集計待ちのほうが遅い」といった本人には確かめようのない読み方を生む。期ごとに1件へ畳む |
| **他の人の状況・件数・社内の基準値** | 比較はご本人の画面に置かない。部品は氏名・等級・点数を一切受け取らない作りにしてある |
| **催促の導線**（上長へ知らせる・急かす） | 評価という関係の中では、本人から上長を突く形は角が立つ。ここは事実だけを置く場所とする |

見出しに「放置」「遅れ」という言葉を使わないことは試験で固定してある
（`myPendingHeadline` + `MY_PENDING_BODY` に「日」「放置」「遅」「催促」「急」が現れないこと）。
**§19 の本人向け文の検査（`src/lib/domain/employee-text-guard.test.ts`）にも、この2文を通してある。**
点数・配点・基準値をひとつも含まないため、そのまま通る。

### 置き場所を「評価の結果を見る」1画面にした理由

ログイン直後のホーム（`/me`）には出さない。ホームは**「今やること」を出す場所**で、
本人がこの件でできることは無い。行動につながらない知らせをホームの先頭に置くと、
本当に手を動かすべき「アンケートに回答する」が押し下げられる。
本人が結果を確かめに来る画面に置き、来たときに必ず答えが返るようにした。

### 言い方

- 1期だけのときは期の名前を言い切る（「「2025年度 下期」の評価は、まだ確定していません」）。
- 複数期あるときは期の数だけを言い、期の一覧を並べる。並びは**終了日の新しい順**
  （動かせる人の一覧は放置の長い順。本人の画面で古い期を先頭に置くと、遅れの大きさを順位づけて見せることになる）。
- 説明は必ず「ご提出いただいた内容は受け付けられています」から始める。本人がまず疑うのは
  「自分の回答が出せていないのではないか」で、そこを打ち消さないと出し直しの問い合わせが増える。
- まだ確定していない期があるときは、これまでの「確定した評価はまだありません」を出さない
  （空の理由を2回言うと、どちらが自分の話か分からなくなる）。

### この仕組みがしないこと

§17 と同じく**読むだけ**。確定・差し戻し・削除・再集計は一切しない。
ご本人の絞り込みは `listMyPendingCycles` の中でログイン中の本人のID（`viewer.id`）により行う。
**画面から渡された値では絞らない**（他人のIDを入れれば他人の状況が読めてしまうため）。


## 22. 説明文の量と出し方をそろえた（2026-08-12 追加・全画面共通）

### きっかけ

発注者から画面を名指しで指摘があった。

> 説明文や注意事項の記載が多くて煩わしい。
> 1文が長くて読みにくい。全ファイルで1文40文字以内にする仕組みを作ってほしい。
> 全部を1行で表現しないで、ちゃんとUI/UXとして構成してほしい。
> 既定で出す必要があるかを見直してほしい。表示するものが多いほど煩わしくなる。
> これは全ての画面で共通です。

さらに、直しの方向について次の指針をもらった。

> 情報は多ければ多いのが正解ではない。**一旦引き算した上で、表示方法をどうプラスするか**で見直すこと。
> ただし**今使っている情報は全て反映させておくこと**。
> 削除する・非表示にして見えなくする方向はやめること。見え方・見せ方を変えること。

つまりこの回のゴールは「文を減らすこと」ではない。
**情報の総量は1つも減らさないまま、既定で目に入る量だけを減らす**ことにある。

### 22-1. 1文40文字（機械で強制する）

`src/components/ui-rules.test.ts` に検査を足した。
利用者の目に触れる日本語の文を句点「。」と改行で切り、**1文が40文字を超えたら落ちる**。

- 対象は `src/` 配下の `.ts` / `.tsx` 全部（**除外ファイルは1つも作っていない**）。
  文字列リテラルと、`.tsx` の地の文（タグとタグの間に直接書いた日本語）の両方を読む。
- **開発者向けの注釈（`//` と `/* */`）は数えない。** 利用者の目に触れないため。
- **差し込み（`${...}` / `{...}`）の中身は長さに数えない。**
  アンケート名・会社名・等級名・設問名は実行時に決まる値で、書いた人が長さを決められない。
  数えるのは**文の骨格**だけ、という線引きにした。骨格が短ければ、あとは折り返しの仕事になる（22-3）。
- 検査そのものが痩せないよう、**網の広さも検査している**
  （`src/` 配下180ファイル以上、`page.tsx` が41枚以上、`app/`・`components/`・`lib/domain/` の
  それぞれで10ファイル超を読んでいること）。一部しか見ていない検査が一番危ない。
- 40文字ちょうどは通り、41文字で落ちることも検査で固定した。

**この上限を緩めない。**緩めた瞬間に、今回の指摘がそのまま戻る。

### 22-2. 引き算の基準（何を既定で出し、何を畳むか）

画面ごとに「**いま この瞬間に必要か**」で分けた。基準はこの2つの表がすべて。

既定で出す（畳まない）:

| 出すもの | 理由 |
|---|---|
| いま何をする画面か（見出し・件数・状態） | これが無いと画面の用が分からない |
| その操作の結果を左右する事実（締切・公開済みか・残り件数） | 畳むと、知らずに操作して事故る |
| 取り返しがつかない操作の警告（消える・戻せない） | 見落とすと損害が出る。畳んではいけない |
| 「できない」という事実そのもの＋次の一歩1つ | 無言の読み取り専用・無言の空表示を作らない（§5-2） |

畳む（押すと出る）:

| 畳むもの | 理由 |
|---|---|
| なぜそうなるのかの理由・背景・制度の考え方 | 1度読めば足りる。毎回目に入る必要が無い |
| 仕組み・計算式の解説 | 同上 |
| 手順・書式の詳しい説明 | 使う人が使うときにだけ要る |
| 名前の列挙（どこで使っているか等） | 行ごとに違うが、普段は件数で足りる |
| **同じ文が3行以上に繰り返されるもの** | 行から外し、1か所にまとめる（下の 22-5） |

### 22-3. 長い文が来ても読める形で折り返る

骨格を短くしても、差し込まれた名前が長ければ表示は長くなる。そこで `globals.css` の `body` に
日本語の折り返しの決まりを1か所だけ置いた。

```
line-break: strict;        /* 句読点・小書き文字を行頭に置かない */
overflow-wrap: break-word; /* はみ出す長い連続文字だけ折る */
word-break: normal;        /* 語の途中では折らない（既定） */
```

**`word-break: break-all` をどこにも書かない**ことを検査で固定した。
これを当てると日本語が意味の切れ目を無視して1文字ずつ折れ、かえって読めなくなる。

### 22-4. 畳んだものへ必ず手が届く（畳む＝隠すにしない）

「畳んだが開き方が無い」「畳んだことに気づけない」は、発注者の言う**非表示と同じ**になる。
そこで畳む仕組みを3つに限定し、機械で検査した。

| 仕組み | 使う場面 | 実体 |
|---|---|---|
| その場で開く | 行やカードの中の短い補足 | `<InlineDetail summary="…">`（`src/components/ui.tsx`） |
| まとめて1か所 | カード1枚ぶんの長い節・全行で同じ説明 | `<Disclosure summary="…">`（同上） |
| 窓で開く | 手順・書式・仕組みなど読み切るもの | `<DetailDialogButton label="…">`（`src/components/ConfirmButton.tsx`） |
| 畳まない | 取り返しのつかない操作の警告 | `<ReasonNote>` などその場に出す |

検査の内容:

- **`<details>` を書いてよいのは `src/components/ui.tsx` だけ。**画面ごとに書き起こさない。
- 畳んだものには必ず押す場所がある（`summary` / `label` を省略できない型にした）。
- 押す場所を `display: none` で消せない（CSS も検査対象）。
- 押す場所は押せる見た目である（`cursor: pointer` と ＋／－ の印）。
- 読むだけの窓を作ってよいのも `ConfirmButton.tsx` だけ（既存の決まりのまま）。
- 窓には必ず「閉じる」がある。

### 22-5. 赤枠で名指しされた箇所（等級要件の一覧）の直し方

指摘のあった元の文はこれ。

> アンケート「A」・アンケート「B」ほか2件で使っているため、完全には消せません。「使わない」なら次のアンケートから外せます。

1文に3つのことが入っている（①使っている場所の列挙 ②消せない理由 ③代わりの手段）。
しかも②③は**どの行でも全く同じ文**で、項目数ぶん繰り返す意味が無い。分解した。

| 元の要素 | 直したあとの置き場所 |
|---|---|
| ①使っている場所 | 行には「使用中（◯件）」だけ。押すと場所が出る（`InlineDetail`） |
| ②消せない理由 | カードの下に1か所（`Disclosure`）。消せない行があるときだけ出す |
| ③代わりの手段 | 同上 |

情報は1つも減っていない。置き場所と、出るきっかけを変えただけ。
また、画面を経由せず API を直に叩いて断られたときの手がかりを残すため、
**サーバーの返事（`deleteBlockedReason`）には使っている場所を今までどおり含めている**
（`master-delete.test.ts` で固定）。

### 22-6. 短くするときにやってはいけないこと

- **本人向けの説明文を、共通の言い換え文に置き換えない。**
  §19 の事故（本人に見せてはいけない基準値の話が共通文に化けた）と同じ落とし穴がある。
  文を短くした結果 `src/lib/domain/employee-text-guard.test.ts` に引っかかったら、
  **検査ではなく言い回しのほうを直す。**検査は1文字も緩めない。
- 権限の判定はサーバー側のまま。**表示を畳んでも、誰に見せるかの判定は一切変えていない。**
- 公開済みアンケートと確定済み評価が変わらないという事実を伝える文は、短くはしても消さない。

### 22-7. 全画面を実際に描画して確かめた

書いてある文を短くしても、**差し込まれた名前が長ければ表示は長くなる**。
そこは実際に描いてみないと分からないので、道具を作って repo に置いた。

`scripts/scan-rendered-text.mjs`

- 4つの役割（全体管理者・会社管理者・上長・本人）でログインする。
- 引数の要らない経路28件を全部取りに行き、
  そこに出てきたリンクから `[id]` つきの経路（アンケート・社員・評価・回答など）を辿る。
- タグを外し、「。」と改行で文に切って40文字超を数える。

|---|---|---|
| 会社が登録した文章そのもの（KPIの設問文・計算式・備考） | 16／170 | 利用者自身が書いた内容。こちらで書き換えない。折り返しで読めるようにする（22-3）。入力するときに長さを知らせる案は残課題 T1 |

### 22-8. 理由の列挙は、文ではなく並びで出す

「◯◯（B）、△△（B）、□□（C） がA未満のため、昇給は見送りです」のように
項目名を1文へ詰めると、**項目が増えた分だけ文が伸びる**。文を分けても直らない
