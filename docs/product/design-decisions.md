# 前例のない設計判断の記録

規範（Skill `jp-web-design` / `ux-design`）に明示が無い、または規範の既定とは違う形を選んだときだけ、ここに1件1ブロックで残す。通常の表示形式・ラベル・加工の判断は書かない（それは各画面の実装とテストが正本）。

書式: 場面の1文 / 選んだ形 / 決め手の軸 / 却下した候補と理由。

## DD-001 畳んだメニューを「隠す」から「絵だけの列（68px）」に変えた（2026-08-15）

- **場面の1文**: 管理者が制度設定・評価・名簿のあいだを日に何度も往復しながら、本文を広く使いたくてメニューを畳んでいる。
- **選んだ形**: 1024px 以上では、畳んだときに幅 68px の絵だけの列を残す。乗せたときとキーボードで移動したときの両方で、右側に名前の吹き出しを出す。名前は `aria-label` にも必ず渡す。
- **決め手の軸**: 識別の手がかり（往復先が15項目以上あり、完全に隠すと毎回開いて閉じる操作が挟まる）。畳む目的は本文の幅であって、行き先を捨てることではない。
- **却下した候補と理由**:
  - 完全に隠す（従来の実装）: 本文は最も広くなるが、行き先を選ぶたびに開閉2操作が増える。往復の多いこのアプリでは費用のほうが大きい。
  - 640〜1023px でも絵の列にする: この幅は本文の1カラムが既に狭く、68px を削ると表が潰れる。重ねて開く引き出しのまま据え置いた（残課題 UX-022）。
- **規範との関係**: `jp-web-design` は「アイコン単独ボタンを作らない／迷ったらアイコンなし」を既定にするが、同スキルの `references/layout-responsive.md`「ナビゲーション骨格」は 641〜1024px で 68px のアイコンレールを認めている（`aria-label` 必須・吹き出し（tooltip）だけに意味を隠さないことが条件）。前例のない部分は、1024px 以上でも畳んだときに 68px の列を出すことと、規範が想定する項目数4〜5に対して本アプリは15項目以上あることの2点。そのため「同じメニューの中で絵を重複させない」をテスト（`src/lib/nav.test.ts`）で固定した。
- **併せて反転した記述**: `src/components/AppSidebar.tsx` にあった「閉じるときは『アイコンだけ残す』のではなく完全に隠す」というコメントは、この判断で置き換えた。

- **場面の1文**: 20以上の画面に絵を足すが、同じ意味に別々の絵が付くと、絵そのものが読み飛ばされるようになる。

## DD-005 長押しドラッグを Pointer Events で自作した（2026-10-13）

- **場面の1文**: 管理者が等級要件・昇格の条件・設問・選択肢を、スマホでも PC でも並べ替えたい。
- **選んだ形**: `useLongPressReorder` を自作する。タッチは 350ms 動かさずに押し続けると持ち上げ、その前に 8px 動けばスクロールとみなす。キーボードは Space で持ち上げ、↑↓で動かし、Space で置き、Esc で戻す。矢印のボタン（先頭・上・下・末尾）も残す。保存は並び全体を送り、id の集まりが違えば 409。
- **決め手の軸**: 依存を足さないことと、タッチで動くこと。
- **却下した候補と理由**:
  - HTML の Drag and Drop API: タッチの端末で動かない。
  - dnd-kit: 依存が増え、Worker の実行ファイルの上限（3,072 KiB）に近づく。この画面の数なら自作の費用が小さい。
- **規範との関係**: WCAG 2.2 SC 2.5.7（ドラッグの代替）を、矢印のボタンとキーボードで満たす。
- **固定した検査**: `src/components/reorder/useLongPressReorder.test.ts`・`src/lib/domain/reorder.test.ts`。
- **見直す条件**: 画面をまたぐ移動（別の一覧へ落とす）が要るようになったら、ライブラリを比べ直す。
- **更新（2026-10-16、不具合の修正）**: 等級要件で、ドラッグで並べ替えてから、もう一度ドラッグで元に戻すと行が消えた（再読み込みで戻る）。
  - 原因（下の追記で改めた）: 行の段組みを、一覧の幅のコンテナクエリ（`container: reorder / inline-size`）で決めていた。Chromium では、size container の中の一覧を2回続けて並べ替えると、2回目の保存のあと行の箱が作られず、何も描かれない（[issues.chromium.org/379030050](https://issues.chromium.org/issues/379030050) と同じ形）。矢印のボタンで2回続けても起きる。一覧を `contain: inline-size` だけにすると起きない。
  - 選んだ形: `ReorderList` が ResizeObserver で一覧の幅を測り、超えた境目（30・36・60rem）を一覧の `data-reorder-w` に書く。CSS はこの値で段組みを選ぶ。測るまでは同じ境目をコンテナクエリで当て（`.reorder-list:not([data-reorder-w])` にだけ container を置く）、読み込みのたびに行が狭い段組みから跳ねないようにする。並べ替えるころには測り終えているので、不具合の条件に入らない。`contain: inline-size` は残す（一覧の幅を中身から切り離し、印の書き換えで測り直しが続かないようにする）。境目の規則は `:where()` で包み、コンテナクエリで書いていたときと詳細度を同じにした。段組みは修正の前と画素まで同じ。
  - 却下した候補と理由: 画面の幅のメディアクエリ（サイドバーの有無で、一覧の幅が画面の幅と合わない。1024px と 900px で一覧の幅が逆になる）。コンテナクエリのまま、保存のあとに一覧の style を触って描き直させる（不具合の形に頼る回避で、起きる時機を外すと効かない）。
  - ほかの size container（`.split-host`・`.list-host`・`.record-list`）は、サーバーが描く一覧で、画面の中で行を並べ替えないので変えない。
  - 固定した検査: `src/components/reorder/ReorderList.test.ts`（境目の書き方、CSS の境目が部品の境目と同じこと、container を測る前の一覧にだけ置くこと）、`e2e/reorder-twice.spec.ts`（ドラッグと矢印で2回続けて並べ替えても、行が見えたまま）。DD-017 の直しより前の版では、修正前の規則（一覧を size container にする）を画面に足すと、ドラッグの検査は2回目の保存のあとで行が読み上げの木からも消えて落ちた。矢印のボタンだけでは起きない（2026-10-16 に確かめた。DD-017 の後は落ちない。下の追記）。
  - 見直す条件: ResizeObserver と印（`data-reorder-w`）の二重の CSS を外してコンテナクエリだけの形へ戻すかは、次のどちらかで比べる。上の不具合の修正（[issues.chromium.org/379030050](https://issues.chromium.org/issues/379030050)）が対象のブラウザに行き渡ったとき。印を使わない形で `e2e/reorder-twice.spec.ts` が通ったとき（2026-10-16 に DD-017 の直しで満たしたが、害が無いので保険として残す。下の追記）。外すときは `ReorderList.test.ts` と `list-row-shape.test.ts` の形の検査を緩めず、戻した形を確かめる検査に置き換える。
- **追記（2026-10-16、同じ日に原因を改めた）**: 本当の引き金は、並べ替えそのものではなく、一覧を包む fieldset（`disabled={saving && !reordering}`）の直下に、保存のたびに RefreshStatus が出入りすることだった（DD-017）。並べ替えは、同じフレームで size container の中身を変える側の条件にあたる。上の「ほかの size container は、画面の中で行を並べ替えないので変えない」は、この見立て違いの上に立っていた。DD-017 で fieldset の中身を包んだあとは、上の古い規則（一覧を常に size container にする）を戻しても行は消えない。ResizeObserver の形は害が無いので残す。

## DD-011 人の一覧は、手元の配列で探して並べ替え、選べる並べ替えを権限で決めた（2026-10-14）

- **場面の1文**: 利用者一覧・社員の一覧・メンバー一覧で、名前・会社・役割・点数・等級で並べ替え、名前などで速く探したい。会社順はシステム全体管理者だけ、のように権限ごとに選べるものを変えたい。

- **決め手の軸**: 打つたびに待たないこと（数百人なら手元の方が速く、通信が要らない）と、見てはいけない値で当たらないこと（S6 のサーバーで落とす作法を、並べ替えと検索にも保つ）。
- **却下した候補と理由**:
  - サーバーで検索して並べ替える（SQL の LIKE と ORDER BY）: 打つたびに通信して待つ。D1（SQLite）の LIKE は、全角半角・カタカナとひらがなの違いを同じに扱えない。一覧は数百人で、まとめて返しても重くない。

  - 並べ替えの種類を全員同じにし、権限の無い値は空として並べる: 会社が1つしかない一覧で会社順を選んでも変わらず、点数を見られない人に点数順を出すと、並びから点数の高低が読めてしまう。
  - 見えない値（メモ・役割の内部の値）も検索の対象にする: 画面に無い理由で行が出て、なぜ当たったのか分からない。
  - 検索の正規化をヘッダーの検索（§25-3 の `normalizeKey`）と1つにする: ヘッダーの検索の当たり方まで変わり、仕組みも複雑になる。2026-10-14 に利用者が「別のままにする」と決めた。
  - 社員の一覧で、利用停止の人を別の節に分けたままにする: 退職した人の情報をあとから確かめたいとき、検索と並べ替えが効かない。2026-10-14 に利用者の要望で同じ一覧に入れ、ほかの2つの一覧とそろえた。
- **規範との関係**: 規範に定めが無い。
- **固定した検査**: `src/lib/domain/people-list.test.ts`（正規化・AND・見えない欄で当たらない・値の無い行は末尾・選べる並べ替え・URL の読み書き）、`src/components/PeopleList.test.ts`（選べない並べ替えを出さない・人数の読み上げ・利用停止の見た目・3つの一覧が利用停止の人も同じ一覧に入れる）、`src/lib/score-visibility.integration.test.ts`（一般の社員の応答に等級の並びを含めない）、`e2e/people-list-navigation.spec.ts`（書き戻しを待たずに会社の札へ進んでも検索語を引き継ぐ・戻ると URL の検索語と並びに戻る）。全社の等級順は会社名のあとに会社IDでまとまりを分け、同名の別会社を混ぜない（`people-list.test.ts`）。

## DD-015 アンケートの設問の集計との紐づけは、保存のときにサーバーが保存済みの値と突き合わせる（2026-10-16）

- **場面の1文**: 管理者が下書きのアンケートを組み立て画面で直して保存する。画面は紐づけ（等級要件・昇格要件・行動指針・KPI 項目と設問の key）と昇格の必須要件の印を引き継ぐだけだが、保存の処理（`saveFormQuestions`）は送られてきた値をそのまま書いていた。点数の計算（`evaluate.ts`）はこの値をそのまま読むので、自由設問を昇格の必須要件にする・別の会社の要件の id を入れる・作り直しの前に開いた古い画面から古い紐づけを書き戻す、のどれもが通っていた。紐づけのある設問の答え方を画面で変えると（KPI の数値 → 文章、等級要件のはい/いいえ → 数値）、点数の計算から黙って外れていた。

## DD-016 実績の聞き方（設問のひな形）を、KPI項目の画面で決められるようにした（2026-10-16）

- **場面の1文**: 評価セットで選んだ KPI 項目のうち、設問のひな形（`kpi_questions`）の無い項目は、アンケートを作っても「設問を作り直す」を押しても設問が出ず、点も付かなかった。ひな形はシード投入とテンプレート会社の複製でしか入らず、画面で足した KPI 項目には必ず無かった。比べる警告（DD-012）は同じ日の2つ目の案で「使うKPIを選ぶへ戻して選び直す」を出していたが、評価に使う項目そのものを替えさせる回り道だった（[spec §28-15](./spec.md#28-15-kpi-項目の実績の聞き方2026-10-16-の追加要望)・§22-9）。

- **却下した候補と理由**:

## DD-017 保存中に止める入力の束（fieldset）は、中身を div 1つで包む部品（FieldGroup）だけで作る（2026-10-16）

- **場面の1文**: 新しい KPI 項目の「実績の聞き方」で「＋ 聞くことを追加」を1回押すと、足した聞くことと追加のボタンが消え、2つ目を足せなかった（再読み込みで戻る）。DD-016 の画面を本物の流れで確かめていて見つけた。
- **原因**: Chromium の描画の不具合（148・153 で確かめた。155 は未確認）。fieldset の中に size container（`container-type: inline-size`。`.split-host`・`.list-host`・`.record-list`・`.list-rows`・測る前の並べ替えの一覧）があり、同じフレームの中で次の2つが重なると、container の子孫の箱が作られない。
  - container の中身が変わる（子の削除や文字の変更）。
  - fieldset の直下に子が足される・消える。

  箱は高さ0になり、読み上げの木からも消え、フォーカスは body へ落ちる。画面の幅を変えても戻らない。アプリを使わない最小の HTML で再現した。div・section・form の下では起きない。fieldset の disabled の切り替えや、子を hidden にするだけでも起きない。fieldset に display（grid・flex・flow-root・contents）・`contain: layout`・`container-type` を当てても防げない。聞き方の欄では、押すと並びの中身が変わり、同じフレームで fieldset の直下に計算式の欄が足される。
- **選んだ形**: `src/components/ui.tsx` の `FieldGroup`。fieldset の reset（`m-0 min-w-0 border-0 p-0`）と legend（任意）を持ち、中身を必ず div 1つで包む。子の出入りは div の中で起き、fieldset の直下は変わらない。アプリの fieldset 10か所（自分の情報・実績の聞き方・行動指針・評価セットの共通設定・基準セット・昇格要件・等級要件・KPI項目・アンケートの回答・アンケートの組み立て）を置き換えた。並べ方の class（`stack`・`profile-rows`）は中の div へ、外の余白（`mt-4` など）は fieldset に置く。legend は読み上げの名前になるよう fieldset の直下に置く（出入りしないので包まない）。
- **決め手の軸**: 不具合の引き金を、置き場所ごとの気配りではなく、部品の形で起こせなくすること。保存のたびに出入りする ReasonNote・RefreshStatus を fieldset の直下に置く書き方が多くの画面にあり、次にどこで起きてもおかしくなかった。
- **却下した候補と理由**:
  - 聞き方の欄だけを直す（追加の行の size container を外すなど）: ほかの9か所に同じ形が残る。size container は一覧の段組み（DD-014）で使い続ける。
  - fieldset をやめて div にし、`aria-disabled` を付ける: 保存中に入力をまとめて止める働きを自前で作り直すことになる。fieldset の disabled は、入力・ボタン・選ぶ欄を一度に止める。
  - fieldset に display や contain を当てる: 試した形はどれも防げなかった。
  - Chromium で直るのを待つ: 直った版がそろうまでの間、利用者の画面で入力が消える。
- **DD-005 との関係**: DD-005 の不具合（並べ替えを2回続けると行が消える）も、本当の原因はこれだった。等級要件の一覧は `disabled={saving && !reordering}` の fieldset の中にあり、保存のたびに RefreshStatus が直下に出入りする。直した版に、DD-005 で外した規則（一覧を常に size container にする）を戻しても、ドラッグでも矢印でも2回続けて並べ替えて行は消えない。同じ版で、さらに包みの div を `display: contents` で無効にすると、ドラッグの2回目のあとで3行とも高さ0になり、読み上げの木からも消えた（Chromium 153、2026-10-16）。DD-005 の ResizeObserver の形は、害が無いので残す。
- **規範との関係**: fieldset と legend で入力のまとまりを伝える形（WCAG 2.2 SC 1.3.1）は変えない。
- **固定した検査**: `src/components/fieldset-group.test.ts`（生の `<fieldset>` を ui.tsx の外に書かないこと・包みの形）、`e2e/kpi-asking-add.spec.ts`（新しい KPI 項目で聞くことを2回続けて足しても、聞くことと追加のボタンが見えたまま。直す前の版では1回目のあとで落ちる）、`e2e/reorder-twice.spec.ts`（DD-005）。
- **見直す条件**: Chromium で直ったことを確かめ、対応する版がそろったら、包みを外すかを比べる（包みに害は無いので急がない）。fieldset でない器（dialog など）で同じ形が見つかったら、部品の範囲を広げる。

## DD-018 操作の帯の押す場所を、状態の文の長さで動かさない（2026-10-16）

- **場面の1文**: アンケートの回答画面（`/me/forms/[id]`）で、数値の欄に入れたまま「内容を確認して提出する」を1回押すと、確認の欄が開かず空振りした（押したのに何も起きない）。「アンケートを送信できないように思う」という利用者の問いを、本物の流れで確かめていて見つけた（[spec §6](./spec.md#6-常時表示要素適用範囲)・§28-16）。
- **原因**: 次の連鎖。ブラウザの不具合ではなく、仕様どおりに動く CSS が生むもろさ。
  1. ボタンを押し下げると、数値の欄からフォーカスが外れる。
  2. `NumberField` は、欄を離れたときに、値が変わっていなくても親へ値を渡していた。
  3. `FormAnswer` はそれを入力とみなして下書きの保存を予約し、「保存済み HH:MM」を消した。帯の状態の文は、長い案内（「入力すると自動で保存されます」）に変わった。
  4. 帯（`.action-bar-inner`）は `flex-wrap: wrap` と `justify-content: space-between` で並べ、状態の文の幅は文の長さで決まっていた。伸びた文とボタンが1行に収まらなくなり、ボタンが次の行の左端へ回った。
  5. 指を離したときには、指の下にボタンが無い。押し下げと離しが別の要素で起きたので、click にならない。保存が済むと文が短くなり、ボタンは元の場所へ戻る。

  実測（1280px、Chrome）: 帯の中身の幅 992px、ボタン 199px。状態の文が「保存済み HH:MM」で幅 689px のときは1行に収まり（ボタンの x=1061、帯の高さ 60px）、長い案内で 778px になると折り返した（ボタンの x=268、帯の高さ 94px）。欄を離れた直後（0ms）から折り返し、1.5秒後に保存が済んで戻った。跳ぶかどうかは「状態の文の長さ × 画面の幅」で決まり、締切の注記（延長の有無で長さが違う）などのデータでも変わる。639px 以下はボタンが常に別の行にあるので起きない。それまでの E2E は選ぶ設問だけを押して提出しており、この経路を通らなかった。
- **選んだ形**:
  1. 押す場所を、状態の文の長さで動かさない。状態の文は基準の幅を固定して自分の欄の中で折り返し、折り返すかどうかを画面の幅だけで決める（CSS の値と折り返しの決まりは [spec §6](./spec.md#6-常時表示要素適用範囲)）。状態の欄が空なら欄ごと畳む（`flex-basis: 0` だけだと、狭い画面で空の1行と行の間隔が残る）。
  2. ボタンは帯の右端・下端にそろえる。文が2行に増えて帯が高くなっても、帯は画面の下に貼り付いているので、ボタンの右端と下端は動かない。
  3. 部品は `StickyActionBar` の1つだけなので、帯を出す画面（spec §6）のすべてにそろって効く。どの画面もボタンは今と同じ右端で、違うのは次の行へ回ったときに左端でなく右端に置かれることだけ。
  4. 引き金も断つ。`NumberField` は、前に親へ渡した値と同じなら知らせない（打っている間・貼り付け・欄を離れたときの3つの経路）。`FormAnswer` は値が同じなら何もしない（いくつでも選ぶ設問の配列は中身で比べる）。選んだ選択肢は数と並びで比べ、並びが違うものは別の値とみなす（選んだ順に保存されるため）。値が変わったら「保存済み」を消す決まり（spec §27-4）はそのまま。
  5. 回答画面の帯の状態は事実だけにし、自動で保存する案内は帯から外して本文の頭に置く（5つの文は spec §6）。
- **決め手の軸**: 押す場所の安定（押し下げてから離すまでのあいだに、押す的を動かさない）。状態の文の長さは、文言・データ・画面の幅で変わる。1つずつ文を短くするのでなく、文の長さが配置に効かない形にする。
- **却下した候補と理由**:
  - grid で状態とボタンの2列にする: ボタンが最大5個になる改善要望の一覧（`/admin/improvements`）で、`auto` の列が状態の文を 0 幅まで潰しうる。flex なら、ボタンの束が入りきらないときだけ次の行へ回せる。
  - コンテナクエリで帯の幅を見て並べ方を変える: DD-017 と同じ判断。size container を増やさない。
  - 締切の注記を帯から外す: 回答している間ずっと見えている場所から締切が消える。文の長さが配置に効かなければ、外す理由が無い。
  - 状態の文を「…」で切る: 締切や延長の文が途中で読めなくなる。
  - 帯を常に2段にする: 縦の場所を食い、入力欄に残る高さが減る（§6 の「半分を切らない」）。
  - `setSavedAt(null)` をやめる: 値が変わったときに「保存済み」を消すのは正しい（`form-freshness-regression.test.ts`）。直すのは、変わっていないのに変わったと知らせるほう。
  - 押し下げ（mousedown）で提出する: 押し下げたあとに指をずらして取り消す、ができなくなる（WCAG 2.2 SC 2.5.2）。
- **DD-005・DD-017 との関係**: 同じ族。3件とも「保存のたびに画面の一部が出入り・伸び縮みし、押している・動かしている的の場所や箱が変わる」形で、単体の試験ではなく本物の流れで見つかった。違いは原因の置き場所。DD-005・DD-017 は Chromium の描画の不具合（size container の子孫の箱が作られない）で、DD-005 は一覧の幅の測り方で、DD-017 は部品の形（`FieldGroup`）で引き金を避けた。今回はブラウザの不具合ではなく、flex の折り返しが仕様どおりに動いた結果で、帯の CSS の決まり（文の長さで並びが決まる）そのものを改めた。どれも、保存の状態の変化を、押す場所や箱へ波及させない向きにそろえている。
- **規範との関係**: `jp-web-design` の操作領域（押す場所を動かさない）に従う。WCAG 2.2 SC 2.5.2（押し下げでは実行しない）を守ったまま、押す場所のほうを安定させた。配色は DD-003 のまま変えない。
- **併せて直した提出の流れ（同じ確かめで見つけたもの）**: 帯の跳びを直したあとも、本物の流れで「数を入れて送る」をたどると、送れない・送ったつもりで送れていない経路が残っていた。どれも押す場所ではなく、保存と提出の順番の問題なので、ここにまとめて残す。
  1. 「提出する」は、下書きの保存中・保存待ちでも押せる。押したら下書きの予約を取り消し、いちばん新しい入力（`latestInput`）で提出する。下書きと提出は `queuedSave` で1件ずつ順に送り、後から送った下書きが提出を上書きしない。
  2. 続けて2回押しても1回だけ送る（`submitLock` と、マウスの `event.detail > 1` を見る。キーボードの押下は `detail` が 0 なので止めない）。返事を待つ間は入力欄と帯のボタンを止め、帯の文を「提出しています…」にする。
  3. 提出が断られたら、まだ保存していない変更（`savedVersion` と `editVersion` が違う）を下書きとして予約し直す。断られたあとに値を変えたら、帯を「保存待ち」に戻す（`draftFailed` で、下書きの失敗と提出の断りを分ける）。
  4. 未入力の例（「（例：…）」）と「最初の未入力の欄へ移る」の飛び先は、画面の上から下の順（`inScreenOrder`）で選ぶ。保存APIが返す例も同じ順にした。拾うのは `missingRequired`（`src/lib/submission-check.ts`）の1つで、回答画面の知らせと保存APIの断りが同じものを使う（件数と「例：」が食い違わない）。以前は登録の順で選んでいたため、画面のずっと下の設問へ飛ぶことがあった。選択肢が登録されていない設問も、案内の文を飛び先にする（飛び先が無いと、押しても何も起きない）。
  5. `NumberField` が「最後に親へ渡した値」とみなす初期値は、初期値が数ならその数にする。欄の決まりで読み直すと、整数だけの欄に残っていた 1.5 が null と読まれ、欄を空にしても親へ知らせず 1.5 が保存され続けた。組み立て画面の下限の欄は、外から設問を読み直した回数を `key` にして作り直す（値そのものを `key` にすると、手で打った「3a」も作り直されて、打ちかけの文字と誤りの文が消える）。
  6. 回答画面で入力欄を止める条件を、保存APIが断る条件と同じ線引きにそろえ、理由と文を1つの関数で選ぶ（`judgeAnswerBlock`・`answerLockedReason`。順と文は [spec §28-16](./spec.md#28-16-アンケートの見本と回答できない理由2026-10-16-の追加要望)）。締切だけで決めていたため、等級が変わった人の下書きは欄が開いたままで、打つたびに自動保存が断られ「保存できていません」が続いた。下書きのアンケートで止める文もこの関数から出す（準備中の文を2か所に持つと、同じ下書きに2通りの文が出ていた）。保存APIは画面を通さずに呼ばれたときの最後の守りで、等級なしと等級違いを同じ文で断る。線引きは同じだが、理由の選び方は画面ほど細かくない。
  7. 断られた理由は、提出（`submitError`）と下書き（`draftError`）で分けて持つ。1つにまとめていると、提出を断られたあとの下書きの保存し直しが通った時点で、提出の断りまで消えていた（下書きは範囲を問わずに通る）。提出の断りを消すのは、次に答えを変えたときと次に提出するときだけ。2つが同じ文なら1回だけ出す。確認の欄を開いている間は、提出の断りを欄の中にだけ出し、画面の頭には出さない。下書きの失敗は提出の断りではないので、確認の欄には入れない。
  8. 保存APIは、範囲を外れた数が2つ以上あるとき、送られた順ではなく画面の上にある欄を挙げる（`inScreenOrder` で並べてから `checkAnswerNumbers` に渡す）。4 の未入力の例と同じ順にそろえた。
  9. 画面に描く節の順（制度の区分順に自由記入を継ぎ足したもの）を `SCREEN_SECTIONS`（`src/lib/question-order.ts`）の1か所で持ち、回答画面・組み立て画面（`FormBuilder`）・回答本文（`ResponseSnapshot`）がそれを使う。各画面がそれぞれ継ぎ足していたので、`inScreenOrder` の順と画面の順がずれうる形だった。設問の保存の受け口（`actions/forms.ts`）が受け付ける節も `z.enum(SCREEN_SECTIONS)` で同じ組から作る。節の見出しの名前も `sectionLabel`（`src/lib/question-order.ts`）の1つで決める。名前を画面ごとに書いていたため、組み立て画面だけ自由記入の節を英字の「free」と出していた。
  10. 見本の画面では、回答者に向けた指示の文（節の説明と説明文）を引用の形（`RespondentGuide`）で出し、説明文の改行はどの画面でも残す（出す画面と形は spec §28-16）。利用者が「実績の数値を入力できない」と読んだのは、見本の画面の「入力してください」を、見ている自分への指示と読んだためでもあった。改行は回答画面だけ落ちていた。
  11. `/forms/[id]` で回答できないときは、見本の先頭の注記で理由を言い直さず、上の注記（`AnswerBlockNote`）の1回だけにする。回答できる人には、上の回答ボタンの名前で入口を言う（文は spec §28-16）。同じ理由が上下に2つ並び、回答できる本人には三人称で、上のボタンと別の入口を案内していた。
  12. 回答一覧の氏名を回答本文へのリンクにする条件を、リンク先と同じ関数（`canReadResponseBody`）で決める（条件は spec の画面一覧の 20-1）。入力途中の人の氏名もリンクになっていて、押した先が「この回答は開けません」の行き止まりだった。
- **併せて直した記述**: spec §6 に押す場所の決まりと、帯を出す画面に `/admin/improvements` を足した。spec §27-4 に「同じ値を入れ直した・欄を離れただけでは変えたことにしない」を足した。spec §28-16 に、締切の文と回答画面の案内の分け方と、`answerLockedReason` の文と、説明文の引用の形・見本の注記で理由を言い直さないことを足した。spec の画面一覧の 20-1（`/admin/forms/[id]/responses`）に、回答一覧の氏名をリンクにする条件を足した。
- **固定した検査**（ファイルごとに1回。括弧の番号は、「選んだ形」は「形 N」、「併せて直した提出の流れ」は「流れ N」）:

## DD-019 見本に入力欄を足さず、設定できる人に保存しない試しの回答を開けるようにした（2026-10-16）

- **場面の1文**: 等級の無い管理者が `/forms/[id]` の見本を見て、「数値を入れる欄も送信ボタンも無い。アンケートに答えて送る機能は成り立っているか」と尋ねた（[spec §28-17](./spec.md#28-17-試しの回答2026-10-16-の追加要望)）。
- **原因**: 回答の機能そのものは成り立っていた。対象の等級の社員で `/me/forms/[id]` を開くと、全28問に答えて提出でき、回答一覧と CSV にも出た。見ていたのは読むための見本（`FormPreview`）で、入力欄と送信ボタンは決まりとして置いていない（§28-16）。足りなかったのは、設定する人が「答えて送れるか」を自分の手で確かめる場所だった。管理者には等級が無く、本物の回答画面は開けない（§3-1「読めるかはロール、答えられるかは等級」）。§28-16 は、見本に数値の欄を置くか、保存しない回答画面を開けるようにするかを決めずに残していた。
- **選んだ形**:

## DD-031 本番 D1 の書き出しを、age の公開鍵で暗号化してから Artifact に置く（2026-10-24）

- **場面の1文**: Deploy workflow と Migrate workflow は、移行の前に本番 D1 の全体を書き出して Actions の Artifact に14日置く。リポジトリは Public なので、Artifact は GitHub にログインした誰もが落とせる。この置き方は [バックログ](./backlog.md) の SECURITY-014 で、0040（P05）のマージの前に決めることになっていた（DD-026）。2026-10-24 に利用者が「ベストプラクティスの方法でお任せします」と判断を任せた。
- **選んだ形**:
  1. **書き出しを [age](https://age-encryption.org)（X25519）の公開鍵で暗号化し、`backup.sql.age` だけを置く**。平文の `backup.sql` はランナーの中で消す。暗号化と検査は `.github/scripts/encrypt-d1-backup.sh`（`check` と `encrypt`）が行う。
  2. **CI が持つのは公開鍵だけにする**。repo の Variables の `D1_BACKUP_AGE_RECIPIENT` に置く（空白か改行で区切って複数を書ける）。開く鍵（秘密鍵）は CI・Secrets・リポジトリに置かず、利用者の手元（リポジトリの外）に置く。公開鍵は人に知られても書き出しを開けないので、Secrets でなく Variables に置く。
  3. **設定が無いときは止める（fail-closed）**。受け手が無いか形が違う（`age1` と bech32 の58文字でない）ときは、書き出す前に止め、移行も配布もしない。形の違う値はログに出さない（秘密鍵を貼り間違えたときに漏らさない）。暗号化した先頭の行が `age-encryption.org/v1` でなければ、出力を消してから止める（保管の step は `always()` で動くため）。
  4. **止まるのは移行を伴う実行だけにする**。Deploy workflow の準備と暗号化の step は、未適用の移行があるとき（`migration_plan` が `pending`）だけ動く。移行の無い Deploy は今までどおり出る。Migrate workflow は必ず書き出すので、変数が無ければ必ず止まる。
  5. **鍵は2本を勧める**（1本をなくしても開けるように）。鍵の用意・変数の設定・開き方は [デプロイ時の注意](../deploy-notes.md) §1 の「書き出しの暗号化」に書いた。
  6. **今までの書き出し**: 2026-10-21 の2つ（0038・0039 の Deploy。実行 `39562261411`・`39564492520`）は平文で保管された。2026-10-24 に読んだ時点で、repo の Artifact は0件だった（どちらも期限 2026-11-04 の前に消えている。消した記録は無く、理由は推し量らない）。「今ある書き出しを消すか」の判断は要らなくなった。
- **決め手の軸**: Public のリポジトリで、評価や給与に近い本番のデータを誰でも落とせる形に置かないこと（README「本番運用とデータの注意」）。DD-020 の9・DD-026 の戻す元（表と列を取り出して入れ直す書き出し）を残すこと。CI に新しい秘密を増やさないこと。設定が抜けたときに平文で置かれる経路を作らないこと。
- **却下した候補と理由**:
  - private の保管先（R2 など）に置く: CI に書き込みの鍵が要り、秘密が1つ増える。期限の掃除も自前で作ることになり、Artifact の14日の期限と一覧の画面を使えない。
  - 要る表に絞る: 戻す元の範囲が移行ごとに変わり（0034 は表示名、0039 は KGI の表、0040 は割り当て）、絞り漏れがそのまま戻せない欠けになる。絞った表にも個人の値が残る。
  - 書き出しをやめ、D1 の Time Travel だけにする: Time Travel は DB の全体を時点へ戻すので、移行の後の保存まで消える。表と列だけを入れ直す戻し方（DD-020 の9、[デプロイ時の注意](../deploy-notes.md) §9 の 0034）ができない。全体を戻すときの別の手段として deploy-notes に書いた。
  - Secrets に置いた共通の鍵で暗号化する（`gpg --symmetric` など）: CI が開く鍵を持つので、workflow を書き換えれば開ける。公開鍵なら CI は開けない。
  - 変数が無いときは平文で置いて警告だけ出す: 設定が抜けたまま平文が置かれる（fail-open）。
- **DD-020・DD-026 との関係**: DD-020 の9（0039 を書き出しから戻す）は、2つの書き出しが消えたので使えない。消した KGI の値は、書き出しからはもう戻せない。DD-020 の9 の「書き出しの置き場所を SECURITY-014 で変えたら、戻す元もそれに合わせる」に従い、これより後の戻す元は暗号化した書き出しで、開いてから表と列を取り出す。DD-026 の 0040 の戻す元は、まず記録の表 `behavior_band_default_rewrites` で、もう1つが暗号化した書き出し。
- **規範との関係**: P05 の write_scope の外（`.github/workflows/deploy.yml`・`.github/workflows/migrate.yml`・`.github/scripts/encrypt-d1-backup.sh`・`scripts/deploy-workflow-contract.test.mjs`）を触る。SECURITY-014 は P05 のマージの前に決めることになっていて、決めを workflow に入れないまま P05 をマージすると、0040 の Deploy で平文の書き出しが1つ増える。だから P05 の変更に入れる。変数の設定と Deploy（本番への変更）は利用者が行い、手で `db:backup`・`db:migrate:remote` を流さない。
- **範囲の外**: 秘密鍵の保管の仕方（利用者の手元の運用）。書き出しを14日より長く置くか（DD-020 の9 で利用者が決める）。初期パスワードの控え（`CREDENTIAL_ENC_KEY`。別の仕組み）。
- **固定する検査**: `scripts/deploy-workflow-contract.test.mjs`（`pnpm test`）。step の順（準備 → 書き出し → 暗号化 → 保管）、平文を指す `path` が無いこと、開く鍵の名前が workflow に無いこと。偽の `age` で台本を流し、受け手が無い・空白だけ・形が違うと止まること、形の違う値を出さないこと、複数の受け手、暗号化したら平文が消えること、出力が age の形式でなければ消して止まること、書き出しが無いか空なら止まること。
- **見直す条件**: 鍵をなくしたとき（変数の公開鍵を替える。それまでの書き出しは開けない）。リポジトリを private にしたとき。GitHub が Artifact を落とせる人の範囲を変えたとき。
