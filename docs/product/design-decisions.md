# 前例のない設計判断の記録

規範（Skill `jp-web-design` / `ux-design`）に明示が無い、または規範の既定とは違う形を選んだときだけ、ここに1件1ブロックで残す。通常の表示形式・ラベル・加工の判断は書かない（それは各画面の実装とテストが正本）。

書式: 場面の1文 / 選んだ形 / 決め手の軸 / 却下した候補と理由。

## DD-001 畳んだメニューを「隠す」から「絵だけの列（68px）」に変えた（2026-08-15）

- **場面の1文**: 管理者が制度設定・評価・名簿のあいだを日に何度も往復しながら、本文を広く使いたくてメニューを畳んでいる。
- **選んだ形**: 1024px 以上では、畳んだときに幅 68px の絵だけの列を残す。乗せたときとキーボードで移動したときの両方で、右側に名前の吹き出しを出す。名前は `aria-label` にも必ず渡す。
- **決め手の軸**: 識別の手がかり（往復先が15項目以上あり、完全に隠すと毎回開いて閉じる操作が挟まる）。畳む目的は本文の幅であって、行き先を捨てることではない。
- **却下した候補と理由**:
  - 完全に隠す（従来の実装）: 本文は最も広くなるが、行き先を選ぶたびに開閉2操作が増える。往復の多いこのアプリでは費用のほうが大きい。
  - 640〜1023px でも絵の列にする: この幅は本文の1カラムが既に狭く、68px を削ると表が潰れる。重ねて開く引き出しのまま据え置いた（残課題 UX-022）。
- **規範との関係**: `jp-web-design` は「アイコン単独ボタンを作らない／迷ったらアイコンなし」を既定にするが、同スキルの `references/layout-responsive.md`「ナビゲーション骨格」は 641〜1024px で 68px のアイコンレールを認めている（`aria-label` 必須・吹き出し（tooltip）だけに意味を隠さないことが条件）。前例のない部分は、1024px 以上でも畳んだときに 68px の列を出すことと、規範が想定する項目数4〜5に対して本アプリは15項目以上あることの2点。そのため「同じメニューの中で絵を重複させない」をテスト（`src/lib/nav.test.ts`）で固定した。
- **併せて反転した記述**: `src/components/AppSidebar.tsx` にあった「閉じるときは『アイコンだけ残す』のではなく完全に隠す」というコメントは、この判断で置き換えた。

## DD-002 絵の意味と実物の対応を1枚の表に閉じた（2026-08-15）

- **場面の1文**: 20以上の画面に絵を足すが、同じ意味に別々の絵が付くと、絵そのものが読み飛ばされるようになる。
- **選んだ形**: `src/components/Icon.tsx` の `ICONS` だけが絵の実物（lucide-react）を知る。画面は意味の名前（`users` / `warning` / `criteria` …）でしか絵を呼べない。見出しの絵は画面ごとに選ばず、いまのURLから左のメニューの絵を引く（`src/components/PageHeadIcon.tsx`）。
- **決め手の軸**: 一貫性。「左のこの絵＝この画面」を突き合わせて覚えられることを、絵を足す目的にした。
- **却下した候補と理由**: 画面ごとに絵を選ぶ（自由度は高いが、同義の絵が増えて意味が薄まる）／絵をデータベースに持つ（設定できても運用で誰も揃えられない）。
- **固定した検査**: `src/components/ui-rules.test.ts` の「絵の実物を持ってよいのは Icon.tsx だけ」「絵文字を画面に書かない」。

## DD-003 配色とテーマをキット既定の平賀配色へ移さず、アプリ独自の契約を承認済みと宣言した（2026-09-29）

- **場面の1文**: キット更新で `jp-web-design` が「既存アプリも平賀配色・ライトのみへ自動移行する」を既定にしたが、本アプリは利用者ごとの配色の選択と、自動・明るい・暗いの切り替えを、仕様・保存データ・テストで既に持っている。

- **平賀配色の扱い**: 移しはしないが、選べる系統の1つ `indigo`（インディゴ）として加え、同日に既定の系統にした（どちらも利用者の判断）。明るいほうは平賀配色の値を骨格18個へ割り当て、平賀配色に無い暗いほうはこのアプリで作った。それまで既定だった無彩色の `graphite` は、値を変えずに系統の1つとして残した。暗い表示・系統の選択・保存・`/api/theme-choice` はそのまま残るので移行ではなく、上の宣言と report-only の判定は変わらない。既定は「保存値なし」で表すため、グレーのまま使っていた人の画面もインディゴに変わる（メニューで選び直せる）。DB の許可値はマイグレーション 0030 で足した。
- **規範との関係**: 文字組み・レイアウト・操作領域・a11y・情報設計は `jp-web-design` に従う。例外は配色の値とテーマの切り替えだけ。
- **固定した検査**: `scripts/aidd-kit-boundary.test.mjs`（守る内容はテスト名が正本）。
- **見直す条件**: キット側に既存アプリの独自配色を正式に除外する規定が入ったら、宣言をその形へ寄せる。

## DD-005 長押しドラッグを Pointer Events で自作した（2026-10-13）

- **場面の1文**: 管理者が等級要件・昇格の条件・設問・選択肢を、スマホでも PC でも並べ替えたい。
- **選んだ形**: `useLongPressReorder` を自作する。タッチは 350ms 動かさずに押し続けると持ち上げ、その前に 8px 動けばスクロールとみなす。キーボードは Space で持ち上げ、↑↓で動かし、Space で置き、Esc で戻す。矢印のボタン（先頭・上・下・末尾）も残す。保存は並び全体を送り、id の集まりが違えば 409。
- **決め手の軸**: 依存を足さないことと、タッチで動くこと。
- **却下した候補と理由**:
  - HTML の Drag and Drop API: タッチの端末で動かない。
  - dnd-kit: 依存が増え、Worker の実行ファイルの上限（3,072 KiB）に近づく。この画面の数なら自作の費用が小さい。
- **規範との関係**: WCAG 2.2 SC 2.5.7（ドラッグの代替）を、矢印のボタンとキーボードで満たす。
- **固定した検査**: `src/components/reorder/useLongPressReorder.test.ts`・`src/lib/domain/reorder.test.ts`。
- **見直す条件**: 画面をまたぐ移動（別の一覧へ落とす）が要るようになったら、ライブラリを比べ直す。
- **更新（2026-10-16、不具合の修正）**: 等級要件で、ドラッグで並べ替えてから、もう一度ドラッグで元に戻すと行が消えた（再読み込みで戻る）。
  - 原因: 行の段組みを、一覧の幅のコンテナクエリ（`container: reorder / inline-size`）で決めていた。Chromium では、size container の中の一覧を2回続けて並べ替えると、2回目の保存のあと行の箱が作られず、何も描かれない（[issues.chromium.org/379030050](https://issues.chromium.org/issues/379030050) と同じ形）。矢印のボタンで2回続けても起きる。一覧を `contain: inline-size` だけにすると起きない。
  - 選んだ形: `ReorderList` が ResizeObserver で一覧の幅を測り、超えた境目（30・36・60rem）を一覧の `data-reorder-w` に書く。CSS はこの値で段組みを選ぶ。測るまでは同じ境目をコンテナクエリで当て（`.reorder-list:not([data-reorder-w])` にだけ container を置く）、読み込みのたびに行が狭い段組みから跳ねないようにする。並べ替えるころには測り終えているので、不具合の条件に入らない。`contain: inline-size` は残す（一覧の幅を中身から切り離し、印の書き換えで測り直しが続かないようにする）。境目の規則は `:where()` で包み、コンテナクエリで書いていたときと詳細度を同じにした。段組みは修正の前と画素まで同じ。
  - 却下した候補と理由: 画面の幅のメディアクエリ（サイドバーの有無で、一覧の幅が画面の幅と合わない。1024px と 900px で一覧の幅が逆になる）。コンテナクエリのまま、保存のあとに一覧の style を触って描き直させる（不具合の形に頼る回避で、起きる時機を外すと効かない）。
  - ほかの size container（`.split-host`・`.list-host`・`.record-list`）は、サーバーが描く一覧で、画面の中で行を並べ替えないので変えない。
  - 固定した検査: `src/components/reorder/ReorderList.test.ts`（境目の書き方、CSS の境目が部品の境目と同じこと、container を測る前の一覧にだけ置くこと）、`e2e/reorder-twice.spec.ts`（ドラッグと矢印で2回続けて並べ替えても、行が見えたまま）。修正前の規則（一覧を size container にする）を画面に足すと、ドラッグの検査は2回目の保存のあとで行が読み上げの木からも消えて落ちる。矢印のボタンだけでは起きない（2026-10-16 に確かめた）。
  - 見直す条件: Chromium で上の不具合が直り、対応する版がそろったら、コンテナクエリだけの形へ戻すかを比べる。

## DD-009 会社選択と既存アカウントへの所属追加の方針を統一した（2026-10-14）

- **場面の1文**: 複数所属の人が意図した会社で操作し、会社をまたぐ所属追加を権限のある担当者が管理したい。
- **選んだ形**: 有効な会社の選択（cookie）を優先し、未選択・無効な選択なら最古の有効所属（`createdAt`、同時刻は所属IDの順）を使う。会社名の順にはしない。所属を持たない全体管理者の既定は従来どおり有効な実会社の会社名順。既存アカウントへの別会社の所属追加は全体管理者だけの専用操作とし、新規利用者登録ではシステム全体のメール重複を拒否する。所属追加で資格情報を変えず、所属と監査を同じbatchで保存する。
- **更新（2026-10-14、利用者の選択）**: 委任に基づく上の裁定の2点を、中立な問で利用者に選び直してもらった（`system-spec/spec-state.json` の `qa-w11`・`qa-w12`、決定 D-008・D-009）。

## DD-013 アカウントの権限にかかわる操作を、専用の追記だけの表に、本体と同じ batch で残した（2026-10-15）

## DD-015 アンケートの設問の集計との紐づけは、保存のときにサーバーが保存済みの値と突き合わせる（2026-10-16）

- **場面の1文**: 管理者が下書きのアンケートを組み立て画面で直して保存する。画面は紐づけ（等級要件・昇格要件・行動指針・KPI 項目と設問の key）と昇格の必須要件の印を引き継ぐだけだが、保存の処理（`saveFormQuestions`）は送られてきた値をそのまま書いていた。点数の計算（`evaluate.ts`）はこの値をそのまま読むので、自由設問を昇格の必須要件にする・別の会社の要件の id を入れる・作り直しの前に開いた古い画面から古い紐づけを書き戻す、のどれもが通っていた。紐づけのある設問の答え方を画面で変えると（KPI の数値 → 文章、等級要件のはい/いいえ → 数値）、点数の計算から黙って外れていた。
- **選んだ形**:
  1. 紐づけの5つの欄と `isGate` は、保存済みの同じ設問（同じ版・同じ id）の値と同じものだけを受け付ける。新しい設問と、この版に無い id の設問には紐づけを許さない。違えば保存全体を断り、読み込み直しを促す（`checkQuestionLinks`。`src/lib/domain/form-question-links.ts`）。
  2. 紐づけのある設問は、まとまりと答え方も保存済みの値から変えさせない。点数の計算は答え方で値の読み方を、昇格の必須要件の種類をまとまりで決めるため。組み立て画面でも2つの選択欄を押せなくし、理由を1行添える（サーバーが断るものを画面で選ばせない）。
  3. この版に無い id で送られた自由設問は、新しい id で保存する（別の版・別の会社の設問の id と主キーがぶつからないように）。同じ id が2つ送られたら断る（紐づけが写されて同じ要件が2回数えられるため）。
- **決め手の軸**: 点数の元になる値は、書いた側（作り直し）だけが決める。画面の作りに頼らず、保存の入口で守る。
- **却下した候補と理由**:
  - 送られた紐づけを黙って捨て、保存済みの値で上書きする: 通常の保存は同じ結果になるが、作り直しの後に古い画面から保存したとき、紐づけのある設問が黙って自由設問になり、点数の計算から外れる。断って読み込み直しを促す。
  - 自社の `kpi_questions` にある組なら受け付ける: 組み立て画面に設問を KPI へ結び付ける操作は無く、結び付けるのは作り直しだけ。受け付ける理由が無く、同じ key の設問が2つできると計算の変数が上書きされる。
  - 紐づけのある設問の削除も止める: 下書きで設問を減らすのは今までどおり管理者の判断に残した（減らした分は達成率の分母からも外れる、という今の計算のまま）。
- **規範との関係**: OWASP の Mass Assignment の対策（利用者が書いてよい欄だけを受け、ほかはサーバーが決める）に当たる。画面の部品は `jp-web-design` の「操作できないものは押せない形で見せ、理由を添える」に従う。
- **固定した検査**: `src/lib/domain/form-question-links.test.ts`、`src/actions/forms-save-questions.test.ts`（作り直しで書いた紐づけの往復・新しい設問の紐づけと印・書き換え・答え方の変更・この版に無い id）、`src/components/form-freshness-regression.test.ts`（紐づけのある設問の2つの選択欄）。
- **見直す条件**: 組み立て画面から設問を KPI に結び付ける操作を足すとき（そのときは自社の `kpi_questions` の組と、同じ key が版の中で1つであることを検査に足す）。
