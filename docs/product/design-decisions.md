# 前例のない設計判断の記録

規範（Skill `jp-web-design` / `ux-design`）に明示が無い、または規範の既定とは違う形を選んだときだけ、ここに1件1ブロックで残す。通常の表示形式・ラベル・加工の判断は書かない（それは各画面の実装とテストが正本）。

書式: 場面の1文 / 選んだ形 / 決め手の軸 / 却下した候補と理由。

---

## DD-001 畳んだメニューを「隠す」から「絵だけの列（68px）」に変えた（2026-08-15）

- **場面の1文**: 管理者が制度設定・評価・名簿のあいだを日に何度も往復しながら、本文を広く使いたくてメニューを畳んでいる。
- **選んだ形**: 1024px 以上では、畳んだときに幅 68px の絵だけの列を残す。乗せたときとキーボードで移動したときの両方で、右側に名前の吹き出しを出す。名前は `aria-label` にも必ず渡す。
- **決め手の軸**: 識別の手がかり（往復先が15項目以上あり、完全に隠すと毎回開いて閉じる操作が挟まる）。畳む目的は本文の幅であって、行き先を捨てることではない。
- **却下した候補と理由**:
  - 完全に隠す（従来の実装）: 本文は最も広くなるが、行き先を選ぶたびに開閉2操作が増える。往復の多いこのアプリでは費用のほうが大きい。
  - 640〜1023px でも絵の列にする: この幅は本文の1カラムが既に狭く、68px を削ると表が潰れる。重ねて開く引き出しのまま据え置いた（残課題 UX-022）。
- **規範との関係**: `jp-web-design` は「アイコン単独ボタンを作らない／迷ったらアイコンなし」を既定にするが、同スキルの `references/layout-responsive.md`「ナビゲーション骨格」は 641〜1024px で 68px のアイコンレールを認めている（`aria-label` 必須・吹き出し（tooltip）だけに意味を隠さないことが条件）。前例のない部分は、1024px 以上でも畳んだときに 68px の列を出すことと、規範が想定する項目数4〜5に対して本アプリは15項目以上あることの2点。そのため「同じメニューの中で絵を重複させない」をテスト（`src/lib/nav.test.ts`）で固定した。
- **併せて反転した記述**: `src/components/AppSidebar.tsx` にあった「閉じるときは『アイコンだけ残す』のではなく完全に隠す」というコメントは、この判断で置き換えた。

## DD-002 絵の意味と実物の対応を1枚の表に閉じた（2026-08-15）

- **場面の1文**: 20以上の画面に絵を足すが、同じ意味に別々の絵が付くと、絵そのものが読み飛ばされるようになる。
- **選んだ形**: `src/components/Icon.tsx` の `ICONS` だけが絵の実物（lucide-react）を知る。画面は意味の名前（`users` / `warning` / `criteria` …）でしか絵を呼べない。見出しの絵は画面ごとに選ばず、いまのURLから左のメニューの絵を引く（`src/components/PageHeadIcon.tsx`）。
- **決め手の軸**: 一貫性。「左のこの絵＝この画面」を突き合わせて覚えられることを、絵を足す目的にした。
- **却下した候補と理由**: 画面ごとに絵を選ぶ（自由度は高いが、同義の絵が増えて意味が薄まる）／絵をデータベースに持つ（設定できても運用で誰も揃えられない）。
- **固定した検査**: `src/components/ui-rules.test.ts` の「絵の実物を持ってよいのは Icon.tsx だけ」「絵文字を画面に書かない」。

## DD-003 配色とテーマをキット既定の平賀配色へ移さず、アプリ独自の契約を承認済みと宣言した（2026-09-29）

- **場面の1文**: キット更新で `jp-web-design` が「既存アプリも平賀配色・ライトのみへ自動移行する」を既定にしたが、本アプリは利用者ごとの配色の選択と、自動・明るい・暗いの切り替えを、仕様・保存データ・テストで既に持っている。
- **選んだ形**: 配色とテーマは規範の既定に合わせず、`docs/product/spec.md` の「テーマ契約（全画面共通）」「配色（テーマの系統）」を正本として維持する。T2（`docs/product/T2-experience-spec.md` §5「アプリ全体の配色契約」）に行頭形式で承認済みの宣言（`brand_color_status: approved` / `brand_color_source: app-theme-contract`）を置き、`src/app/globals.css` の冒頭にも同じ宣言と `aidd-color-migration: exclude-brand` を置く。キットの移行は `src` を走査するため、T2 が走査範囲の外にあっても判定が report-only になるようにする。
- **決め手の軸**: 保存データとの整合と可逆性。利用者が選んで保存した配色と暗い表示を、キット更新で黙って失わせない。
- **却下した候補と理由**:
  - 平賀配色へ移行する: 約500箇所の色を置き換えることになり、保存済みの配色の選択と `/api/theme-choice` が意味を失う。暗い表示を使っている利用者の画面も変わる。
  - キットの判定スクリプトに例外を足す: 配布物を直接直すと次の更新で消える。キット側への提案に回す。
- **平賀配色の扱い**: 移しはしないが、選べる系統の1つ `indigo`（インディゴ）として加え、同日に既定の系統にした（どちらも利用者の判断）。明るいほうは平賀配色の値を骨格18個へ割り当て、平賀配色に無い暗いほうはこのアプリで作った。それまで既定だった無彩色の `graphite` は、値を変えずに系統の1つとして残した。暗い表示・系統の選択・保存・`/api/theme-choice` はそのまま残るので移行ではなく、上の宣言と report-only の判定は変わらない。既定は「保存値なし」で表すため、グレーのまま使っていた人の画面もインディゴに変わる（メニューで選び直せる）。DB の許可値はマイグレーション 0030 で足した。
- **規範との関係**: 文字組み・レイアウト・操作領域・a11y・情報設計は `jp-web-design` に従う。例外は配色の値とテーマの切り替えだけ。
- **固定した検査**: `scripts/aidd-kit-boundary.test.mjs`（守る内容はテスト名が正本）。
- **見直す条件**: キット側に既存アプリの独自配色を正式に除外する規定が入ったら、宣言をその形へ寄せる。

## DD-004 1人を複数の会社に所属させるのに、自前の所属の表と cookie を使った（2026-10-13）

- **場面の1文**: 同じ人が2つの会社で評価を受けたり付けたりするので、ログインしたまま会社を切り替え、その会社の役割・等級・上司で画面を見たい。
- **選んだ形**: `company_memberships`（利用者×会社の一意。役割・等級・事業所・上司を持つ）を足し、選んでいる会社は既存の cookie `hr_company` で伝える。サーバーは cookie の会社を所属の表で確かめてから使い、無ければ元の所属（一番古い所属）に戻す。`users` の会社ごとの列は元の所属の写しとして同じ batch で書き続ける。
- **決め手の軸**: 既存の会社の境界との連続性。`viewer.companyId` を読む箇所はそのまま正しくなり、所属が1つの人の動きは変わらない。
- **却下した候補と理由**:
  - Better Auth の organization plugin: 会社・役割・招待の表を別に持ち、既存の `companies` と `users.role` との二重管理になる。
  - URL に会社を入れる（`/c/{id}/...`）: 47画面のパスと台帳が全部変わり、ブックマークと通知のリンクが壊れる。
- **規範との関係**: 規範に定めが無い。会社の切り替えはサイドバーの既存の場所に出す。
- **固定した検査**: `src/actions/memberships.integration.test.ts`（所属していない会社への切り替えの拒否・所属の重複の拒否・全体管理者による所属追加でパスワードを変えないこと）、`src/lib/session.integration.test.ts`（有効な選択の優先と安定した復帰先）。所属追加の権限と新規登録のメール重複の扱いは、2026-10-14の DD-009 で確定した。
- **見直す条件**: 会社ごとにログインを分ける要望（SSO の会社別の設定など）が来たら、組織の単位をログインの側へ移す。

## DD-005 長押しドラッグを Pointer Events で自作した（2026-10-13）

- **場面の1文**: 管理者が等級要件・昇格の条件・設問・選択肢を、スマホでも PC でも並べ替えたい。
- **選んだ形**: `useLongPressReorder` を自作する。タッチは 350ms 動かさずに押し続けると持ち上げ、その前に 8px 動けばスクロールとみなす。キーボードは Space で持ち上げ、↑↓で動かし、Space で置き、Esc で戻す。矢印のボタン（先頭・上・下・末尾）も残す。保存は並び全体を送り、id の集まりが違えば 409。
- **決め手の軸**: 依存を足さないことと、タッチで動くこと。
- **却下した候補と理由**:
  - HTML の Drag and Drop API: タッチの端末で動かない。
  - dnd-kit: 依存が増え、Worker の実行ファイルの上限（3,072 KiB）に近づく。この画面の数なら自作の費用が小さい。
- **規範との関係**: WCAG 2.2 SC 2.5.7（ドラッグの代替）を、矢印のボタンとキーボードで満たす。
- **固定した検査**: `src/components/reorder/useLongPressReorder.test.ts`・`src/lib/domain/reorder.test.ts`。
- **見直す条件**: 画面をまたぐ移動（別の一覧へ落とす）が要るようになったら、ライブラリを比べ直す。

## DD-006 権限一覧を1つの表に役割のタブを足し、狭い幅ではカードにした（2026-10-13）

- **場面の1文**: 管理者が、利用者の役割を決める前に「その役割で何ができるか」を、どの画面からでもすぐ確かめたい。
- **選んだ形**: 行をページ、列を4つの役割にした1つの表（`PermissionMatrix`）。役割のタブで1つの列に絞れる。768px 未満ではページごとのカードに切り替える。可否は記号（○・△・—）と言葉で示す。同じ部品を権限一覧のページと、利用者一覧・社員一覧から開くモーダルで使う。説明（`InfoTip`）はポインター・フォーカス・タップで出し、Esc で消える。
- **決め手の軸**: 比べやすさ（役割を横に並べる）と、狭い幅での読みやすさ。
- **却下した候補と理由**:

- **規範との関係**: `jp-web-design` は表を横にはみ出させないことを求める。狭い幅のカードへの切り替えはその形。色だけに意味を持たせない（記号と言葉）。
- **固定した検査**: `src/components/permissions/PermissionMatrix.test.ts`、`e2e/improvement-requests-2026-10.spec.ts`（4幅）。
- **見直す条件**: 役割が増えたら列の数を見直す。

## DD-007 権限の定義をルート台帳に足し、コードは台帳を読むだけにした（2026-10-13）

- **場面の1文**: 権限一覧に出す中身と、実際にページ・処理を止める判定が、いつのまにか食い違うのを防ぎたい。
- **選んだ形**: ルート台帳（`route-ledger.json`）の各ページに `permissions`（概要・操作 id・最低の役割・説明）を足す。画面に結び付かない操作は `sharedOperations` に置く。ページの入口 `requireRoute(path)`・サーバー処理の `runAction({ operation })`・メニューの絞り込み・権限一覧は、どれも `src/lib/route-access.ts` を通して台帳を読む。未知の操作 id は 403。
- **決め手の軸**: 正本を1つにすること。台帳を変えれば、止める判定と見せる一覧が同時に変わる。
- **却下した候補と理由**:
  - DB の表: 実行中に書き換えられ、権限の変更が配布と試験を通らなくなる。
  - TS のモジュール: 台帳（ページの一覧と幅の約束）と別の正本が増える。
- **規範との関係**: 規範に定めが無い。
- **固定した検査**: `src/lib/permissions-contract.test.ts`（全ページの入口・全サーバー処理・全メニューが台帳と合う）、`scripts/route-ledger.test.mjs`（47画面と `permissions` の形）。
- **見直す条件**: 会社ごとに権限を変える要望が来たら、台帳を既定にして会社ごとの上書きを DB に持つ形を考える。

## DD-008 等級の呼び名を保存せず、会社の等級名から表示のたびに作る（2026-10-13）

- **場面の1文**: 等級名を変えたら、行動指針の区分・昇格の段階・アンケートの題名まで、全ての表示が同じ名前に変わってほしい。
- **選んだ形**: `src/lib/domain/grade-label.ts` が、等級名から区分（「等級4-1・等級4-2」）・行動指針のセット（「等級1・等級2向け」）・昇格の段階（「等級1→等級2」）・アンケートの既定の題名を作る。区分の鍵 `pointGroup` は配点の表と結び付けるので値を変えず、画面にも出さない。既存の会社の等級名は移行 0034 で全社を一律に「等級1」〜「等級5-2」へ書き換え、書き換え前の値は `display_name_rewrites` に残して戻せるようにした。予行（P08）で見つかった漏れ（前の等級名で保存された既定の題名・KPI 項目の文・昇格要件の本文の写し）は、当て済みの 0034 を書き換えず移行 0035 の1本で直した。写しは当時の文面を残すためのものだが、変えるのは等級の呼び名だけで聞いた中身は変わらないので、0034 の昇格要件の本文と同じ扱いにした。回答CSVとメンバーCSVの取り込みは、`display_name_rewrites` の旧い値でも列・等級を引けるようにした（今の名前が優先）。
- **決め手の軸**: 一貫性（呼び名の作り方が1か所）と可逆性。
- **却下した候補と理由**:
  - 呼び名を各表に保存して、等級名の変更のたびに書き換える: 書き換え漏れが起き、利用者が付けた名前との区別が付かない。
  - 管理者が会社ごとに直す: 既存の会社が英語の区分名のまま残る（利用者の判断 qa-v02 問4 で一律を選んだ）。
- **規範との関係**: 規範に定めが無い。
- **固定した検査**: `src/lib/domain/grade-label.test.ts`・`src/lib/grade-label-static.test.ts`（画面の文字列に英語の区分名が無い）・`src/actions/grade-names.integration.test.ts`・`src/db/grade-names-migration.test.ts`・`src/db/migration-corrections.test.ts`（0034・0035 の書き換え・2回目0行・戻し）・`src/lib/import.integration.test.ts`（前の設問名の列）。
- **見直す条件**: 等級の段数が会社ごとに大きく違うようになったら、既定の等級名の表を会社の設定へ移す。

## DD-009 会社選択と既存アカウントへの所属追加の方針を統一した（2026-10-14）

- **場面の1文**: 複数所属の人が意図した会社で操作し、会社をまたぐ所属追加を権限のある担当者が管理したい。
- **選んだ形**: 有効な会社の選択（cookie）を優先し、未選択・無効な選択なら最古の有効所属（`createdAt`、同時刻は所属IDの順）を使う。会社名の順にはしない。所属を持たない全体管理者の既定は従来どおり有効な実会社の会社名順。既存アカウントへの別会社の所属追加は全体管理者だけの専用操作とし、新規利用者登録ではシステム全体のメール重複を拒否する。所属追加で資格情報を変えず、所属と監査を同じbatchで保存する。
- **決定の根拠**: 利用者がこの2点の説明を受けて「ベストプラクティスの方を選択して実行を進めてください。」と選定を委任したため、エージェントが上の方針を採用した。上の具体方針を利用者の逐語回答として扱わない。
- **決め手の軸**: 選択の安定性、既存運用との連続性、会社をまたぐ権限付与の明示性。改名で復帰先を変えず、他社既存アカウントの所属追加を新規登録の副作用にしない。
- **規範との関係**: [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) の最小権限・要求ごとの認可、[Multi Tenant Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html) の現在の所属に基づくテナント検証を適用する。最古の所属への復帰と全体管理者に限定する具体設計は、このアプリの運用に対する判断であり、OWASPが一律に要求するものではない（確認日: 2026-10-14）。
- **却下した候補と理由**:
  - 会社名順で所属を選ぶ: 改名で復帰先が変わり、元の所属の写しの基準とも別になる。
  - 既存メールの新規登録で所属を自動追加する: 新規発行と会社をまたぐ権限付与を一つの操作に混ぜる。会社管理者の招待を広げる場合は、本人の受諾を含む招待フローを別途設計する。
- **履歴との関係**: qa-v27の会社名順、qa-v28の既存メール自動所属追加は、この2点だけ本決定で更新する。原質問・原回答は保存し、訂正の記録を優先する。DD-004の所属テーブル・cookie・旧形式への写しの設計は継続する。
- **固定した検査**: `src/lib/session.integration.test.ts`、`src/actions/memberships.integration.test.ts`、`src/lib/permissions-contract.test.ts`、`src/actions/account-and-company-admin.integration.test.ts`、`e2e/improvement-data-flows.spec.ts`。
- **見直す条件**: 会社管理者が他社既存アカウントを招待する必要が生じた場合、対象者の本人確認・受諾・招待期限・監査を含む方式として再検討する。
